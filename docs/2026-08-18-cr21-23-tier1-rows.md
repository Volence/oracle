## CR-21 — `emulator/write_memory`: a row that predates every rule now governing it

### What exists today

One table row, `protocol.md:825`, legacy vintage:

```
| `emulator/write_memory` ← `write` | `addr`\|`symbol`; `bytes`\|(`value`+`width`) | `addr`, `len` *(68k RAM `$FF0000–$FFFFFF` only)* |
```

That is the entire specification. Measured against the rules the contract has grown since:

- **No prose.** The memory table's blockquote (`protocol.md:829` onward) specifies `emulator/read` in
  five normative bullets; `write_memory` has none.
- **No schema fragment.** The vendored `bus-protocol.schema.json` holds 29 method fragments (counted
  2026-08-18 — see the close below); `emulator/write_memory` is not among them, so §8 item 20's
  closed-result conformance cannot reach it.
- **Untyped `width`.** The row says `value`+`width` and never says `width` ∈ {1, 2, 4}, what happens
  when `value` overflows it, or what byte order multi-byte values land in.
- **No refusal code.** *"(68k RAM `$FF0000–$FFFFFF` only)"* names a bound with no error code and no
  refuse-vs-clip rule — where the contract's own precedents demand both: §2.1's limits rule (*"it
  **refuses** above it rather than clamping"*, `protocol.md:386-387`) and §11.12's
  refused-never-clipped. *(Amended per ruling correction i: this bullet originally cited CR-4 as the
  precedent, but CR-4 is D12's unbounded-wait gap, not a refuse-vs-clip rule.)*
- **Silent on the run-control state rule.** `protocol.md:793-801` names `run_to`, `run_to_scanline`,
  `run_frames`, `step*`, `press`, `play_input` and `reload_rom` as paused-machine-only, closing with:
  *"Leaving them unnamed would let one server refuse and another accept, both conforming."* `write_memory`
  is unnamed, so today that split is exactly what the contract permits for it.

**The ruling that opens this CR.** Whether the keep-dead register's "register-write op" entry covered
memory writes *"was never ruled"* — the owner ruled it on 2026-08-17
(`docs/2026-08-17-aeon-switchover-gap-list.md`, §"Assessment — two collisions with standing rulings"):
**"ADOPT, scoped. The keep-dead entry covers register writes only, not memory writes. `emulator/write_memory`
is to be built contract-first"** (quoted from lines 73-74; the ruling's own words are *"Owner ruling,
2026-08-17: ADOPT, scoped"*). So adoption is already decided; this CR exists to make the row specifiable
before the handler, per that same ruling.

### The proposed row, prose, and rule change (post-ruling authoritative text)

Replace `protocol.md:825` with *(amended per ruling R1 — the draft row's params column said "`len` ≤
`limits.maxWriteLen`", naming a `len` param the fragment correctly does not have; a write's length
derives from its payload, and D14 would have made the row text a standing spec bug on day one)*:

```markdown
| `emulator/write_memory` ← `write` | `addr`\|`symbol`; `bytes`\|(`value`+`width` 1\|2\|4); payload ≤ `limits.maxWriteLen` bytes | `addr`, `len` |
```

and add as its **own blockquote block** in the memory table's prose region — after the `read`/alias
block, NOT a sixth bullet inside `read`'s blockquote, whose opening "Five things are normative"
(`protocol.md:831`) would become false in place *(placement amended per ruling R4; text amended per
rulings R1, R2 and R5)*:

```markdown
> **`emulator/write_memory`** is the poke primitive. Scope: the work-RAM window
> `$E00000–$FFFFFF` (mirror-masked — the same window `read` reports as region "work RAM") — a base
> outside it, a range whose **end** runs past it, or any ROM/IO target is `-32004`, **refused,
> never clipped**. Exactly one payload spelling: `bytes` (hex string, even digit count) or
> `value`+`width` (`width` ∈ 1|2|4; `value` must fit `width`); both, neither, `width` with
> `bytes`, or `value` without `width` is `-32602`. A payload longer than `limits.maxWriteLen`
> bytes is `-32602` — refused, never truncated. Multi-byte values land **big-endian**, as the
> 68000 stores. Writes travel the bus path (hardware mirror masking), not a buffer poke. A poke
> is a debugger access, not a guest access: it is never offered to the watch surface — no watch
> matches it, and `watchpoint_hits.seen` does not move — because a hit's `pc` names the
> instruction that drove the access and a poke has none to name. Requires a **paused** machine
> (see the run-control state rule) — strict by design: relaxing a refusal later is additive (D5);
> introducing one is not.
```

In the run-control state rule (`protocol.md:793-801` — anchor corrected per ruling correction ii;

`run_to_scanline`, `run_frames`, `step*`, `press`, `play_input`, `reload_rom` **and `write_memory`**, and
append one sentence to the *why*: *"`write_memory` is named for `press`'s reason — a poke mid-free-run
mutates the timeline just as surely, and leaving it unnamed would let one server refuse and another

### Open questions: none — pins 1-4, each with its reasoning

1. **Window = work RAM `$E00000–$FFFFFF`** (the mirror window `debug_read` already serves), not the
   row's legacy `$FF0000–$FFFFFF`: an address you can `read` you can write, and watch hits can report
   mirror addresses — a client handed a mirror coordinate must be able to hand it back, which is
   §11.12's own argument for `emulator/read`. Refusal `-32004`, refused-never-clipped, ROM/IO refused.
2. **Requires a paused machine** (`-32005`, `data.reason="machineRunning"`), named in §6's run-control
   state rule. Strict-first: relaxing a refusal later is additive (D5); adding one later breaks clients.
   The rule's own closing sentence (`protocol.md:800-801`) is the reason it must be *named* rather than
   left to server taste.
3. **Exactly one payload spelling**: `bytes` (hex string, even digits) XOR `value`+`width`
   (width ∈ {1,2,4}, value must fit, big-endian as the 68000 stores). Both, neither, `width` with
   `bytes`, or `value` without `width` → `-32602`. Cap: payload ≤ `limits.maxWriteLen` bytes (4096,
   mirroring `maxReadLen`), over it `-32602` refused never truncated *(spelling amended per ruling
   R1 — there is no `len` param)*. This is the legacy MCP row's shape made total — every ambiguous
   combination gets a defined refusal instead of an implementation-defined guess, now mechanical in
   the fragment per ruling R3.
4. **Writes go through the bus path** — `mega_bus().write8(...)` with FC=5 (supervisor data), byte at a
   time. Hardware mirror masking for free; no `ram_mut()` debug back door added to core. The replay
   runner already took this route for the same reason (`runner.rs:22-23`). Per ruling R5, the bus
   path does NOT reach the watch surface: no watch matches a poke, because a hit's `pc` names the
   instruction that drove the access and a poke has none to name.

Ruling recommendation (b) — value-fits-width as schema if/thens on `width` — is **declined** for
this round: the prose rule and the server's own parameter checks suffice; revisit if a second server
misreads it.

## CR-22 — `emulator/reset`: a result key two servers share and no text defines

### What exists today

One table row, `protocol.md:783`:

```
| `emulator/reset` | — | `deferred` |
```

`deferred` appears **nowhere else in the contract** (checked by grep 2026-08-18: the word's only §6
occurrence is this row). No prose says what `true` or `false` means, no schema fragment types it, and
§5 already anticipates the method can fail by timeout — `-32010` is glossed *"operation timed out (e.g.
`reload_rom`, `reset`)"* (`protocol.md:731`) — which is more than the result itself gets.

Meanwhile **the reference server serves the key**: `oracle/linux-port/gui/ControlSocket.cpp`'s
`OpReset` (from `:459`) emits `.addBool("deferred", false)` at `:469` and `.addBool("deferred",
true)` at `:492`. What those paths actually do matters *(amended per ruling R1 — this section
originally claimed Oracle "emits both truthful values today" with the reset draining after the
reply; the code says the opposite)*: the `:469` fallback path calls `FlagInitialize()`, which flags
a reset the system applies on its next cycle, so even "applied before the reply" is an
interpretation the code does not show; and the `:492` main path queues the request, **busy-waits up
to 5 seconds for the main thread to run `doFullReset` and set the done flag**
(`ControlSocket.cpp:479-486`, `main_gui.cpp:2056-2061`), and only then composes the
`deferred: true` reply — a timeout returns an error, never `deferred: true`. So in Oracle's main
path the reset is **complete before the reply**, and its `true` reports *which thread applied the
reset*, not *when it landed*. The key is on the wire with no definition, and the one server
emitting it answers a question no client could rely on.

**This repo's own books flagged the gap.** `docs/2026-08-15-mcp-as-aether-client-validation.md:144-145`:
*"**`reset` is the conspicuous absence** — the most basic control op on the machine, missing from a
25-method control surface."* And the player has had reset the whole time — Tab (with F1 as hidden
alias), `crates/oracle-frontend/src/commands.rs:102-108`, handled at
`crates/oracle-frontend/src/main.rs:1369` (`sys.reset()`), which under D15's parity discipline is a live
gap: a GUI surface with no bus method behind it.

### The proposed prose (post-ruling authoritative text — the row at `:783` stays as-is)

In the run-control table's blockquote region (after the run-control state rule, before the checkpoints
group), add *(amended per ruling R1 — the `deferred` definition rewritten: "queued for the next
frame boundary" was ambiguous, since a paused machine advances no emulated frames; per R2 — the
run-state pin added; per R3 — the "checkpoint methods' reason" citation replaced with the reason
itself, which a contract reader can find; and per adopted recommendation (b) — the pre-reset stamp
note)*:

```markdown
> **`emulator/reset`** drives the machine's `/RESET` sequence against the current cartridge.
> Deliberately **not** subject to the state rule above, and a server MUST NOT refuse it with
> `-32005` on a free-running machine: it advances nothing and replaces state wholesale between
> frames, so it cannot fight the free-run loop for the machine, and gating it would force the
> pause-call-resume dance §5 forbids resolving implicitly. `deferred` reports *when* the reset
> landed relative to this reply — `false`: it was applied before this reply was composed, and
> every subsequent read on any connection sees the post-reset machine; `true`: the server accepted
> it and handed it to the thread that owns the machine without waiting for completion. A deferred
> reset MUST be applied within a bounded time regardless of run state — a server that cannot
> bound it answers `-32010` instead of `true` — and a client that needs it visible polls `status`
> until the stamp's `mclk` has restarted. A server that hands the reset off and then waits for
> completion before replying answers `false`: the key reports when it landed, never which thread
> applied it. `reset` MUST NOT change the machine's run state: a paused machine is paused at the
> reset vector, a free-running machine keeps running from it — §5's ban on implicit mode changes,
> applied here. (The legacy socket's `run` param, which resumes by default, is deliberately not
> adopted: that composition is `reset` + `resume`.) The master clock restarts from 0, so §2.2
> stamps on later replies jump backwards — that is the reset, not a bug — and a `deferred: true`
> reply's own stamp is pre-reset. Battery SRAM contents survive (as on real hardware); loaded
> symbols survive (the image is unchanged — contrast `reload_rom`); checkpoints and watchpoints
> survive; held pads clear. Can time out (`-32010`).
```

### The demand evidence

- The Aeon gap list, Tier 1 item 2: *"scene preambles need a cold start"* — and each of the three
  committed scenes opens with `"reset": true`.
- The reference server implements it today (`ControlSocket.cpp:459-493`), the legacy MCP offers it as a
  tool (`oracle_mcp.py:134`), and the player binds it to Tab/F1 — three of the four surfaces exist,
  and the bus row is the one absent, which is D15 parity inverted.
- The 25-method-surface quote above, from this repo's own MCP-as-client validation.

### Why the row must *define* `deferred` — the conformance argument, spelled out

*(Rewritten per ruling R1. The original version claimed Oracle's threading "forces `true` in its
normal path because the reset drains on the GUI thread after the reply is composed" and that the
proposed definition was "the only definition under which both shipping behaviours are legal." Both
claims were wrong — the ruling's central factual correction — and they are quoted here so the
correction stays visible.)*

If the contract leaves `deferred` undefined, either (a) whichever server ships first defines it de
facto and that definition is retroactively imposed on the next, or (b) a client invents its own
reading — the *"third answer that must be kept equal to the other two by hand"* failure §6's count
note names. So the row must define it. The definition adopted is *when the reset landed relative to
this reply* — an observable client semantics (what a subsequent read sees), never a threading
report. Under it, our server's honest answer is `false` (the engine thread applies the reset before
composing the reply). **Oracle's shipping `deferred: true` is NOT truthful under this definition**:
its main path completes the reset before the reply is composed (`ControlSocket.cpp:479-486` waits on
the done flag that `main_gui.cpp:2056-2061` sets after `doFullReset`), so its `true` reports which
thread applied the reset — the mechanism report the definition deliberately excludes (*"never which
thread applied it"*). That is accepted rather than accommodated: Oracle is already non-conformant on
the stamp (D11), and the contract's stated posture is to *"accept that the C++ server is a legacy
peer that no longer claims conformance"* (`protocol.md:1436-1438`). The definition is chosen for
clients, not to legalize every shipping emission. The CR-8 (`droppedEvents`) lesson still applies,
sharpened: a key on the wire without a definition belongs in the contract before a third server has
to guess — and before the second server's different answer hardens into a de-facto spec.

### Open questions: one, registered — and pins 5-6, each with its reasoning

5. **`reset` is NOT run-state gated** — the reasoning first written in this repo's checkpoint block
   (`crates/oracle-aether/src/engine.rs:2017-2029`: *"Deliberately NOT `require_paused`"* because
   none of those methods *advances* the machine — *"they read or replace the machine wholesale, on
   the engine thread, between frames"*). A reset is the same shape: it advances nothing and replaces
   state wholesale between frames, so it cannot fight the free-run loop, and §5's ban on implicit
   mode changes means gating it would force a pause-call-resume dance the call never needed. *(Per
   ruling R3, the contract text states this reason in full rather than citing a "checkpoint
   precedent" — an implementation comment a contract reader cannot find.)* Result `deferred: bool`
   defined honestly as *when the reset landed relative to the reply*: `false` = applied before the
   reply was composed (our server, always); `true` = accepted and handed to the machine-owning
   thread without waiting for completion, bounded (`-32010` otherwise). Both values conformant.
   *(Amended per ruling R1 — the earlier "queued for the next frame boundary" spelling was ambiguous
   on a paused machine, and the accompanying Oracle-threading gloss was wrong.)*
6. **`reset` semantics on the wire**: master clock restarts at 0 (stamps jump backwards — stated in
   prose so a stamp-watching client does not file the jump as a bug); SRAM contents survive (as on real
   hardware — the player's own reset flushes the pending `.srm` first, `main.rs:1364-1368`); loaded
   symbols survive (the image is unchanged — unlike `reload_rom`, whose row reports `symbolsDropped`);
   checkpoints and watchpoints survive; held pads clear; run state preserved — a paused machine
   stays paused at the reset vector, a free-running one keeps running *(added per ruling R2: the
   legacy socket's `run` param resumes a paused machine by default, an implicit mode change
   deliberately not adopted — that composition is `reset` + `resume`)*; `rom_generation` bumps (the
   `restore` precedent, so a hosted player resyncs). Each of these is a question a second
   implementer would otherwise answer by reading our source, which is the definition of a contract
   gap (§11.1, second sitting).

Ruling recommendation (a) — a fuller held-pads rationale in the prose — is **declined** as a
wording change; the rationale the ruling supplies is recorded here instead: held pads clear because
a reset is a cold start for scene preambles — determinism demands it — and the debugger's injected
pad state is not the machine's.

**The one open question, registered (ruling recommendation c) — a pushed event for reset.** Should
a reset (a deferred one especially) emit a notification, as `reload_rom` emits `romReloaded`, so
stream consumers need not poll `status` for the restarted `mclk`? Registered here, deliberately not
designed or built in this slice.

## CR-23 — `emulator/memory_hash`: the genuinely new row, raised before it is built

### What exists today

**Nothing.** `grep -rn memory_hash /home/volence/sonic_hacks/empyrean/` returns no matches (run
2026-08-18). No §6 row, no schema fragment, no deferral entry. Unlike CR-21 and CR-22 — both of which
amend rows that exist — this is a new op, and §8's rule reaches it directly: *"invent new ops not in
this spec"* is the first item on the must-not list (`protocol.md:1440`), so the row must exist before
the handler does. Hence this CR.

**The de-facto spec is the legacy MCP row**, `oracle/linux-port/mcp/oracle_mcp.py:239-254`, backed by a
socket op landed 2026-08-01 (`1c54004`, *"memory_hash op — parametric bus-memory content hash"*). Its
declared behaviour, quoted from the tool description: fnv1a64 *"(same family as state_hash)"* + crc32
*"(zlib/`crc32`-compatible, so a cart-window hash matches CRC32 over the ROM-file slice)"*; *"no
4096-byte cap"* with `len` max 4194304; *"Auto-routes RAM ($FF0000-$FFFFFF) vs cart ROM (<$400000)
exactly like read_memory"*; and *"A range that runs past the target device's last byte is rejected,
never wrapped or clamped."* The proposal below is that shape, ported to this contract's conventions
(D9 hex spellings, `limits.*` advertisement, `-32004`).

**CR-20 already anticipated this method and deliberately left it out.** Its ruling on question 3
(`docs/2026-08-16-cr20-unified-read.md`): *"**`memory_hash` is struck from this CR** — digest-shaped,
with its own obligations (the algorithm must be pinned as `state_hash`'s is, since cross-server
comparability is its whole point)."* This CR is the discharge of that obligation: CRC-32 pinned by
naming IEEE/zlib (polynomial, init, reflection and final xor all fixed), and FNV-1a-64 pinned by its
parameters — offset basis `0xCBF29CE484222325`, prime `0x100000001B3`, folded over the range's bytes
in ascending address order *(added per ruling R2: the family name alone left two servers free to
both say "FNV-1a 64" and never match; the constants match `oracle-core/src/state_hash.rs:9-11`
exactly)*. Per the same ruling's reservation it does **not** take the `space` vocabulary, because it
is not adopted with multi-space reach: it serves the two bus regions named below and nothing else.

### The proposed row and prose (post-ruling authoritative text)

In the memory table, directly under `emulator/read`:

```markdown

```

### The demand evidence

- The Aeon gap list, Tier 1 item 3: *"region hashing for gates. The FNV code exists in `state_hash`."*
  The Aeon side's `ab_runner` gates compare memory regions between runs; a hash answers that without a
  payload where `read` would need `len/4096` round-trips.
- The legacy socket op + MCP tool shipped 2026-08-01 and the MCP validation pass filed it under
  *"backed by shipped core capability, exposable"* (quoted in CR-20's "What the collapse actually
  buys"). The capability exists; only the contract row is missing.
- The CRC-32 choice has an external consumer property: a cartridge-window hash equals `crc32` over the
  same slice of the ROM *file*, so an Aeon-side gate can precompute its expectation from the `.bin`
  without a running emulator.

### The `frame_hash` distinction, explicitly — because a CR that ignores a standing deferral invites the momentum-refund failure

§9 defers *"**Scenario ops** (`scenario_load/advance/seek`) and **`frame_hash`** — the replay &
regression primitives (later)"* (`protocol.md:1457-1458`), and §9.1 re-affirms it after lifting the
save-state deferral: *"What is **not** lifted: `scenario_load/advance/seek` and `frame_hash` stay
deferred"* (`protocol.md:1488`). **CR-23 does not touch that deferral, and is not a partial lift of
it.** `frame_hash` is a *picture* hash — a fingerprint of rendered output, whose live spelling is
already `state_hash includeFramebuffer` (`protocol.md:1152`) — and it stays deferred. `memory_hash` is
a *memory* hash, filling the opposite gap: `state_hash`'s five fingerprints (`vram`, `cram`, `vsram`,
`regs`, `combined`) cover VDP state only, and nothing on this bus hashes 68000 memory. The two methods
share a suffix and nothing else. This paragraph exists because the keep-dead register's caution is
*"do not let momentum re-fund these"* — an amendment that added a hash method without saying which
deferral it does *not* lift would be exactly the momentum-refund a later reader could cite.

### Open questions: none — pins 7-9, each with its reasoning

7. **`memory_hash` is a pure read** (not gated, answers free-running — like `read`, unlike
   `write_memory`): it advances nothing and mutates nothing, so §5's worked `-32005` examples give no
   ground for refusing it, and the checkpoint block's reasoning against uncontracted bounds applies.
   Params `addr`|`symbol` + **required** `len` (1..=`limits.maxHashLen` = 4194304 — the legacy op's

   contract does not contain (amended)*.
8. **`memory_hash` ≠ the deferred `frame_hash`** (§9/§9.1): that is a picture hash and
   `state_hash includeFramebuffer` already serves it; `memory_hash` fills the gap `state_hash` leaves

9. **CRC-32 lives in `oracle-aether`** (`src/crc32.rs`, const-table, dep-free), NOT in `oracle-core`'s
