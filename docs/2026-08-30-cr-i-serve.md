`e7e94fa6a09b870ef1736804e4ee02927404479b`. **Date:** 2026-08-30.

This lane filed CR-I (`docs/proposed/2026-08-30-cr-i-symbolspath.md`, oracle `5808d8c`); the hub adopted

## 1. The trap this parcel was built around, and what actually witnesses the change

`main` was red on arrival: `crates/oracle-aether/tests/schema_conformance.rs` asserts the vendored schema
is byte-identical to upstream, and the contract had moved.

**The whole schema delta is three `description` edits.** Enumerated leaf by leaf, by walking both
documents to their scalars and comparing every path — **total leaf differences: 3**:

```
/methods/emulator/status/result/properties/symbolsPath/description
/methods/emulator/load_symbols/result/properties/path/description
/methods/emulator/screenshot/result/properties/path/description
```

And the complementary check that rules out a shape change hiding in the prose: with **every**
`description` stripped recursively from both documents, the two parse to the *same value*. No `type`,
`required`, `enum`, `$ref`, `additionalProperties` or `unevaluatedProperties` moved anywhere.

JSON Schema `description` is an annotation with **no validation force**. So the moment the new bytes
landed, the byte-identity gate went green and every conformance vector still passed — against a server
that was still putting `fixtures/aeon/s4.lst` on the wire. **The re-vendor's green witnesses nothing
about the behaviour it describes.** This was verified, not assumed: the full aether suite was green
against the old server *and* the new schema is byte-identical to upstream, and neither fact touches
`symbolsPath`.

What witnesses it is `crates/oracle-aether/tests/symbols_path.rs` — behavioural, red-first, asserting the
actual spellings. Section 4 is its evidence. The same warning is now the first box in
`crates/oracle-aether/tests/contract/PROVENANCE.md`, so a later reader does not have to rediscover that
the gate and the subject are disjoint.

### The no-fallback design is preserved, and so is its reason

`absolutise` is still `canonicalize`-with-pass-through. `symbolsPath` got **the same helper and the same
SHOULD as `romPath`, not a stricter one** — the ruling's words, and the CR's argument: a hosted embedder
may name its image `"testrom"` with no file behind it, and prefixing a working directory would
manufacture an authoritative-looking path that resolves to nothing. §6 is a SHOULD so that "I cannot
honestly say" stays available. `a_symbols_label_that_names_no_file_is_passed_through_untouched` pins that
half, and §4 shows it is not vacuous.

## 3. The checkpoint/restore finding

**Asked for explicitly, so here is what was found rather than what was assumed.**

`symbols_path` is carried through `Checkpoint` and put back by `restore`. Three findings:

1. **A checkpoint cannot predate this change.** `Checkpoint` is an in-memory `Vec` field on `Engine`; it
   is never serialized to disk. Grepped for a write/serialize path and found none. So there is no such
   thing as a slot carrying a relative spelling from an older binary — the concern the parcel raised is
   real in shape but empty in fact for this server, and worth recording as *checked* rather than
   *dismissed*.
2. **A restore cannot de-absolutise, because every store is already resolved.** Both `rom_path` and
   `symbols_path` enter a slot from `self.*`, which every route now sets through `set_symbols` /
   `set_rom_path` / `reload_rom` — all of which absolutise. `restore` puts the value back raw and that is
   correct.
3. **Re-absolutising inside `restore` would be actively wrong**, and this is the reason it was *not*
   done for symmetry's sake: for the pass-through case, a label with no file behind it could acquire a
   manufactured path if a file of that name appeared between the capture and the restore — a restore
   would then change what it reports about a machine it did not change. A `debug_assert` of the same
   invariant was considered and rejected for the identical reason: it would fire spuriously in exactly
   that window.

Finding 2 is an invariant about functions far apart in one file, so it is asserted rather than
remembered: `a_checkpoint_restore_does_not_de_absolutise_the_symbols_path` loads a listing by a relative
path, checkpoints, runs, restores, and requires `status.symbolsPath` to still be the resolved spelling.
It was **red before the change** (§4).

### M1 — `load_symbols`'s reply moves with `status.symbolsPath`

`load_symbols_reply_path_and_a_following_status_agree_exactly`. The real content of M1 is the *exactly*:
the test asserts the reply `path` is absolute, names the file, **and is the byte-identical string** the
next `status` returns. Two paths that merely resolve to one file would not do — a client comparing them
has only the strings. Red-first above.

### M2 — `screenshot.path` is absolute even for a caller-supplied relative path

`screenshot_reports_an_absolute_path_when_the_caller_supplied_a_relative_one`. The caller passes a
genuinely relative spelling (built by walking up out of the process's own cwd, never a `/home/…`
literal), and the reply must be absolute *and* name a file that exists. Red-first above — before the
change the server echoed the relative spelling straight back.

### M3 — refusals quote the caller's own spelling

Three tests, one per refusal site: `load_symbols`, `reload_rom`, `screenshot`.

**M3 is a preservation MUST, so red-first means something different for it**: these tests pass both
before and after, which on its own proves nothing. The evidence is an **anti-vacuity probe** — the three
`error.data.path` sites were deliberately mutated to absolutise, and the tests must fire:

| refusal site | first draft | after sharpening |
|---|---|---|
| `load_symbols` | **FAILED** under the probe | FAILED |
| `reload_rom` | **FAILED** under the probe | FAILED |
| `screenshot` | **passed** — vacuous | **FAILED** |

**The probe caught one of my own tests being blunt, which is the point of running it.** The screenshot
refusal test first used `no-such-directory-here/shot.png`. That path does not resolve, so `absolutise`
passes it through and the assertion held even with the error site mutated — a guard that would not have
stopped the "tidy" it exists to stop. Every M3 case now uses an input that **resolves but fails**: an
existing file whose *parse* fails (`load_symbols`), and a directory, which resolves but cannot be read as
a ROM or written as a PNG (`reload_rom`, `screenshot`). The mutation was reverted; the sharpened tests are
what is committed.

### The pass-through guard

`a_symbols_label_that_names_no_file_is_passed_through_untouched` passes before and after too, for the
same structural reason, so it got its own probe: `absolutise`'s `Err` branch was mutated to join the cwd.
Run **on top of the implementation** it FAILED with
`/…/crates/oracle-aether/not-a-listing-just-a-label` against `not-a-listing-just-a-label`.

**One process note worth carrying.** The first attempt at this probe was run with `engine.rs` at HEAD and
reported green — which looked like the test was vacuous but actually meant the probe had no path to
reach: at HEAD the symbols route never calls `absolutise` at all, so mutating the helper changed nothing
downstream. A probe run against the wrong baseline answers a question nobody asked. Re-run on top of the
implementation, it fired.

## 7. The smoke tool: the human-legible proof

`tools/aether_smoke.py` is a consumer in another language and another process reaching a running binary,
which is the one thing `cargo test` structurally cannot be. Server spawned by this seat as an ordinary
local binary on the frozen fixtures, launched with a **relative** `--symbols`, no emulator MCP tool
involved:

```
./target/release/oracle-aether fixtures/aeon/s4.bin \
    --socket /tmp/ae-cri-{before,after}.sock --symbols fixtures/aeon/s4.lst
python3 tools/aether_smoke.py /tmp/ae-cri-{before,after}.sock
```

**BEFORE** (`engine.rs` stashed to `5808d8c`, release rebuilt):

```
       romPath    /…/agent-ae37d92ef82e3325e/fixtures/aeon/s4.bin
       symbolsPath fixtures/aeon/s4.lst
SMOKE FAILURES: none
```

**AFTER**:

```
       romPath    /…/agent-ae37d92ef82e3325e/fixtures/aeon/s4.bin
       symbolsPath /…/agent-ae37d92ef82e3325e/fixtures/aeon/s4.lst
SMOKE FAILURES: none
```

Both paths absolute, from one command line, where before only the first was. Both runs pass every other
check identically — the change moved the spelling and nothing else.

**The smoke tool's own comment is retired in the same commit.** It read *"the server reports `romPath`
absolute but `symbolsPath` as it resolved it … so run the script from where the server was launched."*
That is the defect, written down inside the tool whose output revealed it, and it is now false. The
replacement says so and is explicit that this script is **not** the gate for the rule — a relative string
would still open here, since this process's cwd would resolve it. `tests/symbols_path.rs` is the gate.

*(An unrelated first BEFORE attempt showed `FAIL free-run is paced near 60Hz 376` — that was my own
`--no-pace` flag on the launch line, not a defect. Both runs above are paced, and both are clean.)*

## 8. Open / TAGGED / BLOCKED

**Nothing BLOCKED.** No emulator MCP tool was used at any point.

**TAGGED for foreground follow-up — none required.** The usual reason to tag is a claim needing live
runtime confirmation, and this one got it: the smoke runs above *are* a live binary, spawned locally
rather than through an MCP surface.

**Open, and deliberately not done here:**

* **The `romReloaded` event's `path` is in §11.30's enumeration and is already compliant** — `reload_rom`
  absolutises once, before both the event and the reply are built from the same `path` binding, so the
  event cannot disagree with the reply. It is covered by construction rather than by an assertion. A
  test would be cheap; it is not added because the two values are literally the same variable, and a test
  that a variable equals itself is the kind of green that this document's §1 warns about.
* **The MCP surface** (`emulator_status`, `emulator_load_symbols`, `emulator_screenshot`) relays these
  fields through unchanged, so it inherits the fix with no edit. Not re-verified live here, for the
  standing no-emulator-MCP reason.
