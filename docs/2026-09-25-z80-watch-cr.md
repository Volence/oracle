## What's going on, in plain words

The Mega Drive has two processors: the main one (the 68000) and a small sound processor (the Z80). Oracle's
"watch this address" tool only sees the main processor. When the sound processor reads music data or its own
memory, the watch reports nothing, so a zero can mean "not touched" or "the tool can't see". There is one exception,
and it matters: when the sound processor writes to the sound chip, the watch does see it. aeon already relies on
this to record every note the sound driver sends to the chip. But the watch labels those writes badly: they look
like writes by the main processor to the cartridge, stamped with the main processor's position in the code. My
recommendation is a small fix to that one working case: label those writes as the sound processor's, at the
sound chip's real address, with the sound processor's own code position. A person debugging sound would then get a
correctly labelled log of what the driver sent to the chip, and could tell it apart from the main processor's own
writes. Watching everything the sound processor touches is fully designed below, but it waits until someone
actually needs it. Nobody does today.

## 1. The premise, re-derived at HEAD `fb6ca8a`

The booking (`docs/OVERSEER-REFERENCE.md` l.1568-1582, registered 2026-09-13 from aeon at `e272ac7`) says a bus watch
never sees the Z80 read cartridge ROM through its `$8000` window, and that more widely the only sink call in
`crates/oracle-core/src/z80/bus.rs` is the FM/PSG write tap. **Verdict: TRUE at HEAD, and the booking understates the
one thing the Z80 does deliver.** The tap's hits reach the Aether wire today with a false address, a false function
code meaning and a false `pc`, and a live aeon tool reads them (§2).

### 1.1 What reaches a sink (measured by reading the code at HEAD; re-run the commands)

    git -C <worktree> grep -n -E 'self\.sink\.on_' HEAD -- crates/oracle-core/src/z80/bus.rs
    -> HEAD:crates/oracle-core/src/z80/bus.rs:241:  self.sink.on_event_at(      (the one call)

That call sits in `Z80Io::write`'s `0x4000..=0x4003 | 0x7F11` arm (`bus.rs:240-254`). It emits
`BusEvent { op: Write, fc: 0, addr: <raw Z80 address>, size: Byte }` at `self.now_mclk`, which is the Z80's frontier
at the **start of the instruction** (`bus.rs:110-114`, `system.rs:1939`). So:

| Z80 access | Reaches a sink? | Where (HEAD) |
|---|---|---|
| Opcode fetch (M1), operand fetch | **no** | `z80/mod.rs:486-499` (`next_opcode`/`next_byte` call `bus.read`) → `bus.rs:194` (no sink call) |
| Data read of its own RAM (`$0000-$3FFF`) | **no** | `bus.rs:197` |
| Data write of its own RAM | **no** | `bus.rs:224` |
| Read through the `$8000` bank window (ROM / Z80 RAM alias / work RAM) | **no** | `bus.rs:208-211` → `read_window` `:159` |
| Write through the window (work RAM / Z80 RAM alias) | **no** | `bus.rs:230-233` → `write_window` `:183` |
| Bank-register write (`$6000`) | **no** | `bus.rs:228` |
| VDP mirror read (`$7F00-$7FFF`), incl. the side-effecting status read | **no** | `bus.rs:206` |
| FM status read (`$4000-$4003`) | **no** | `bus.rs:201` |
| Interrupt acknowledge; IM 2 vector read; the push of PC | **no** (push and vector go through `bus.write`/`bus.read`, undelivered) | `z80/mod.rs:642-667` |
| **FM write (`$4000-$4003`), PSG write (`$7F11`)** | **yes**, as a `BusEvent` at the raw Z80 address, `fc 0` | `bus.rs:240-254` |

No Z80 access hook exists anywhere in the tree (measured, `ABSENCE` 1 in the detectors block):
`git -C <worktree> grep -c -E 'wants_z80_accesses|on_z80_access|Z80Access' HEAD -- crates` returns nothing.

**The cheap half is landed and is invisible on the wire.** `Watchpoints::caveats()` carries both caveats
(`crates/oracle-core/src/watchpoints.rs:868-906`), and the module header is now true (`:28-49`). But the Aether server

Aether client, which is how aeon reads watches, is told nothing. `crates/oracle-aether/tests/watchpoints.rs:421-425`
says so in a comment. **The contract is the only place a wire client can learn this**, and today it says nothing
(§1.3).

### 1.3 What the contract says about it (read at `93740f63`)

Nothing says Z80 accesses are unwatched, and four texts say something false about the one kind that is delivered:

1. **§2.4, l.638-646 (§11.51, landed today):** *"Every 68000 address field on this bus names what the CPU drives on
   its 24 address lines"*, naming `watchpoint_hits.hits[].addr`. A Z80 FM write drives nothing on the 68000's
   address lines, yet it is reported at `$004000`, a cartridge address.
2. **Schema `fc` (l.4438-4442):** *"5/6 = CPU supervisor data/program, 0 = a non-CPU master"*. The Z80 is a CPU.
3. **Schema `via` (l.4444-4450):** *"'bus' = a 68000 bus access"*. These hits carry `via: "bus"`.
4. **Schema `pc` (l.4451-4454):** *"PC of the instruction that drove the access"*. It is the 68000 instruction whose
   step the Z80 caught up after.

And the `bus` space description (schema l.3926) reads *"'bus' is the 68000 address space (work RAM, ROM, Z80 RAM,
I/O, VDP ports)"* while §6's `seen` paragraph (l.1391-1397) says `seen` *"counts every access offered to the
recorder"*: nothing in either tells a client that the Z80's traffic to those places is never offered. §9
(l.2702) defers *"Deeper Z80 — disassembly, Z80 breakpoints (Phase 2)"*; nothing there mentions watches.
(`ABSENCE` 3 in the detectors block controls the "nothing says" claim.)

**Where the prior design (`docs/2026-09-13-z80-timing-currency-design.md`) is wrong or out of date at HEAD**, each
checked here:

- **§3's `Z80Access` kinds `Fetch | Read | Write | Ack` cannot come from §4's `Watched` wrapper as described.**
  `Watched` "implements `Z80Io` by forwarding", but `Z80Io` (`z80/mod.rs:39-51`) has only `read`/`write`/`input`/
  `output`. An M1 opcode fetch, an operand fetch and a data read are all `bus.read` (`z80/mod.rs:486-499`), and on
  this machine an IM 1 acknowledge makes **no** bus call at all (`z80/mod.rs:658-664`: the floating bus is modelled as
  a constant). So a forwarding wrapper sees `Read`/`Write` only. `Fetch` needs a defaulted `Z80Io` method called
  from `next_opcode`, and `Ack` needs an explicit call in `accept_interrupt`. **(reasoned from the code; measured
  that no such method exists: `ABSENCE` 4.)** The "candidate (d) for free" claim does not hold.
- **§0.7's "the hit ring stops being clock-ordered" is already true of today's tap, and the contract never promised
  otherwise.** The tap rides the same catch-up. `catch_up_z80` runs after the 68000 step and the clock advance
  (`system.rs:1531-1540`), so a Z80 hit's `mclk` lies in the same interval as the 68000 step's accesses and may be
  earlier than a 68000 hit recorded just before it **(reasoned)**. The scratch run saw no backwards step in 67 hits
  **(measured, but a 4-line window with two Z80 hits cannot refute it)**. The in-tree invariant
  (`tests/watchpoints.rs:272`) holds because its fixture holds the Z80 in reset. The contract promises `seq` order
  only (grep for `monoton` in `protocol.md` finds no hit-ordering claim). The draft (§5.1) says so explicitly.
- **§5's claim that the cheap half tells the reader** holds for in-process readers only; see §1.1.
- **The `EI` shadow is landed** (`z80/mod.rs:604-617`), so §7's parcel 3 is done. It does not affect this CR.

## 2. Who needs it (the real consumer)

The hub's rule: the contract grows against a real consumer, not a foreseeable one (§11.51 "Deferred, not rejected … Ground",
l.6192-6197; §11.50 "RIDER R1 IS DROPPED", l.6112-6118). I looked for consumers in every suite repo that calls the watch
methods, at a named revision.

**2.1 A live consumer of the one delivered kind: YES, aeon.** `aeon 85615e8:tools/song_load_mid_drum_witness.py`
(landed `06ca227b`, 2026-09-12; amended `d876177e`) arms `watchpoint_add {space:"bus", addr:"0x4000", len:4,
write:true}` (l.217-223) as **its only YM2612 write log**, because oracle serves `capabilities.vgm: false`
(l.16-26). It reconstructs (register, value) from the raw address (`part = 0 if addr in (YM_A0, YM_A1) else 1`,
l.244) and orders by `mclk`/`seq`. It does not read `fc`, `via`, `pc` or `symbol`. It has a **poison control**: leg L0
requires `seen > 0` and `matched > 0` and a `--poison` run that aims the watch where nothing writes must go loud
(l.23-26, l.51-52). The same instrument is documented as "the instrument the booking asked for" in
`docs/superpowers/notes/2026-09-12-owed-runtime-witnesses-c.md:70-74`. **So the delivered kind is load-bearing today**,
and it works by a behaviour the contract does not describe and §11.51's sentence contradicts. A server that
"fixed" the collision by dropping the tap from watches would silently remove aeon's only YM instrument (loudly, in
fact, thanks to L0; but nothing in the contract would say the server was wrong).

**2.2 A live consumer of the undelivered kinds (reads, fetches, RAM, the window): NO.** The one ask was aeon's F3
runtime tag, 2026-09-13 (`aeon 85615e8:docs/superpowers/notes/2026-09-13-f3-runtime-tag.md:47-54`): a read watch on
ROM bytes the Z80 reads got 0 hits. **aeon answered the question another way** (an A/B of the Z80 driver's own
channel state, same note §1) and closed the row (`docs/DEFERRED_WORK.md:8769-8778`). aeon's standing rule since is
"never read a zero Z80 count from a watch as a result" (`docs/superpowers/2026-09-13-aeon-overseer-handoff-14.md:99-101`).
No open row, decision, lens finding, queue entry or roadmap line in aeon asks for it (measured, `ABSENCE` 5), and no
aeon commit since 2026-09-14 mentioning the Z80 is about watches (`git log --since=2026-09-14 -i --grep=z80`: 15
commits, all LS-13b bus-hold, census or S2-room work, read by title). **The push for this parcel is the hub's, not a
client's:** empyrean `93740f63:docs/OVERSEER-LOG.md:15189` ("draft the F-Z80-ACCESSES-UNWATCHED contract CR now, since
the hub rules CRs, with no code until ruled").

**2.3 Other clients.** seraph (the DAW, `origin/HEAD` `f8a7a3b`) calls no watch method (`git grep -c -E
'watchpoint_(add|hits)'` → nothing). aurora (`40a9c3f`) mentions them only in two docs, no code. Oracle's own player
shows `caveats()` in its watch panel, so the in-process surface already tells the truth; the MCP surface is the
legacy shim and is out of scope.

**Consumer verdict.** There is a real, current consumer, but **of the tap, not of the full stream**. It needs the tap
to keep working and to be described truthfully. Nobody needs Z80 reads, fetches or RAM traffic on the watch surface
today. The full design is therefore deferred text with a named trigger (§4, §5.5), and the recommended change is
scoped to the tap.

## 3. Options

Common facts every option is priced against:

- **Hot-path numbers are BOOKED, not re-measured here.** Design §4, spike `21622cd` at base `5ee7d6a`: a defaulted
  `on_z80_access` hook plus a `Watched` wrapper and one branch in `catch_up_z80` measured **no detectable slowdown on
  the null path** (the A/B's resolution was about ±4%; the hook build was ~3% faster, which the design attributes to
  layout), and an **armed counting sink cost about 6.6% of a frame** at aeon's load of **14,927 Z80 accesses per
  frame** (17,945,764 over 1200 frames). Release, five interleaved rounds of 5 × 600 frames, load 2.7-3.1. Re-measuring
  means rebuilding that spike on HEAD, which is an implementation parcel's job, not a docs parcel's; the implementing
  parcel owes the re-run (§6, T9).
- **Re-vendoring.** Any byte change to `contract/schema/bus-protocol.schema.json` (including a `description`) forces
  oracle to re-vendor, because `crates/oracle-aether/tests/contract/` pins the blob (`PROVENANCE.md` l.7-26). A
  prose-only change to `protocol.md` does not.
- **Every Z80 access has a 68000-map coordinate** (reasoned from `z80/bus.rs` and `crates/oracle-core/src/bus.rs:936`):
  a Z80 address `a < $8000` is the target the 68000 reaches at `$A00000 | a` (Z80 RAM `$A00000-$A03FFF`, YM
  `$A04000-$A04003`, bank latch `$A06000`, VDP/PSG mirror `$A07F00-$A07FFF`); a window access `a ≥ $8000` drives
  `(bank << 15) | (a & $7FFF)` onto the 68000 bus through the arbiter (`z80/bus.rs:151-153`, `window_addr`).

### (A) Declare only, and describe today's tap as it is

A normative paragraph in §6: a bus watch observes the 68000's accesses; of the Z80's, **only** its YM and PSG
register writes are offered, **at their Z80-side addresses** `$004000-$004003` / `$007F11`, with `fc 0`, a `pc` that
is **not** the driving instruction and a `symbol` that means nothing; every other Z80 access is not offered, so a zero
on a Z80-reachable address says nothing about the Z80. It must also say that a 68000 write to `$A07F11` produces a
second hit at `$007F11`, `fc 0` (the F-TRACE-MASTER re-emit, `crates/oracle-core/src/bus.rs:1261-1273`).

- **Client gains:** the truth, in the one place a wire client can read it. aeon changes nothing.
- **Hot path:** none. **Server work:** none.
- **Schema/vendoring:** the `fc` ("0 = a non-CPU master"), `via` ("'bus' = a 68000 bus access") and `pc`
  descriptions become false unless reworded, so an honest (A) rewords three descriptions and re-vendors; §11.51's first
  sentence needs an exception. **Leaves added: none.**
- **What it costs in meaning:** it **ratifies a collision** (`$004000` is both "cartridge ROM" and "the Z80's YM
  address port"; a write watch over low ROM matches the sound driver), and it makes `pc` mean "the driving
  instruction, except when it doesn't", with the exception inferred from `fc 0` plus the address. It also fixes the
  raw address convention in contract text, which the full stream (D) would have to move again.

### (B) Stop offering the tap to watches, and declare that no Z80 access is offered

Watches ignore the tap's `BusEvent`s (the VGM logger keeps them, byte-identical). A normative sentence: *no Z80
access is offered to a watch; a zero on a Z80-reachable address says nothing about the Z80.*

- **Client gains:** the simplest true statement. `fc 0` and `via "bus"` become true again for every bus hit.
- **Hot path:** none. **Schema/vendoring:** **none**. This is the only option that is prose-only *and* true.
- **Cost:** it **removes aeon's only YM instrument** (§2.1). aeon's L0 control would catch it loudly, but aeon would
  have nothing to switch to while `capabilities.vgm` is `false`. **Rejected as a stand-alone move**: it breaks the
  one live consumer to tidy a contract. It is correct *after* a replacement exists (see BA1 below).

### (C) Truthful tap: the Z80's YM/PSG writes on existing bus watches, at their 68000-map address, `via: "z80"`

The same set of accesses as today, with every field true:

- `addr` = the 68000-map address of the register the Z80 wrote: `$A04000-$A04003` for the YM, `$A07F11` for the PSG.
  This is the address a 68000 uses for the same register, so one watch on `$A04000-$A04003` now sees **both**
  masters' YM writes, told apart by `via`.
- `via` = **`"z80"`** (a new enum member). `fc` **absent** (a Z80 has no 68000 function code). `pc` = the **Z80's** PC
  at the start of the writing instruction. `symbol`/`symbolDisp` **absent** (they resolve against the 68000 listing).
- `mclk` = the Z80's clock at the start of that instruction: **instruction-granular**, like a VDP hit's.
- A Z80 hit **never counts toward `stopAfter`** (it records and counts; it never ends a run). Reason: a watch stop is
  declared `afterCommit`, which promises that *the 68000 instruction immediately before `pc`* caused it. A
  Z80-triggered stop cannot keep that promise, and `stopPrecision`'s binding rule (§2.1, l.498-501) would force the
  server to declare the weakest precision it may emit, degrading **every** watch stop to `approximate` for the sake of
  a case no client asked for. Halting on a Z80 access is a Z80 breakpoint in all but name, which §9 already defers
  (l.2702).
- The 68000's own `$A07F11` write stays one hit (its own `fc 5` event at `$A07F11`); the Z80-shaped `$007F11`
  re-emit no longer reaches watches. The `F-TRACE-MASTER` census caveat (`watchpoints.rs:848-859`) and caveat 2
  (`:889-906`) retire.

- **Client gains:** a correctly labelled YM/PSG write log, with the Z80 PC of each write, on the address a client
  would naturally watch, and the 68000's writes to the same registers in the same stream. `censusKey: "via"` over
  `$A04000-$A04003` answers "which processor drives the YM" in one number. aeon: one constant moves
  (`YM_A0..A3` gain `$A00000`); its L0 control goes loud if it does not.
- **Hot path:** a sink call already sits in the tap arm (`z80/bus.rs:241`). The new hook is called from that arm
  only, a defaulted no-op for `S = ()`. **Nothing is added to the fetch, RAM or window paths.** (Reasoned: the null
  monomorph gains no code on any path the Z80 takes more than a few hundred times a frame. The tap's own rate is
  measured by aeon: 662 YM writes in 30 idle frames, and a DAC drum writes about 300 bytes a frame, per
  `song_load_mid_drum_witness.py:225`.)
- **Schema/vendoring:** `via` gains `"z80"`; the hits item's presence rule changes (`fc` iff `space` is `bus` **and**
  `via` is not `z80`; `symbol`/`symbolDisp` never with `via: "z80"`); `$defs/watchStamp` gains an optional `via`
  (`const "z80"`), because `watchpoint_list`'s `first`/`last` carry a `pc` that would otherwise be ambiguous; the
  census `key` description gains `3 = z80`; four descriptions reworded. **One re-vendor.**
- **What it does not do:** Z80 reads, fetches, RAM traffic and window accesses stay unoffered, and the normative
  paragraph says so.

### (D) The full stream on existing bus watches (the design's option B, parcel 5)

Every Z80 access, offered at its 68000-map coordinate, with (C)'s wire shape unchanged.

- **Client gains:** aeon's F3 question ("does the Z80 still read these ROM bytes?") becomes one watch; "who writes this
  driver variable", 68000 or Z80, becomes one watch over `$A0xxxx`. The `seen`/`matched` negative control starts
  covering the Z80.
- **Hot path:** the booked figures above: null path unchanged within ±4%, armed +6.6% of a frame at aeon's load.
  `seen` grows by about 15 k per frame for any armed bus watch (booked, design §3).
- **Schema/vendoring:** **none beyond (C)** if (C) lands first; only a normative sentence changes (the offered set).
  An `op` for a fetch has no spelling today (`read`/`write`/`tas`; a 68000 fetch is a `read` with `fc 6`, and a Z80
  fetch has no `fc`). Either a fetch is a `read` (and "was this executed or read as data" is lost) or `op` gains
  `"fetch"`. **A decision for the day (D) is taken, not now.**
- **Implementation:** `Z80Io` needs a defaulted fetch method called from `next_opcode`, and an explicit acknowledge
  call in `accept_interrupt` (§1.3's correction to the design).

### (E) A separate `z80` watch space with Z80-side addresses

`watchpoint_add {space:"z80", addr:"0x1C00"}`, matching the Z80's own 16-bit addresses.

- **Client gains:** the driver author's spelling (`$1C00`, not `$A01C00`), and window accesses matched by Z80 address
  whatever the bank.
- **Costs:** (1) **§11.12's shared-enum rule** (l.1153-1156, l.3549-3553): `emulator/read` takes the watch enum
  *unchanged*, and `z80` was struck from `read` precisely because the watch enum refused it. A watch enum holding
  `z80` forces `read` to gain it too (duplicating `z80_read`'s bounds), or breaks the rule the other way. (2) *"Spaces
  never cross-trigger"* (schema l.3926): a `z80`-space watch on `$1C00` would not see the 68000 writing the same byte at
  `$A01C00`, which is the cross-master question (D) answers in one watch. (3) `old` would be required by the
  presence rule (non-`bus` space), which is fine for Z80 RAM and meaningless for a YM write. (4) It adds no reach: every
  Z80 access already has a 68000-map coordinate. **Rejected.** If a client ever wants the Z80 spelling, it is a
  client-side `$A00000 |` or a `symbol` resolved against a Z80 listing, and aeon's Z80 symbols reach no listing today
  (`owed-runtime-witnesses-c.md`, *"No Z80 symbols in the listing"*).

### (F) Only the bank-window accesses, at their 68000 address (the §11.51-shaped question)

Offer only the accesses that really drive the 68000 bus: Z80 reads and writes through `$8000-$FFFF`, at
`(bank << 15) | (a & $7FFF)`. Cartridge addresses among them are bank-blind in §11.51's sense (the cart mapper's bank
is not reported, like every other cart-space address).

- **Client gains:** exactly aeon's F3 case, and it satisfies §11.51's first sentence literally.
- **Hot path:** a sink call in `read_window`/`write_window` only (the window path, not fetches or RAM). Unmeasured;
  the design's 14,927 accesses per frame are mostly RAM fetches, so this should be far below (D)'s +6.6%
  **(reasoned, not measured)**.
- **Schema:** as (C). **Deferred with (D)**: it is the cheapest widening if the trigger is a ROM-reachability
  question, and (C)'s wire shape serves it unchanged.

### Better-approach pass (the options above are the floor)

- **BA1. aeon's real need is a YM write log, and the contract already catalogues one: `emulator/vgm_*`**
  (`protocol.md` l.1753-1755), unserved (`capabilities.vgm: false`, pinned by `schema_conformance.rs`'s
  `SCHEMATIZED_NOT_ADVERTISED`). `crates/oracle-core/src/vgm.rs` has the logger. Serving it needs **no CR**, and it is
  already demand-ordered on seraph's S1 (`docs/OVERSEER-REFERENCE.md` l.2297-2310). It is **not** a replacement for
  (C): VGM is file-based and sample-granular (a 44.1 kHz wait is about 1,218 mclk), with no `seq`, no hole check and no
  writer PC, and aeon's witness is built around a polled, `seq`-checked stream. **Recommendation:** tell aeon it is a
  second consumer of the VGM item, so the day VGM is served, (B) becomes available. Not a reason to delay (C).
- **BA2. A `master` key instead of a `via` member.** `master: "m68k"|"z80"` is more orthogonal (a Z80 write is not a
  *route*), but it is a new key on a closed object, needs its own presence rule, and a census over it needs
  `censusKey` to gain `master`. A `via` member reuses the existing census. And `via` is already documented as the
  attribution that replaces `fc` where `fc` cannot answer (schema l.4444-4450), which is exactly the Z80's case.
  **Chosen: `via`.** The wording defines `via: "z80"` as *the Z80 drove it*, so it is attribution, not a route.
- **BA3. Keep the raw Z80 addresses and add `via: "z80"`.** aeon changes nothing. But `addr` stays a non-68000 coordinate
  in the bus space (against §11.51), the ROM collision stays, and (D) would then have to choose between two address
  conventions for Z80 hits. **Rejected.**
- **BA4. Put the caveat on the wire instead** (a `caveat` on `watchpoint_hits` naming the Z80). The fragment already
  declares `caveat` (§6's watchpoint block: *"every one of these methods may emit one"*). **As a stop-gap it needs no
  CR.** But §2.4's advisory (l.625-634) says a permanent property belongs in the document, not in a caveat clients
  learn to ignore, and "the Z80 is not watched" is permanent until (D). **Not recommended in place of the normative
  paragraph.** A *conditional* caveat is worth booking for (D)'s absence period: emit it only when the watch covers a
  Z80-reachable range *and* the Z80 ran during the capture. That is the §2.4 shape (a measurement, not a slogan), and it
  needs no contract text beyond what §2.4 already says.
- **BA5. Order.** (C) first, (D)/(F) later, means the wire shape is settled once and later widening is behaviour plus
  one normative sentence. That is the §11.48 S1 lesson (the typed key ships once) applied here.

## 4. Recommendation

**Adopt (C), the truthful tap, now; defer (D) and (F) with a named trigger; reject (E); book BA1.**

(C) is recommended on the ground §11.51 itself gives for acting without new demand: *the false sentence is
different in kind*. Today the reference server emits, on a wire a live consumer reads (§2.1), hits whose `addr`,
`fc`, `via` and `pc` each contradict the contract's own text (§1.3). There are only two honest repairs. (A) rewrites
four texts to describe the quirk: it carries the ROM collision into the contract and makes `pc` mean something else
for some hits. (C) makes the hits true: it costs one `via` member and one presence-rule change, one re-vendor, a
tap-site-only server change, and one constant in aeon's tool. Both re-vendor, because (A) must reword the same
descriptions, so (C)'s extra cost over (A) is the server change and aeon's one-line move. It buys true fields, and a
shape the full stream reuses without a second wire change. (B) is the only prose-only true option, and it breaks the
live consumer. **Fallback, if the hub prefers the smallest text:** (A), with the three descriptions reworded as §5.4
lists, plus the same normative "not offered" paragraph. That paragraph is common to (A) and (C) and is the part a wire
client most needs.

**Trigger for (D)/(F), named so it is not re-derived:** a client asks a question about Z80 reads or writes of
68000-reachable memory that it cannot answer from the driver's own state. The precedent is aeon's F3 tag, which *was*
answerable another way, so it does not fire the trigger. **(F) first if the question is about ROM or work RAM through
the window; (D) if it is about the Z80's own RAM or fetches.** At that point the wire shape is (C)'s, the only
contract change is the offered-set sentence (§5.5), and the implementing parcel owes the hot-path re-measurement.

### 5.1 §6, a new paragraph in the watchpoint block, after *"`old` is present if and only if …"* (l.1419-1423)

> **The Z80 and the watch surface** *(added §11.NN)*. A `bus` watch observes the 68000's accesses. Of the Z80's
> accesses, a server offers a watch **exactly one kind: the Z80's writes to the YM2612 and SN76489 registers.** Its
> opcode fetches, its reads, its writes to its own RAM, its accesses through the `$8000` bank window and its VDP-mirror
> accesses are **not offered**. They do not match, and `seen` does not count them. **So a zero on an address the Z80 can
> reach says nothing about the Z80.** The 68000 alias of Z80 RAM (`$A00000–$A0FFFF`), cartridge ROM and work RAM
> are all such addresses. Five things are normative about the kind that is offered:
>
> - **`addr` is the register's address in the 68000's map**: `$A04000–$A04003` for the YM2612, `$A07F11` for the
>   PSG. That is the address a 68000 uses for the same register, so one watch sees both processors' writes to it.
>   A server MUST NOT report a Z80 access at its Z80-side address (`$4000`, `$7F11`), which in this space names
>   cartridge ROM.
> - **`via` is `"z80"`**, and it means *the Z80 drove this access*. `fc` is **absent**, because the Z80 has no 68000
>   function code. `pc` is the **Z80's** program counter at the start of the instruction that wrote. `symbol` and
>   `symbolDisp` are **absent**, because a symbol resolves against the 68000's listing (§4). Each of these is
>   enforced in the schema.
> - **`mclk` is the master clock at the start of the Z80 instruction that wrote**. Like a VDP-internal hit's, it is
>   instruction-granular.
> - **Hits stay in `seq` order, and `mclk` is not monotonic across processors.** The two CPUs run interleaved, so a
>   Z80 hit may carry an earlier `mclk` than a 68000 hit recorded before it. Within one processor, `mclk` never
>   decreases.
> - **A Z80 hit never counts toward `stopAfter`.** It is recorded, counted in `matched` and `seen`, and grouped by
>   `census`, but it never ends a run. A watch stop is `afterCommit` (§2.1): the 68000 instruction before `pc`
>   caused it, and a Z80 access cannot meet that promise. Halting on a Z80 access is a Z80 breakpoint, which §9 defers.
>
> `censusKey: "via"` groups a Z80 access under key `3`.

*Why this belongs in §6 and not in a caveat:* the property is permanent until the set is widened (§5.5), and §2.4's
advisory puts permanent properties in the document (l.625-634).

### 5.2 §2.4, *Addresses are bus addresses …* (l.638), the first sentence

> ~~Every 68000 address field on this bus names what the CPU drives on its 24 address lines.~~
> **Every 68000 address field on this bus names a location in the 68000's address map. For the 68000's own accesses,
> that is what it drives on its 24 address lines. For a Z80 access on the watch surface (`via: "z80"`, §6), it is the
> 68000-map address of the same target.** It is never an image offset.

The rest of the paragraph is unchanged. The bank-blind rule applies to a Z80 hit exactly as to a 68000 one. Under (C)
no offered Z80 access lands in cart space, so today the sentence is only forward-looking; under (D)/(F) a Z80 window
read of ROM is reported at `(bank << 15) | (a & $7FFF)` and is bank-blind in §11.51's sense.
