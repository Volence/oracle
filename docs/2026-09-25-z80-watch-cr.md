## What's going on, in plain words

The Mega Drive has two processors: the main one (the 68000) and a small sound processor (the Z80). Oracle's
"watch this address" tool only sees the main processor. When the sound processor reads music data or its own
memory, the watch reports nothing, so a zero can mean "not touched" or "the tool can't see". There is one exception,
and it matters: when the sound processor writes to the sound chip, the watch does see it. aeon already relies on
this to record every note the sound driver sends to the chip. But the watch labels those writes badly: they look
like writes by the main processor to the cartridge, stamped with the main processor's position in the code. My
recommendation is a small fix to that one working case: label those writes as the sound processor's, at the
sound chip's real address, with the sound processor's own code position. A person debugging sound would then get a
correctly labelled log of what the driver sent to the chip, and could tell it apart from the main processor's own
writes. Watching everything the sound processor touches is fully designed below, but it waits until someone
actually needs it. Nobody does today.

## 1. The premise, re-derived at HEAD `fb6ca8a`

The booking (`docs/OVERSEER-REFERENCE.md` l.1568-1582, registered 2026-09-13 from aeon at `e272ac7`) says a bus watch
never sees the Z80 read cartridge ROM through its `$8000` window, and that more widely the only sink call in
`crates/oracle-core/src/z80/bus.rs` is the FM/PSG write tap. **Verdict: TRUE at HEAD, and the booking understates the
one thing the Z80 does deliver.** The tap's hits reach the Aether wire today with a false address, a false function
code meaning and a false `pc`, and a live aeon tool reads them (§2).

### 1.1 What reaches a sink (measured by reading the code at HEAD; re-run the commands)

    git -C <worktree> grep -n -E 'self\.sink\.on_' HEAD -- crates/oracle-core/src/z80/bus.rs
    -> HEAD:crates/oracle-core/src/z80/bus.rs:241:  self.sink.on_event_at(      (the one call)

That call sits in `Z80Io::write`'s `0x4000..=0x4003 | 0x7F11` arm (`bus.rs:240-254`). It emits
`BusEvent { op: Write, fc: 0, addr: <raw Z80 address>, size: Byte }` at `self.now_mclk`, which is the Z80's frontier
at the **start of the instruction** (`bus.rs:110-114`, `system.rs:1939`). So:

| Z80 access | Reaches a sink? | Where (HEAD) |
|---|---|---|
| Opcode fetch (M1), operand fetch | **no** | `z80/mod.rs:486-499` (`next_opcode`/`next_byte` call `bus.read`) → `bus.rs:194` (no sink call) |
| Data read of its own RAM (`$0000-$3FFF`) | **no** | `bus.rs:197` |
| Data write of its own RAM | **no** | `bus.rs:224` |
| Read through the `$8000` bank window (ROM / Z80 RAM alias / work RAM) | **no** | `bus.rs:208-211` → `read_window` `:159` |
| Write through the window (work RAM / Z80 RAM alias) | **no** | `bus.rs:230-233` → `write_window` `:183` |
| Bank-register write (`$6000`) | **no** | `bus.rs:228` |
| VDP mirror read (`$7F00-$7FFF`), incl. the side-effecting status read | **no** | `bus.rs:206` |
| FM status read (`$4000-$4003`) | **no** | `bus.rs:201` |
| Interrupt acknowledge; IM 2 vector read; the push of PC | **no** (push and vector go through `bus.write`/`bus.read`, undelivered) | `z80/mod.rs:642-667` |
| **FM write (`$4000-$4003`), PSG write (`$7F11`)** | **yes**, as a `BusEvent` at the raw Z80 address, `fc 0` | `bus.rs:240-254` |

No Z80 access hook exists anywhere in the tree (measured, `ABSENCE` 1 in the detectors block):
`git -C <worktree> grep -c -E 'wants_z80_accesses|on_z80_access|Z80Access' HEAD -- crates` returns nothing.

**The cheap half is landed and is invisible on the wire.** `Watchpoints::caveats()` carries both caveats
(`crates/oracle-core/src/watchpoints.rs:868-906`), and the module header is now true (`:28-49`). But the Aether server
never calls `caveats()` (measured, `ABSENCE` 2: `git grep -c 'caveats\(\)' HEAD -- crates/oracle-aether/src` → 0; its
only readers are the player's watch panel `crates/oracle-player/src/stopping.rs:717`, two examples and a test). So an
Aether client, which is how aeon reads watches, is told nothing. `crates/oracle-aether/tests/watchpoints.rs:421-425`
says so in a comment. **The contract is the only place a wire client can learn this**, and today it says nothing
(§1.3).

### 1.2 What the wire carries for the one delivered kind (measured, in process)

A scratch test (never committed; the file was deleted before the first commit, and `git status --short` was empty
afterwards) released the Z80 on `testrom::build`, as `crates/oracle-core/tests/z80_timing_probes.rs::released` does,
with the program `LD A,($8000); LD ($1000),A; LD A,$2B; LD ($4000),A; LD A,$80; LD ($4001),A; HALT` (bank 0), and
armed five bus watches on one `Watchpoints` passed to `run_until_with_sink` for 4 lines. Release profile,
`cargo test -q --release -p oracle-core --test zz_scratch_z80_watch_probe -- --nocapture`:

    z80 stored 0x00, rom0 0x00          (positive control: $1000 was pre-set to !rom0 = 0xFF, so the Z80 did read ROM)
    seen 459
    rom:    0 hits    (read watch on $000000, the byte the Z80 just read through its window)
    fm:     2 hits    (write watch on $004000-$004003)
    zram:   0 hits    (write watch on $A01000, the 68k alias of the Z80 RAM byte it just wrote)
    zfetch: 0 hits    (read watch on $A00000-$A00010, the 68k alias of the bytes it fetched)
    ram:    65 hits   (write watch on $FF0000-$FFFFFF, the 68000's own stirring loop: the instrument is live)
    FM hit addr 0x004000 fc 0 val 0x2b pc 0x00020e mclk 1517 seq 2
    FM hit addr 0x004001 fc 0 val 0x80 pc 0x000212 mclk 1817 seq 5

So, at HEAD, **(measured)**: the window read, the Z80-RAM write and the fetches produce zero hits while `seen > 0`
(aeon's F3 measurement, in miniature); and each FM write produces a bus hit at **`$004000`, a cartridge-ROM
address**, with `fc 0` and **`pc` = a 68000 address** (`$00020E` and `$000212` are the test ROM's 68000 loop, not the Z80
program at `$0000`). The server serialises exactly those fields (`crates/oracle-aether/src/engine.rs:8768-8795`,
`watch_hit_json`: `addr`, `fc` for bus hits, `via` = `"bus"`, `pc`, and a `symbol` resolved against the **68000**
listing). That the Aether engine's watch sink rides the Z80 catch-up is **(reasoned)**: the run's sink is
`Fanout(… Observe(armed) …)` (`engine.rs:2756`, `:2945`), and `System::catch_up_z80` builds `Z80Bus` with that same
sink (`system.rs:1540`, `:1931-1941`). aeon measured it on the wire: `seen=852228 matched=662 dropped=0` over 30 idle
frames on a `$4000-$4003` watch (aeon `85615e8:docs/superpowers/notes/2026-09-12-owed-runtime-witnesses-c.md:71-74`).

### 1.3 What the contract says about it (read at `93740f63`)

Nothing says Z80 accesses are unwatched, and four texts say something false about the one kind that is delivered:

1. **§2.4, l.638-646 (§11.51, landed today):** *"Every 68000 address field on this bus names what the CPU drives on
   its 24 address lines"*, naming `watchpoint_hits.hits[].addr`. A Z80 FM write drives nothing on the 68000's
   address lines, yet it is reported at `$004000`, a cartridge address.
2. **Schema `fc` (l.4438-4442):** *"5/6 = CPU supervisor data/program, 0 = a non-CPU master"*. The Z80 is a CPU.
3. **Schema `via` (l.4444-4450):** *"'bus' = a 68000 bus access"*. These hits carry `via: "bus"`.
4. **Schema `pc` (l.4451-4454):** *"PC of the instruction that drove the access"*. It is the 68000 instruction whose
   step the Z80 caught up after.

And the `bus` space description (schema l.3926) reads *"'bus' is the 68000 address space (work RAM, ROM, Z80 RAM,
I/O, VDP ports)"* while §6's `seen` paragraph (l.1391-1397) says `seen` *"counts every access offered to the
recorder"*: nothing in either tells a client that the Z80's traffic to those places is never offered. §9
(l.2702) defers *"Deeper Z80 — disassembly, Z80 breakpoints (Phase 2)"*; nothing there mentions watches.
(`ABSENCE` 3 in the detectors block controls the "nothing says" claim.)

**Where the prior design (`docs/2026-09-13-z80-timing-currency-design.md`) is wrong or out of date at HEAD**, each
checked here:

- **§3's `Z80Access` kinds `Fetch | Read | Write | Ack` cannot come from §4's `Watched` wrapper as described.**
  `Watched` "implements `Z80Io` by forwarding", but `Z80Io` (`z80/mod.rs:39-51`) has only `read`/`write`/`input`/
  `output`. An M1 opcode fetch, an operand fetch and a data read are all `bus.read` (`z80/mod.rs:486-499`), and on
  this machine an IM 1 acknowledge makes **no** bus call at all (`z80/mod.rs:658-664`: the floating bus is modelled as
  a constant). So a forwarding wrapper sees `Read`/`Write` only. `Fetch` needs a defaulted `Z80Io` method called
  from `next_opcode`, and `Ack` needs an explicit call in `accept_interrupt`. **(reasoned from the code; measured
  that no such method exists: `ABSENCE` 4.)** The "candidate (d) for free" claim does not hold.
- **§0.7's "the hit ring stops being clock-ordered" is already true of today's tap, and the contract never promised
  otherwise.** The tap rides the same catch-up. `catch_up_z80` runs after the 68000 step and the clock advance
  (`system.rs:1531-1540`), so a Z80 hit's `mclk` lies in the same interval as the 68000 step's accesses and may be
  earlier than a 68000 hit recorded just before it **(reasoned)**. The scratch run saw no backwards step in 67 hits
  **(measured, but a 4-line window with two Z80 hits cannot refute it)**. The in-tree invariant
  (`tests/watchpoints.rs:272`) holds because its fixture holds the Z80 in reset. The contract promises `seq` order
  only (grep for `monoton` in `protocol.md` finds no hit-ordering claim). The draft (§6) says so explicitly.
- **§5's claim that the cheap half tells the reader** holds for in-process readers only; see §1.1.
- **The `EI` shadow is landed** (`z80/mod.rs:604-617`), so §7's parcel 3 is done. It does not affect this CR.

## 2. Who needs it (the real consumer)

The hub's rule: the contract grows against a real consumer, not a foreseeable one (§11.51 "Deferred, not rejected … Ground",
l.6192-6197; §11.50 "RIDER R1 IS DROPPED", l.6112-6118). I looked for consumers in every suite repo that calls the watch
methods, at a named revision.

**2.1 A live consumer of the one delivered kind: YES, aeon.** `aeon 85615e8:tools/song_load_mid_drum_witness.py`
(landed `06ca227b`, 2026-09-12; amended `d876177e`) arms `watchpoint_add {space:"bus", addr:"0x4000", len:4,
write:true}` (l.217-223) as **its only YM2612 write log**, because oracle serves `capabilities.vgm: false`
(l.16-26). It reconstructs (register, value) from the raw address (`part = 0 if addr in (YM_A0, YM_A1) else 1`,
l.244) and orders by `mclk`/`seq`. It does not read `fc`, `via`, `pc` or `symbol`. It has a **poison control**: leg L0
requires `seen > 0` and `matched > 0` and a `--poison` run that aims the watch where nothing writes must go loud
(l.23-26, l.51-52). The same instrument is documented as "the instrument the booking asked for" in
`docs/superpowers/notes/2026-09-12-owed-runtime-witnesses-c.md:70-74`. **So the delivered kind is load-bearing today**,
and it works by a behaviour the contract does not describe and §11.51's sentence contradicts. A server that
"fixed" the collision by dropping the tap from watches would silently remove aeon's only YM instrument (loudly, in
fact, thanks to L0; but nothing in the contract would say the server was wrong).

**2.2 A live consumer of the undelivered kinds (reads, fetches, RAM, the window): NO.** The one ask was aeon's F3
runtime tag, 2026-09-13 (`aeon 85615e8:docs/superpowers/notes/2026-09-13-f3-runtime-tag.md:47-54`): a read watch on
ROM bytes the Z80 reads got 0 hits. **aeon answered the question another way** (an A/B of the Z80 driver's own
channel state, same note §1) and closed the row (`docs/DEFERRED_WORK.md:8769-8778`). aeon's standing rule since is
"never read a zero Z80 count from a watch as a result" (`docs/superpowers/2026-09-13-aeon-overseer-handoff-14.md:99-101`).
No open row, decision, lens finding, queue entry or roadmap line in aeon asks for it (measured, `ABSENCE` 5), and no
aeon commit since 2026-09-14 mentioning the Z80 is about watches (`git log --since=2026-09-14 -i --grep=z80`: 15
commits, all LS-13b bus-hold, census or S2-room work, read by title). **The push for this parcel is the hub's, not a
client's:** empyrean `93740f63:docs/OVERSEER-LOG.md:15189` ("draft the F-Z80-ACCESSES-UNWATCHED contract CR now, since
the hub rules CRs, with no code until ruled").

**2.3 Other clients.** seraph (the DAW, `origin/HEAD` `f8a7a3b`) calls no watch method (`git grep -c -E
'watchpoint_(add|hits)'` → nothing). aurora (`40a9c3f`) mentions them only in two docs, no code. Oracle's own player
shows `caveats()` in its watch panel, so the in-process surface already tells the truth; the MCP surface is the
legacy shim and is out of scope.

**Consumer verdict.** There is a real, current consumer, but **of the tap, not of the full stream**. It needs the tap
to keep working and to be described truthfully. Nobody needs Z80 reads, fetches or RAM traffic on the watch surface
today. The full design is therefore deferred text with a named trigger (§5, §6.5), and the recommended change is
scoped to the tap.
