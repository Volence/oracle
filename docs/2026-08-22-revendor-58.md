## The three failures

The dry run predicted three and attributed one. All three reproduced exactly under the vendored 58, and
the attributed one **had changed form** — worth noting, because the upstream fix landing between the dry
run and this commit did not remove the failure, it moved it.

### 1. `params_closure::every_params_object_in_the_vendored_schema_is_closed` — class (c)

**Reproduced:**

```
thread 'every_params_object_in_the_vendored_schema_is_closed' panicked at
crates/oracle-aether/tests/params_closure.rs:143:10:
the description must state its fragment count as `N of §6's ... methods`
```

Not the dry run's `left: 37, right: 58`. The check parsed the description for the first `N of §6's …`
triple and compared it to the count derived from the document. Upstream's fix (`eecce95`) **deleted the
number** rather than repairing it — reasoning that a correction carrying the coordinate inherits the
defect, and that the parsing gate is the only authority worth pointing at. Our `.expect()` then fired on
its absence.

**Diagnosis, to ground truth.** The description's numeric triples, extracted by the test's own parse:

| revision | triples matching `_ of §6…` | numeric | disclaimer present |
|---|---|---|---|
| `82dde99e…` (dry run's candidate) | `37 of §6's`, `58 of §6's` | `[37, 58]` | no |
| `8cc08be1…` (adopted) | `subset of §6's` | `[]` | yes |

**Classification (c)** — the test encoded an assumption the new revision legitimately invalidates: that a
self-describing count must exist. It also encoded a second, weaker assumption the dry run flagged against
itself — that reading *the first* triple is the right parse position. The pre-fix candidate stated its own
size **twice, disagreeing with itself**, and a last-match parser would have gone green on it.

**Fixed properly, in both directions.** Every numeric triple is now checked against the parsed count, so
no position is privileged and a self-contradicting document is red whichever half is true. Where none is
stated, the document's own deliberate-omission sentence is required, read out of the document. There is
no third branch and no branch that asserts nothing — "no count present" and "the parser found nothing"
are otherwise the same observation from here, which is the vacuous shape this repo has been bitten by.

### 2. `schema_conformance::the_schema_covers_every_method_we_advertise_and_the_uncovered_list_is_pinned_empty` — class (c), and the F2 decision

**Reproduced:** `the schema has fragments for methods this server does not advertise: [… all 21 …]`.

This is F2. Its diagnosis and decision are the next section.

### 3. `mcp_tool_sweep::every_mcp_tool_property_is_declared_by_its_contract_fragment` — class (c)

**Reproduced:**

```
these MCP tool properties are declared by no contract fragment:
  ["audio_spectrum.fft_size", "audio_spectrum.max_hz", "wait_for_break.timeout_ms"]
```

The sweep compares the legacy MCP client's tool table against the fragments. Its numbers improve sharply
under 58 — tools with a fragment go 37 → 57 of 63 — and that improvement is what surfaces the conflict:
`audio_spectrum` and `wait_for_break` previously had **no fragment to disagree with**. Nothing regressed;
an instrument arrived.

**Diagnosis, to ground truth.** The dry run concluded "the fragments are right and the client is wrong".
empyrean checked the half the dry run did not and **inverted it** (`eecce95`): the legacy *server* reads
the snake_case spellings too — `req.getU32("fft_size")` assigned into a variable named `fftSize`, which is
why it hid so long — so client and server agree with each other and both diverge from §6. Acting on "fix
the client" would have broken the owner's working MCP tooling, since the server reads what the client
sends.

Their measurement across the whole legacy surface: 38 wire keys the server reads against 49 fragment
param names, **four** genuine conflicts — `fftSize`, `maxHz`, `timeoutMs`, and `maxFrames`. The ruling is
**direction only**: camelCase is the stated convention and D14 makes the schema normative for wire shapes,
so §6 does not move; the load-bearing half is that server and client must migrate together via
dual-accept, and the scheduling is the owner's call. In their words: *"Nothing in the ruling changes code
today."*

**Classification (c).** The test encoded the assumption that any tool property without a fragment is a
client bug to fix now. That was sound while the divergence was invisible and is not sound after a ruling
that says the fix is a coordinated migration nobody has scheduled. Neither artifact is ours; unilaterally
renaming either half is precisely the breakage the inversion was caught to prevent.

**Fixed properly: registered, not silenced.** See "What changed in the tests" below.

**Class (b) — the fragment is wrong: zero.** The dry run's one (b) was the stale description count, and
upstream fixed it in `eecce95` before this commit. Nothing here is blocked on a fragment defect, so there
is nothing to stop and report. **Class (a) — our server is wrong: zero**, and that is measured rather than
inferred: the whole aether suite ran with these bytes in place and no reply this server emits was refused
by any fragment.

## F2 — the decision, and its defence

> Is "schematized but not advertised" a legitimate steady state, and if so should the assertion become a
> reported count rather than a failure?

**Yes to the first. No to the second.** It becomes a **pinned set**.

### Why it is a legitimate steady state

1. **The contract says the fragment comes first.** §8 item 20 makes a fragment the *precondition* for a
   handler and not its record. The schema's own description says the CRAM pair was "schematized first on
   purpose" for exactly that reason. A gate that turns the contract's required order into a failure is
   punishing the artifact for being correct.
2. **These 21 are not this server's rows.** §6 is the suite catalog, not our backlog. Every one is served
   today by `oracle-old` and by no route in this process: no `METHODS` entry, no handler symbol, no cargo
   feature (`oracle-aether/Cargo.toml` has no `[features]` section at all), no runtime toggle. The dry run
   enumerated all seven routes that could produce a reply and named the blocker on each. Eight of the 21
   are governed by a capability flag this server publishes as `false` — the contract's own way of saying
   "not here".
3. **The failure the assertion was written to catch is a different failure.** Its comment names the case:
   §11.13's and §11.14's rows, which were *ours*, sitting unserved for days with nothing saying so.
   Nothing about these 21 was accepted here.

### Why not a reported count

A report says "21" and goes green forever. A 22nd fragment for a method we never serve — the exact
original failure — would then print `22` and pass.

Worse, a bare count and `is_empty()` share a shape: **both are satisfied by a schema that failed to load**,
parsed to nothing, or was silently empty. `0` and `not checked` are the same observation, and that is the
vacuous gate this repo has been bitten by before.

### What it became, and why that is strictly louder

A `const SCHEMATIZED_NOT_ADVERTISED: &[&str]` of the 21, compared with `assert_eq!` — the shape
`UNCOVERED_METHODS` beside it already uses. It fires in three directions where `is_empty()` fired in one:

* a fragment arriving for a 22nd unserved method (the original purpose, kept);
* one of the 21 **becoming served**, forcing its removal in the commit that ships the handler — the half
  `is_empty()` could never have caught, since serving a method only moved it *toward* green;
* an empty or unparsed schema, because the expectation is 21 names and not zero. This is the property the
  brief demands: **the check cannot be satisfied by not running.**

The list is literal because it is a decision record — the same reasoning `UNCOVERED_METHODS` documents,
where the point is that the number cannot quietly improve. What must not be literal is any *claim* about
the names, so the two claims the pin implies are re-derived on every run from the schema and from
`METHODS`: each pinned name has a fragment in the document, and each is genuinely unadvertised. A typo or
a stale entry cannot sit there looking like a decision.

## What changed in the tests

Three files, one commit, each change proven red before it was trusted.

**`schema_conformance.rs`** — the F2 pin above, plus one new check and one **deleted** check.

The first thing written was `covered.len() + schema_only.len() == schematized.len()` and it was deleted
for being **tautological**: those two sets partition `schematized` by construction, so the identity holds
however few fragments `schematized` contains. An assertion that cannot fail is worse than none, because it
reads like coverage.

The real gap is one level back. `schematized` is built from fragments that declare a `result`, so a
fragment **without** one is invisible to every bucket — not in `covered`, `uncovered` or `schema_only` —
and all three pins stay green while a fragment nobody has looked at sits in the document. The replacement
re-derives the population straight off the raw document (every non-`$` key under `methods`) and requires
every fragment to reach the split. Its reachability was checked, not assumed: the other routes into
`schematized` shrinking are caught earlier (an *advertised* method losing its `result` trips the
`UNCOVERED_METHODS` pin; a *pinned* one trips the F2 pin), so the check was proven red on the one case
that is genuinely its own — a fragment neither advertised nor pinned, with `params` and no `result`.

**`params_closure.rs`** — the description-count parse, reshaped as described above.

**`mcp_tool_sweep.rs`** — D-33 registered as a named divergence with the ruling quoted, using `assert_eq!`
on the whole set rather than an allowlist subtraction, so it is anti-rot **in both directions**: a new
undeclared property is red because it is not in the pin, and a registered one going away is red too, so
the entry is deleted by the commit that resolves it rather than outliving its divergence. (That failure
mode is not hypothetical here — `schema_conformance.rs` records an allowance that outlived its divergence
and started *causing* the failure it was written to suppress.) It also cannot pass vacuously: the
expectation is three names, so a sweep that compared nothing fails where `is_empty()` called it success.

And the registry's own claim is **re-derived, not asserted**: each entry says *this is a respelling, not
an unknown parameter*, so the test respells it snake→camel and requires the fragment to declare that
partner. A genuinely undeclared param smuggled into the registry has no partner and is rejected — the pin
cannot be used to hide the bug the file exists to find.

### Why our sweep sees three and empyrean measured four

The fourth conflict is `call_stack.max_frames`, and it is invisible to this sweep for a structural reason
rather than by oversight: `call_stack` is one of the **eight §6 rows the contract deliberately leaves
unschematized**, so it has no fragment and the sweep reports it as `unschematized` and moves on. It will
appear here, as a fourth entry, on the day that eighth row is schematized. That is written into the
registry's comment so the arrival is not read as a new defect.

`emulator/play_input`'s `maxFrames` — camelCase, in the same file — is conformant and is not this.

## Things found that were not asked about

1. **The upstream fix moved the failure rather than removing it.** The brief said the description-count
   defect was "since fixed upstream", which is true — and the check still went red, because upstream fixed
   it by deleting the number and our parser required one to exist. Worth generalising: *a defect repaired
   by removing the field is not the same event as a defect repaired by correcting it*, and a consumer that
   parses the field sees the two very differently.
2. **The dry run's conclusion on D-33 was inverted upstream, and our repo now carries the corrected
   version.** "The client is wrong" was reported here in good faith after checking one of two artifacts;
   acting on it would have broken the owner's working MCP tooling. The inversion is quoted in the test's
   own comment so the corrected finding travels with the code rather than only in a doc.
3. **`call_stack.max_frames` — the fourth D-33 conflict — is structurally invisible to our sweep**, and
   will surface as a *new* undeclared property the day the eighth blocked §6 row is schematized. Written
   into the registry's comment so that arrival is not mistaken for a regression.
4. **`empyrean`'s `origin/main` moved twice inside this single task.** Any future instruction phrased as
   "vendor from revision X" should be read as naming a blob; the tips in a brief are stale on arrival.
5. **`params_closure`'s old count check would have gone green on a document that contradicted itself**,
   had upstream repaired the number in the later position instead of the earlier one. That was luck of
   parse position, not a working gate. It is now checked at every position.
