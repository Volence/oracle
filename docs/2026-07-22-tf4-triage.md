# DR-2 Thunder Force IV triage — what the `$0FF35x` init loop is actually waiting on

**Status: TRIAGE (recon), 2026-07-22. Docs only — no code.** TF4 survived both DR-1 slices (BUSREQ + FM-status)
unchanged, proving it is *not* the Gunstar family. The overseer's single triage question: **is TF4's stuck
init loop polling a Z80-RAM mailbox (→ promotes the full Z80 core) or uploading fine but the render/DMA is
wrong (→ promotes the render thread)?** This doc answers it with a direct measurement of oracle-next running
TF4, and picks the next rock with a datum.

**Method.** A throwaway instrumented run of oracle-next (a `BusEventSink` capturing per-instruction PC + read
addresses via `on_step_boundary`, plus a one-line print of the DMA cost path — **all reverted**, nothing
committed, tree clean). TF4 ROM on the user's disk (D5). Static disassembly of TF4 cross-checks each dynamic
finding.

Items **T1–T5**. Each states the finding, its evidence, and its bearing on the branch decision.

---

## T1 — TF4 does **not** poll a Z80-RAM mailbox → it does **not** need the Z80 core

**PINNED.** Across every captured window (boot and the settled loop), the CPU makes **zero** reads of Z80
space (`$A00000–$A0FFFF`) — and zero reads of the FM ports, the I/O block, or the VDP status/HV port
(`$C00004–7`). TF4 is **not** waiting on any byte another chip would set. **Evidence**: instrumented read
tally over multiple frames — `z80_reads=0`, `vdp_status_reads=0`, `io_reads=0`. This directly **eliminates the
Z80-mailbox branch**: no amount of Z80 execution would change a loop that never reads what the Z80 writes.

## T2 — Not a status poll, not a `STOP`

**PINNED.** The loop reads only ROM (instruction fetches + table data) and work RAM. There is **no** `STOP`
instruction anywhere in TF4's boot region (`$0FE000–$100000` scanned — zero `$4E72`). SR sits at `$2700`
(interrupts masked) throughout, but nothing is waiting on an interrupt-set flag either (T1: no polled address).
So the stall is **not** a wait-for-external-event of any kind. **Evidence**: static `$4E72` scan (empty);
dynamic read tally (only ROM/work-RAM); SR trajectory constant `$2700`.

## T3 — The stall is a single 68k→VRAM DMA that halts the CPU for ~28 frames

**PINNED — this is the blocker.** TF4's boot advances **only 531 instructions total**, and that count is
**frozen at 531 for a 2-, 6-, or 20-frame run alike** — one instruction consumes *all remaining* mclk no matter
how much is given. The frame-eating instruction is at **PC `$0FF350`: `move.l d6,(4,a6)`** — a **long write to
the VDP control port** (`$C00004`). In oracle-next a control-port write runs any armed DMA
(`bus.rs:390 run_pending_dma`), and here it fires a **68k→VRAM Mem DMA** whose measured cost is:

```
mem-DMA  len=0x0000  count=65536 words  src=$FF0100  target=VRAM
         cost = 24,903,680 mclk = 3,557,669 CPU cycles wait  (~27.8 NTSC frames)
```

`run_mem_dma` treats a length register of **0 as 65536 words** (`bus.rs:425`), and charges the whole transfer
to the triggering instruction as one CPU-halt (`bus.rs:449`). So a single `move.l` stalls the 68000 for ~28
frames; boot never escapes the first upload pass. **Evidence**: instrumented last-PC (`$0FF350`) + the printed
DMA cost; the frozen 531-step count across frame budgets; static disasm of `$0FF340–$0FF36E` (the control write
feeding a VRAM-upload loop, `d5` = a VDP command advanced by `$80` per pass).

## T4 — The root: a spurious / mis-decoded DMA, or a length-register-capture bug (for the next slice)

**OPEN (framed, not solved — belongs to the next rock).** Two facts make the 65536-word DMA look **wrong**,
not a legitimate big transfer:

- At the sampled point **DMA-enable is off**: VDP reg 1 = `$44`, **bit 4 (M1 / DMA enable) = 0**. A control
  write with CD5 set should not start a DMA while DMA is disabled.
- The **DMA length registers are 0** (reg 19 = `$00`, reg 20 = `$00`) → the `len==0 ⇒ 65536` path. A game does
  not normally kick a max-length 68k→VRAM DMA during a tile-upload loop that is otherwise doing plain data-port
  writes (`$0FF35C/$0FF360 move.w (a0,d0),(a6)`).

So oracle-next is most likely **either** (a) decoding a non-DMA VRAM-write command as a DMA trigger (a
control-word CD-bit / DMA-enable-gating bug), **or** (b) firing a real DMA but with the length registers read
as 0 because TF4 set them by a path oracle-next didn't capture. Disambiguating (a) vs (b) — and confirming
whether DMA should be gated on reg-1 bit 4 — is the **first task of the follow-up VDP/DMA recon**, not this
triage.

## T5 — Verdict: TF4 is the render/VDP-DMA thread, not the Z80 core

**PINNED.** T1 rules out the Z80-mailbox branch; T3 localizes the blocker to oracle-next's **68k→VRAM DMA
model** (a runaway halt window from a len=0 transfer that likely should not be firing at all, T4). TF4 is a
**VDP/DMA-timing/decode bug — the same family as DR-3 (Batman & Robin)**, which the sweep already classified as
a separate VDP/DMA render bug. **DR-2 and DR-3 collapse into one rock: the VDP/DMA thread.**

---

## Recommendation — next rock

**Open the VDP/DMA recon (DR-2 + DR-3), with TF4's `$0FF350` len=0 halt as the concrete entry point.** The
first question it must answer (T4): *why does a control write fire a 65536-word 68k→VRAM DMA while reg-1 bit 4
(DMA enable) is 0 and the length registers are 0* — is oracle-next mis-decoding a plain VRAM-write command as a
DMA, or mis-capturing the length? Either way the fix is bounded and in the VDP/bus layer (no Z80 core). Then
re-test TF4 (should boot past `$0FF350`) and Batman (DR-3). This picks the rock with a reproducible datum, not a
guess — the same rhythm as DR-1a/DR-1b.

**The full Z80 core is *not* promoted by TF4.** It remains deferred until a game is found whose block genuinely
depends on Z80 *execution* (a real mailbox) — TF4 is not it.
