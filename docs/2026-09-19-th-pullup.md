# The undriven-TH pull direction — F-TH-PULLUP-UNDISCRIMINATED, settled to *corroborated*

**Status: CORROBORATED 2026-09-19** (parcel `F-TH-PULLUP-UNDISCRIMINATED`, branch `parcel/th-pullup`).
Outcome **(a)** of the three the brief allowed. Nothing under `crates/oracle-core/src/` was changed.

**The rule under test**, pinned at `docs/2026-07-17-io-recon.md` IO3: *"A wire configured as input with nothing
driving it floats **high** (pull-up → reads `1`)."* Every pad-detection argument in this tree stands on it,
and so does the 2026-09-18 answer to `docs/2026-07-25-testrom-conformance.md`'s **Q1** — that
`vdp_sprite_masking`'s on-screen "press Start" text is stale, because the ROM never makes TH an output, so
TH floats high and bit 5 of the byte it reads is `C`, not `Start`. **If the pull were the other way, bit 5
would be `Start` and the ROM's text would have been right all along.**

**The verdict: the rule stands.** Four arms agree, with the confidence each can carry stated below. One is a
mechanism rather than an assertion, and it is the strongest: **the 3-button pad carries its own discrete
pull-up on the select line**, so a plugged-in pad holds TH high whenever the console is not driving it,
whatever the console's internal pull does.

**And the brief's premise needed correcting.** It said *"No ROM in our corpus discriminates it."* That was
true when the follow-up was registered and **false by the end of the same landing that registered it**:
`TESTROM-H40-HALF` taught the harness to reach `vdp_sprite_masking`'s H40 half **by pressing `C`**, which
only works if an undriven TH reads high. Measured below — the corpus row goes red under the mutation.

---

## Arm 1 — our own core. A consistency check, and *not* evidence.

`crates/oracle-core/src/io.rs` answers `$FF`, and it does so **by construction**: `Io::read_data` contains
`true // input pin floats high` and `pad_device_byte` forces bit 7 high, which together *are* IO3 and IO4.
Asking our core what an input TH reads and asserting the answer cannot fail. **An expectation derived from
the thing under test is not a measurement**, and writing this arm up as though it settled the question would
be the sharpest form of the mistake this repo keeps banking.

What it *is* good for: it showed that our core and BlastEm run the same ROM image to the same twelve
observables on bits 6–0, which is a **differential** and is the only thing an in-tree gate can honestly
police. That is what `undriven_th_reads_high_in_both_models` asserts, against BlastEm's recorded table.

*A second finding of this arm, which was not the question:* the existing unit tests in `io.rs` never
configure a port with TH as an **input** — `configured()` writes `ctrl = $40` every time, and
`exp_port_reads_an_all_released_pad` does too. So before this parcel the pull direction had **no direct
test at all**, which is what the follow-up said. Confirmed under mutation:
`holding_start_changes_the_backdrop_via_the_real_pad_protocol` and
`an_unrelated_button_does_not_flip_the_start_backdrop` both stay **green** with the pull inverted, because
`build_pad_poll`'s ROM *drives* TH.

## Arm 2 — BlastEm 0.6.2 over the bus. An independent model, and still not hardware.

`tools/blastem-differential/th_pullup.bin` (built by `build_th_pullup.py`, driven by `run_th_pullup.py`
through the existing RAM-dispatch RSP rig) reads `$A10003` in states no corpus ROM visits. **The same image
is what the in-tree gate loads** — one instrument, two models.

Recorded 2026-09-18, nothing held on the pad:

| obs | what | read | meaning |
|---|---|---|---|
| +0 | `$A10003` P1 Data, **pristine** | `$7F` | **bits 6–0 all high → TH reads HIGH while an input** |
| +1 | `$A10009` P1 Ctrl, pristine | `$00` | premise: Control powers on at `$00` — *observed, not assumed* |
| +2 | `$A10005` P2 Data, pristine | `$7F` | the same answer on a second port |
| +3 | `$A1000B` P2 Ctrl, pristine | `$00` | premise, Port 2 |
| +4 | `$A10001` version | `$A0` | the I/O block answers, and not with `$FF` |
| +5 | latch `$40`, ctrl `$00` | `$7F` | with +8, rules out an input pin echoing its own latch |
| +6 | ctrl `$40`, latch `$40` | `$7F` | **CONTROL**: TH genuinely driven high |
| +7 | ctrl `$40`, latch `$00` | `$33` | **CONTROL**: TH driven low — bit 6 clear, bits 3–2 forced low |
| +8 | back to ctrl `$00` | `$7F` | TH an input again |
| +9 | `$A10009` read back | `$00` | |
| +10 | ctrl `$40`, latch `$C0` | `$FF` | bit 7 — see the divergence below |
| +11 | ctrl `$00`, latch `$80` | `$FF` | likewise |

**The controls are what give the main cells meaning.** +7 reading `$33` proves this ROM and this readback
path *can* carry a low TH and the pad's forced bits 3–2, so +0/+5/+8 reading `$7F` is a measurement of a
**high** TH rather than a stuck value. The three-way discriminator on bits 6–0 of (+0, +5, +8):

| hypothesis | +0 | +5 | +8 | observed? |
|---|---|---|---|---|
| **pull-up HIGH** (IO3 as pinned) | `$7F` | `$7F` | `$7F` | **yes** |
| pull-down LOW | `$33` | `$33` | `$33` | no |
| input pin echoes the latch | `$33` | `$7F` | `$33` | no |

**What this arm proves:** a model nobody in this tree wrote, reading the same bytes, reads an undriven TH
high. Two independent models agreeing is real evidence. **What it cannot prove:** hardware. Both models can
inherit one documentation error, and BlastEm has already been caught with a blind spot **in this very rig**
— it never traces `STOP` for any `T`, failing even the cell where every candidate rule agrees (see
`tools/blastem-differential/README.md`). So this is corroboration, not proof.

*Method note, stated because the rule says a tightened method is retroactive.* The runner's first
predicates were whole-byte (`$FF` / `$B3`) and both controls reported **FAILED** on the first run, because
BlastEm read `$7F` / `$33` — bit 7 low. The predicates were rewritten to compare bits 6–0, bit 7 was given
its own two observables (+10/+11), and **the whole experiment was re-run**; nothing was patched around and
no earlier number is carried forward.

## Arm 3 — documented sources. What IO3 actually cites for the pull direction: **nothing.**

This is the finding the brief said would be more useful than a passing test, and it is the one to act on.

**IO3's own citation does not cover its pull-direction sentence.** IO3 quotes Plutiedev "Mega Drive I/O
ports" for the read/write *model* — *"Writing to the data port changes the values of the pins that have been
set as outputs (the rest are ignored)… Reading back from the data port returns the current values of all
pins (both input and output)"* — and that quote is accurate and load-bearing for the mask expression. It
says **nothing about which way an undriven pin floats.** The page was re-fetched and scanned: the word
*pull* appears on `plutiedev.com/io-ports` only in the two sentences about **Control bit 7**, the
TH-interrupt enable. `plutiedev.com/controllers` does not contain it at all, and mentions register bit 7
nowhere. **IO2's parenthetical** *"the port floats high through its pull-ups until a game configures it"*
is likewise uncited, and **IO4's table row** *"bit 7 — 1 (pull-up, undriven)"* is not in the material IO4
quotes. So three separate statements of the pull rest on one unattributed clause.

**What the permitted source does say, and it points the same way.** Plutiedev "Controllers", section
*Checking if there's a controller*: *"If there's nothing in the port it should look as if no buttons are
pressed, so normally you don't have to bother with this. If you want to check if there's a controller
however … look at bits 3-2 from the second step: they **should be `00`**. If they aren't, then it means
there isn't a controller plugged in."* Buttons are active-low (IO4, cited), so *"looks as if no buttons are
pressed"* **is** *"undriven pins read `1`"*; and bits 3–2, which a present pad pulls to ground, read
**not-`00`** when nothing is there. That is a documented statement of the pull direction from the permitted
source — it is simply not on the page-section IO3 cites, and it is about D2/D3 rather than TH.

**The mechanism, and the strongest leg.** Hardware teardowns of the pad itself state the pull *and its
reason*, which the brief said beats a bare assertion:

* *Sega Six Button Controller Hardware Info* (`github.com/SukkoPera/MegaDrivePlusPlus` wiki): *"Inside the
  controller is a small PC board which contains the 74HC157, some 10K pull-up resistors and some bypass
  capacitors. The switches are connected so when a switch is pressed (closed) it shorts its output to
  ground, otherwise it's output is 5 volts (via the pull-up resistors)."* And decisively: **"One additional
  connection is a pull-up resistor on the select line. If it is left unconnected it will be 'pulled'
  high."** For the six-button pad: *"the pull-up resistors for the switches have moved inside the chip …
  The pull-up for the select signal still exists as a discrete resistor."*
* *Sega Genesis Controller Interfacing* (Strong & Just, U. Alberta CMPE 490 app note, 2016) and the
  `jonthysell/SegaController` wiki agree: *"By default, all of the output pins are set high (meaning a
  button press will bring the pin down to ground)"*; *"If pin 7 … is left floating, the controller defaults
  to this line being high."*

**Why the mechanism matters more than the console's pull.** The select line is TH. The console leaving TH
an input means it presents a high impedance; the **pad's own** resistor then holds the line at 5 V, the
`74HC157`'s select input sees `1`, and the pad multiplexes out its TH-**high** nibble, in which bit 5 is
`C`. So the answer does not even depend on whether the I/O chip has internal pull-ups: with a 3-button pad
plugged in, an undriven TH is high **because the pad pulls it there**.

**Source classification, per the recon doc's own audit policy.** Permitted: Plutiedev (the detection
paragraph above) and the Sega Software Manual. The pad teardowns are **hardware references outside that
policy's list** — they are not emulator source, but they are also not one of the three named source classes,
so they are recorded here as **corroborating mechanism**, not as the pin. **The official Sega Software
Manual's own text on the port pull-ups was not located in this session**; that is a gap in this arm, not a
silence in the manual, and it is stated rather than papered over.

## Arm 4 — the corpus, which turns out to discriminate it after all.

Measured, and it corrects the brief. `vendor/TestRoms/vdp_sprite_masking.bin` was fetched
(`sha256 1331819e…dc967d`, matching `tools/testroms.sha256`) and `tests/conformance_roms.rs` run **with the
pull-direction mutation applied**:

```
testrom_conformance_scorecard ... FAILED
the_glyph_scrape_reads_the_live_render_path ... FAILED
  vdp_sprite_masking never went idle within 300 frames in its H40 half
  (stopped at StopRecord { reason: DeadlineReached, pc: 790, frame: 317, … })
```

`pc: 790` is `$000316` — the `btst #5,$A10003` of the ROM's wait routine, exactly the instruction the Q1
write-up disassembles. With the pull inverted the ROM waits for `Start` on bit 5, the harness presses `C`,
and the H40 half never arrives. Both rows are green again with the baseline restored (`H32` and `H40` each
`1=TICK/TICK … 9=TICK/TICK`).

**So the corpus has had a discriminator since 2026-09-18** — since the landing that registered this
follow-up taught the harness to press `C`. **It is an indirect one and does not replace the direct gate**:
what it prints is *"never went idle within 300 frames … the idle condition no longer describes this ROM"*,
which points a reader at a frame budget, not at a pull direction. A row that goes red for the right reason
with the wrong message is a discriminator you cannot read.

## The one thing that changed hands: **Data bit 7**

The instrument found a divergence that was not the question, and it is **booked, not fixed**.

* **Ours** (`pad_device_byte`): bit 7 is `1` unconditionally — IO4's table row *"1 (pull-up, undriven)"*.
* **BlastEm 0.6.2**: bit 7 is **the Data latch's own bit 7** — `0` at every observable until the ROM writes
  `$C0`/`$80`, then `1`, and independently of the Control register, which has no direction bit for it
  (Control bit 7 is the TH-interrupt enable, IO2).

Every BlastEm observable above is consistent with that and with nothing else. So on a pristine pad read our
core returns `$FF` where BlastEm returns `$7F`: **a one-bit divergence on every pad read that does not first
latch a `1` into bit 7** — which is every pad read a normal game performs.

**Neither side is corroborated.** The port has seven I/O pins, so no pin corresponds to Data bit 7 at all;
Plutiedev's I/O-ports and Controllers pages do not mention the register's bit 7, and the MegaDrive wiki's
`315-5309` page **contradicts itself** on it (*"PD7: Unused. Should be set as 0"* immediately followed by
*"PD7: /TH pin"*). Recorded as **F-IO-DATA-BIT7** with the same standing as `known_differences.py`'s
STOP × trace entry, and pinned by `bit_7_of_the_data_register_is_a_recorded_divergence` so that changing
our side is loud rather than silent.

**It does not touch Q1.** Q1 turns on bit 5 (`btst #5`) and on bit 6 (whether TH is high). Bit 7 is neither.
The bytes the Q1 write-up records (`$FF` released, `$DF` with `C` held) would be `$7F` and `$5F` under
BlastEm's bit-7 model; bit 5 is unchanged in both, and so is the conclusion.

## Confidence, and what is still missing

**Confidence: high that an undriven TH reads high** — higher than before this parcel, and for a reason that
is not "two emulators agree". The pad's discrete pull-up on the select line is a *mechanism* stated by
hardware teardowns, and it makes the console's own pull irrelevant to the case the corpus actually cares
about (a pad plugged in, the console not driving TH). Plutiedev's controller-detection paragraph says the
same thing from the software side, and an independent emulator, a corpus ROM, and our core all behave that
way.

**Still missing: real hardware.** Nothing here is a measurement on a Mega Drive. What would close that last
gap is `th_pullup.bin` run on a console with its result read back — the ROM is committed and does not need a
screen, so it would need only a way to observe work RAM (a flash cart with a debug link, or a build that
paints the twelve observables onto the screen). **Tagged for foreground follow-up**; a background agent
cannot do it.

**Also still open, and narrower than before:** `F-IO-DATA-BIT7` above. And the *citation* gap, which is a
documentation defect rather than a behaviour one: IO3's pull sentence, IO2's parenthetical and IO4's bit-7
row were all uncited. IO3 and IO4 are amended with what is now known.

## Reproduce

```bash
cd tools/blastem-differential
python3 build_th_pullup.py          # -> th_pullup.bin + the listing
python3 run_th_pullup.py            # the BlastEm arm (needs xvfb-run + the blastem binary)
cd ../.. && cargo test -p oracle-core --test io_controllers
```

`build_th_pullup.py` hand-assembles the image rather than calling `asl`/`p2bin` like this rig's other
builders: `resolve_aeon_tools` on this box resolves a directory holding `convsym` and **no assembler**, so
making the parcel's result depend on that toolchain would have made it unreproducible. `--check` verifies
the committed `.bin` still matches a fresh assembly, and `run_th_pullup.py` refuses to run if it does not.
