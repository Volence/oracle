## R1 — Control-port pending-command semantics (§2 control-port state)

**PINNED.**

- **No input latch.** The control port feeds the internal code/address registers directly:
  the 1st word applies CD1–CD0 + A13–A0 *immediately*; the 2nd word applies CD5–CD2 + A15–A14.
  A word whose top two bits are `10` is a register write — it completes in one word and never
  arms the second-half state. (Kabuto: *"The VDP's command port is directly connected to its
  internal address buffer without any latching … after writing the 1st half of an address the
  next write will go to the 2nd half unless you e.g. write to the data port first"*;
  format from the official Genesis Technical Overview §6.)
- **A partial (first-word-only) write is a real operation**: the *live* code/address registers
  already hold the new low half with the old high half, and the auto-incrementing address
  reloads from it (Nemesis, VDP Internals t=1291 p.4: *"This cached address register gets
  reloaded from the live address register even if you only perform a partial control port
  write"*). A data-port access after only the first word proceeds on that half-updated state.
- **What clears the armed toggle**: (i) the second word (command complete); (ii) a
  **data-port write** (Kabuto, doc-pinned; experiment-confirmed); (iii) a **control-port
  (status) read** — *experiment-pinned* (permitted docs are silent; the BlastEm run below is
  the evidence, same instrument standing as the STOP×trace pin — flagged as
  instrument-sourced, revisit if a better oracle contradicts). An **HV-counter read does
  NOT clear it** (same experiment). A register write ($8xxx first word) never arms the
  toggle; an armed toggle consumes *any* next control write as the second word.
- **Danger cell pinned as lockup**: a data-port *read* after rewriting just the first half of
  a read command hangs the machine (Nemesis t=1291: partial write disturbs CD4; Mask of
  Destiny t=2036: *"if you setup a write and then try to read the 68K will hang until the
  machine is reset"*). The emulator must model a deterministic outcome for these (documented
  stall), never a host hang.
- **Control port during DMA fill**: officially prohibited (only PSG/HV/status may be touched
  mid-fill — Technical Overview §7). Mechanism: the fill runs off the **live** command
  code/address registers, so a mid-fill control write redirects the remainder; the status
  DMA-busy flag sets on the fill's *control-port* setup write, not the data-port trigger
  (Eke). CD5 can only be changed by a control write while DMA-enable (reg 1 bit 4) is set;
  with it clear, CD5 is retained.
- Sega's own 1993 technical bulletin treats interrupt-interleaved port access purely as a
  *software* hazard (disable interrupts around command setup) — no hardware reset rule exists.

**Evidence**: Kabuto notes (plutiedev.com/mirror/kabuto-hardware-notes); Nemesis, SpritesMind
t=1291 p.4; Sega Genesis Technical Overview v1.00 §6/§7; Sega Mega Drive Technical Bulletin
(Dave Marshall, 1993-07-08) + the Address Checker spec (partial-command detection); Mask of
Destiny t=2036/t=2492; the vdp_pending experiment below.
**Confidence**: high (no conflicts). **Classification**: behavioral (register state, lockups,
real-game interrupt bugs).
**Open remainder**: full mid-fill control-write semantics beyond the live-register mechanism —
*interim model = live-register redirect* (the DMA-push experiment did not force a pin: Nemesis
records hardware itself as intermittent on three of these cells, so this stays a documented
limitation, not a pin — see R4). Data-port-read effect on the toggle in the non-lockup
configurations — **RESOLVED (DMA push, 2026-07-16, `vdp_dma_fill.asm` cell 1)**: the config in
which the toggle is armed *and* a data-port read is issued **is** the pinned lockup — BlastEm
0.6.2 hangs (watchdog timeout, no done marker), confirming the read-while-write-armed lockup
brackets the whole window, exactly as this section predicted ("low exposure: the lockup cell
brackets it"). So there is no reachable non-lockup armed-read window to observe a toggle clear;
the legal case (a read after a *completed* read command) clears the toggle like any data-port
access (implemented in `data_read`). Instrument-sourced, same standing as the other BlastEm pins.

## R2 — H/V counter mid-line jump values (§2 timing FSM)

**PINNED.**

- **H counter (the $C00008 read is the top 8 of a 9-bit counter):**
  H32 `0x00–0x93` then `0xE9–0xFF` (171 values = 342 positions); H40 `0x00–0xB6` then
  `0xE4–0xFF` (211 values = 422 positions).
- **V counter, NTSC V28:** `0x00–0xEA` then `0xE5–0xFF` (235 + 27 = 262 lines ✓); the jump is
  `0xEA → 0xE5`. VBlank status flag sets at the `0xDF → 0xE0` transition.
- **Phase anchors** (flag transitions, hardware-sampled): HBlank flag sets at H `0x92→0x93`
  (H32) / `0xB2→0xB3` (H40), clears at `0x04→0x05` (H32) / `0x05→0x06` (H40). The V counter
  increments mid-line at H `0x84→0x85` (H32) / `0xA4→0xA5` (H40).
- **HV latch (reg 0 bit 1, M3)**: freezes the readable HV counter; the value latches on the
  HL trigger input (lightgun), which also raises the level-2 external interrupt (official).

**Evidence**: Nemesis, SpritesMind t=768 (hardware-sampled progressions, quoted verbatim);
Kabuto notes (independent corroboration, identical numbers); Sega Genesis Software Manual §6
(HV counter + M3 + the not-valid-during-vblank caution). **Confidence**: high — two
independent hardware testers agree exactly. **Classification**: behavioral (games poll
$C00008 for raster effects; the jump values are what they observe).
**Open remainder**: M3 freeze-on-write vs latch-on-HL nuance — *defer* (needs the lightgun
HL pin, which the Mega Drive pad path never asserts; revisit with peripheral support).

## R3 — FIFO + external access slots (§2 FIFO)

**PINNED.**

- **FIFO: 4 entries**, each storing the data word **plus a copy of the code/address registers
  at enqueue time**. FIFO full ⇒ the 68k write stalls via /DTACK (official max wait ≈5.96 µs
  H32 / ≈4.77 µs H40). FIFO state never delays control-port writes.
- **External (CPU/DMA) access slots per line**: active display **H32 = 16, H40 = 18**;
  vblank or display-off lines **H32 = 167 (+4 refresh), H40 = 205 (+5 refresh)**.
- **Slot width**: one slot = one byte-wide VRAM access — a FIFO word to VRAM takes **2
  slots**; CRAM/VSRAM writes use the same slots at **one word per slot**. ~2–3 slots of
  latency through the FIFO (entry-vs-exit attribution unresolved).
- **Reads bypass the FIFO**: a separate read buffer with pre-cache — the fetch happens at an
  external slot once the write FIFO is empty; a data-port read with nothing cached stalls the
  68k; pending FIFO writes take priority over reads and over DMA-fill steps.
- **Snoop quirk** (behavioral): CRAM/VSRAM read results fill their undefined bits from the
  next-available FIFO entry (the data written 4 data-port writes ago).

**Evidence**: Sega Genesis Technical Overview v1.00 "ACCESS TIMING" (16 accesses/line active,
167/205 blanked, the 4-word FIFO + CPU wait); Mask of Destiny t=2492/t=2036 (slot mechanics,
byte-wide VRAM exit, /DTACK stall); TascoDLX t=851 (167+4 / 205+5); Eke t=851 p.2; Nemesis
t=1291 p.4 (FIFO entry contents, read pre-cache, snoop quirk). A conflicting Near paraphrase
(204, "4 or 6") in t=3221 is outweighed by the official 205 + TascoDLX.
**Confidence**: high. **Classification**: depth/entry-contents/stall/read-buffer/snoop =
behavioral; slot counts + FIFO latency = pure timing (they gate *when* the behavioral
effects manifest).
**Open remainder**: exact slot positions within the line (Nemesis/Kabuto published per-slot
maps — fetch when Phase 3 needs slot-exact timing) — *defer, pure timing*; FIFO 2–3-slot
latency attribution — *defer, pure timing*.

## R4 — DMA ↔ 68k bus interaction (§2 DMA unit)

**PINNED.**

- **(a) 68k→VDP transfer: the 68k bus is taken for the whole transfer** (VDP does the full
  /BR → /BG → /BGACK arbitration; the 68k idles until /BGACK releases). Transferred words go
  **through the FIFO** (the DMA engine pauses when it's full). The Z80 keeps running unless
  it touches the 68k bus. *This is the design brief's "68k bus-stall crossing the
  deferred-write seam": the stall is total, not per-access — model as a bus-level halt window,
  fed through the `Bus68k` wait-cycle channel.*
- **(b) VRAM fill: the 68k keeps running** (no bus request). Officially only PSG/HV/status
  may be touched mid-fill. Hardware behavior of a mid-fill *data-port* write (Nemesis): the
  write enqueues normally, the fill suspends until the FIFO drains, resumes **with the new
  data**, and ends one location further (the write's autoincrement) — with a documented
  coalescing race. Fill steps run only in external slots with an empty FIFO. Fill data
  source: the last FIFO entry's data (top byte for VRAM; for CRAM/VSRAM fills, the
  next-available entry — "4 writes ago" — a documented hardware bug).
- **(c) VRAM copy: 68k keeps running**; copy bypasses the FIFO entirely but consumes the same
  external slots at one byte read + one byte write per step (half the fill's byte rate).
  Overlapping source/dest officially cautioned.
- **(d) The RAM-not-ROM trigger rule is official but unexplained**: for ROM→VRAM transfers,
  the destination write to $C00004 must be a word write and *"the final write must use the
  work RAM"* (Technical Overview §7, verbatim). Root cause not pinnable; Plutiedev links it
  to the separately-documented Z80/DMA bus-clash glitch. For the emulator: nothing to model
  beyond the Z80 bus-clash itself (later, with the Z80).
- **(e) Transfer rates = the R3 slot table**: VRAM ≈8/9 words per active line (H32/H40),
  ≈83/102 words per blanked line; CRAM/VSRAM 16/18 and 167/205 words. Copy at half byte
  rate; fill loses one slot on its first line (the trigger write). Kabuto's measured 68k-side
  cost formulas corroborate (fast `words×2.4+5.6`, slow `max(words×2.4+5.6, words×4.7−6)`
  68k cycles, 5 refresh skips/line).

**Evidence**: Sega Genesis Technical Overview v1.00 §7 (all three modes + the RAM rule,
verbatim); Eke t=2492 (/BR–/BG–/BGACK detail); TmEE t=2492 (mid-instruction bus grab
anecdote); Mask of Destiny t=2492/t=2036 (FIFO interaction per mode); Nemesis t=1291 p.4
(mid-fill writes, fill/copy step algorithms); Eke t=851 p.2 (rates); Kabuto notes (cycle
formulas); Plutiedev dma-transfer + hardware-issues.
**Confidence**: high for (a)(c)(d)(e); medium-high for the mid-fill write behavior (single
researcher, published test ROM, flagged "best working theory" in places).
**Classification**: (a) timing envelope with one behavioral edge (the 68k is frozen — programs
observe elapsed time, not state change); (b)(c) behavioral (mid-fill writes change VRAM
contents and addresses; busy flag is architectural); (e) pure timing.
**Open remainder**: RAM-rule root cause — *not pinnable, nothing to model*; mid-fill
control-port writes and CRAM/VSRAM fill timing variants — *documented limitation, interim model*
(Nemesis notes even hardware is intermittent on three of these cells — recorded honestly, not a
pin; the emulator uses the live-register redirect for mid-fill control writes and the
"4-writes-ago" next-available FIFO entry for CRAM/VSRAM fills).
**Pinned this push** (DMA + FIFO, 2026-07-16, `vdp_dma_fill.asm` cell 0 + `run_vdp_dma_fill.py`):
the **VRAM fill baseline is confirmed against BlastEm 0.6.2** — an 8-byte fill with DMA-enable set
(reg 1 bit 4), fill mode (reg 23 = `$80`), and autoincrement 1 wrote the data word's **top byte**
(`$EE` from `$EEEE`) to all 8 consecutive VRAM bytes, with DMA-busy (status bit 1) set across the
transfer window. This is the concrete R4(b) VRAM-fill behavior the DMA push implements (slice F).
**Harness feasibility CONFIRMED** (corrects the frame-capture-spike pessimism): the RSP-reads-
work-RAM pattern under `xvfb-run` reproduces cleanly — `vdp_pending` all 4 cells + both DMA cells.

## R5 — SAT cache update rules (§2 SAT cache)

**PINNED.**

- **Cached: the first 4 bytes of each 8-byte entry — Y (2) + size/link (2) — for all 80
  entries.** X and tile/attr are never cached. (Charles MacDonald's post omits link;
  Kabuto/Plutiedev include it, and phase-1 link-walking requires it — pinned as Y+size+link.)
- **Write-through window**: on *every* VRAM write the VDP checks the target against the SAT
  window computed from the **current** reg 5 (`base .. base+512` H32 / `base+640` H40); a hit
  on a Y or size/link field updates the cache entry. **There is no other refresh path — the
  VDP never re-reads the SAT from VRAM.**
- **Changing reg 5 does NOT invalidate or reload the cache** → stale-cache mixing: rendering
  uses cached Y/size/link (old table) + VRAM X/tile at the new base. Castlevania Bloodlines
  relies on this (Nemesis, t=1291).
- **Evaluation vs render split**: phase-1 sprite evaluation (which sprites touch this line,
  link order) reads **only the cache**; rendering fetches X + tile/attr **from VRAM at the
  current reg-5 slot address**, Y/size still from cache.
- **H40 masks reg 5 bit 0** (SAT forced to a $400 boundary; $200 in H32). The cache window
  compare is sensitive to the full 128 KB address range even in 64 KB mode (A16 mismatch →
  VRAM updated, cache not) — Kabuto.
- **68k→VRAM DMA updates the cache like CPU writes** (Charles MacDonald: *"Any DMA operation
  that writes to VRAM also counts"*).

**Evidence**: Charles MacDonald, SpritesMind t=666 (+ Graz's live hardware experiment in the
same thread); Nemesis t=1291; Kabuto notes; Plutiedev sprites page.
**Confidence**: high (medium-high on the DMA-updates point — single explicit statement,
consistent with Kabuto's formulation). **Classification**: behavioral throughout.
**Open remainder** (all behavioral → **pin by experiment in the sprite push**, interim model
documented in the design brief): DMA **fill/copy** vs the cache (not stated in any permitted
source — interim: all VRAM writes including fill/copy steps hit the window compare, matching
the general formulations); whether the H40 bit-0 masking applies to the cache window compare;
byte-wide odd-address writes into Y/size fields.

## R6 — VINT → Z80 /INT pulse width (§2 interrupts)

**PINNED.**

- Asserted at the same instant as the 68k VINT pending set — line `0xE0`, **H counter =
  0x02** (V28 NTSC) — and deasserted **one full scanline later at H = 0x02 on the next
  line**: exactly one line ≈ **228 Z80 clocks** (3420 mclk / 15). It cannot be disabled by
  any VDP register, and the deassert happens on schedule regardless of Z80-side masking.
- Level-sensed by the Z80 (IM1): a handler that re-enables within the window re-triggers; a
  Z80 that keeps interrupts disabled through the whole window **misses the frame's interrupt
  entirely** (nothing latches on the Z80 side) — a corollary of the two pinned facts, not a
  separately quoted test.

**Evidence**: Charles MacDonald, SpritesMind t=740 (*"asserted every frame for exactly one
scanline, and it can't be disabled … re-triggered … within 228 Z80 clock cycles"*); Eke t=787
(H=$02 set/clear endpoints; the masked-side independence flagged "needs to be confirmed" by
its author). **Confidence**: high on width/endpoints; medium on the masking independence and
the missed-interrupt corollary. **Classification**: behavioral for the Z80 program; the H=$02
endpoints are timing detail. **Open remainder**: mclk-exact assertion edge beyond "H=$02" —
*defer, pure timing* (the Z80 core doesn't exist yet; revisit at its recon).

## R7 — HINT line-counter reload/edge rules (§2 interrupts)

**PINNED** (NTSC V28; active lines 0–223, frame lines 0–261):

- **Reload** from reg 10: on **every line during vblank** (lines 225–261) and **immediately
  on underflow**. Writing reg 10 does *not* load the live counter; the value takes effect at
  the next reload (TmEE).
- **Decrement**: once per line, lines **0..=224** — line $E0 (224) is *included* ($F0 in V30
  mode). The HINT-pending flag sets on underflow at **H = $A6 (H40) / $86 (H32)**.
- **Underflow**: fires and reloads on the same line → with reg10 = N the HINT lines are
  N, 2N+1, 3N+2, … while ≤ 224. reg10 = 0 → every line 0..224 (official: *"the interrupt
  occurs every line"*). An HINT **can fire on line 224** (the first line after active); a
  line-0 HINT occurs iff reg10 = 0.
- The display-blank bit (reg 1 bit 6) has **no effect** on HINT generation (Eke, verified).

**Evidence**: Eke, SpritesMind t=787 (hardware-test summary, quoted verbatim in the recon
notes); Sega Genesis Software Manual (interrupt section: reg10=0/1/2 schedules, "CPU can
control the display of the next line but not the line on which the interrupt occurs"); TmEE
t=1511 (reload-on-event, not on write). **Confidence**: high (the line-224 and first-HINT
arithmetic follows directly from Eke's explicit "line $E0 … included" rule).
**Classification**: behavioral (which lines raise level 4 is what raster-split games are
built on); the in-line H position is timing.
**Open remainder**: whether line 261 differs from other vblank reload lines (implied no) and
mid-line reg-10 write granularity — *defer, pure timing at scanline granularity* (a mid-line
write lands "next line" in the scanline model by construction).

## R12 — Interrupt pending/clear + IPL deassert (§2 interrupts + the standing set_ipl docket item)

**PINNED** — the highest-value item; this is the design for the standing "delivered VInt
re-fires after RTE" docket entry.

- **Two pending latches** (hint_pending, vint_pending) + **combinational IPL**:
  `IPL = 6 if (vint_pending && IE0/reg1.b5) else 4 if (hint_pending && IE1/reg0.b4) else 0`.
- **Only the 68k interrupt-acknowledge clears a latch.** At /INTAK the VDP samples the
  acknowledged level off /IPL1–/IPL2, clears **that level's** flag, and re-drives IPL from
  the remaining flag. Eke (t=787, hardware): *"The only way for these two flags to be cleared
  is when the /INTACK signal is asserted."* They are **not** cleared by status reads,
  disabling the enable bits, frame start, or display on/off.
- **Documented conflict, resolved**: Nemesis (t=740) wrote that reading status clears the
  VINT flag; Eke's dedicated hardware tests (t=787), Charles MacDonald (*"In mode 5 the
  interrupt is cleared automatically when the 68000 issues an interrupt acknowledge cycle. In
  mode 4 … you must read the status register"* — the status-read rule is the **SMS mode-4**
  behavior), and TmEE's field experience all say IACK-only in mode 5. **Pinned: IACK-only.**
- **Enable gating**: clearing IE0/IE1 while pending drops the IPL line but keeps the latch;
  re-enabling with the flag still set re-asserts and the interrupt is taken — with the 68k's
  one-instruction latency (Mask of Destiny, t=2202: required for **Sesame Street Counting
  Cafe**). IPL follows a register write within ~90–210 ns (scope-measured; sub-instruction —
  effectively immediate at our granularity).
- **Both pending**: IPL = 6; the level-6 IACK clears only vint_pending; the VDP then re-drives
  level 4 and the HINT is serviced when the mask allows.

**Evidence**: Eke t=787 (quoted above + per-flag AND-gating); Charles MacDonald t=740; Mask
of Destiny t=2202 (scope measurements + the Counting Cafe gate); TmEE t=740; Sega Genesis
Software Manual (autovector levels 6/4/2). **Confidence**: high; the one conflict is
documented and resolved on hardware-test weight. **Classification**: behavioral throughout
(the one-instruction re-assert latency is a 68k property our instruction-boundary IPL
sampling already provides).
**Open remainder**: whether a mode-5 status read affects the F bit's *read-back value* (as
opposed to the latch/IPL) — *pin conservatively as no-side-effect* (safe: no permitted
evidence of any side effect; flag for a differential probe when the nightly VDP differential
exists); the level-2 EXT pending latch — *defer to the I/O push* (out of VDP scope).

## R8 — Leftmost-column v-scroll quirk in 2-cell mode (§3 pipeline step 2)

**PINNED, with an explicit model choice** (delegated call, recorded here):

- Trigger: 2-cell v-scroll mode + `hscroll % 16 != 0` (a partial column at the left edge).
- **H40: the partial column's v-scroll = `VSRAM[$4C] & VSRAM[$4E]`** (bitwise AND of the two
  *last* word entries, 38/39 — the entries for column 19's A and B planes), the **same value
  for both planes**. **H32: the partial column cannot v-scroll — fixed 0, both planes.**
  H-scroll *mode* (full/cell/line) is irrelevant.
- **Revision fork, documented**: Eke's hardware test (the AND rule) was on one Model 2
  (315-5660 integrated ASIC), explicitly flagged by him as untested on the discrete 315-5313;
  Plutiedev's hardware-issues page records revision variance (VSRAM 40→64 words at M2 VA4+;
  "column −1" v-scroll = garbage on early hardware, copy-of-column-0 on later).
  **Model choice: pin Eke's deterministic rule** (AND in H40, 0 in H32) — it is the only
  fully-specified documented behavior, it is deterministic (foundations rule), and the
  variance goes in the divergence ledger for the golden-frame/differential rungs to surface.

**Evidence**: Eke, SpritesMind t=737 (hardware test, quoted verbatim; corroborated against
Gynoug/Cuty/F1 behavior in-thread); Plutiedev hardware-issues. **Confidence**: high on the
tested unit; medium universality (hence the ledger entry). **Classification**: behavioral.
**Open remainder**: which revisions produce AND vs copy-of-column-0 vs garbage; whether
64-word-VSRAM parts use entries 62/63 — *recorded in the divergence ledger, revisit only if a
differential surfaces it* (behavioral, but pinned to a specific documented revision — the
open part is cross-revision variance, not our model's behavior).

## R9 — The window bug (§3 pipeline step 3)

**PINNED — officially documented by Sega.**

- **Trigger**: window on the **left** + plane A h-scroll not a multiple of 16 px
  (`hscroll & 15 != 0`). V-only scrolling does not trigger it; a right-side window never
  glitches (both official).
- **Effect**: the first 2-cell column of plane A right of the window boundary **reuses the
  tile data fetched for the window's last column** (Sega: *"the character corresponding to
  two cells on the right side of the boundary … will be disfigured"*; Sik: the window takes
  over plane A's map+tile fetch slots for that internal column). Official workaround: mask
  those two cells (high-priority window column / sprites).
- **Mechanism** (Mask of Destiny, t=2492): the VDP renders 42 internal columns (34 in H32);
  the extra column feeds fine scroll; the window doesn't consume the scroll-buffer column,
  which is why the right side is safe.

**Evidence**: Sega Genesis Software Manual §J "WINDOW" p.50 (verbatim, including the
diagram caption *"Display of this portion will be disfigured. Therefore, mask Scroll A by
using high priority."*); Sik + Mask of Destiny, SpritesMind t=2492. (Plutiedev has no window
article — the official manual is the primary source here.) **Confidence**: high.
**Classification**: behavioral (deterministic wrong tiles).
**Open remainder**: the sub-tile alignment of the reused pixels in the glitched column (Mask
of Destiny's buffer model implies the buffer is read at plane A's fine-scroll offset — an
inference) — *pin by golden-frame/differential during the planes push*; interim model: reuse
the window column's fetched tiles, read at plane A's fine-scroll offset.

## R10 — Sprite x=0 masking exact rules (§3 pipeline step 4)

**PINNED — and the design brief's "two modes" wording is CORRECTED: masking mode 2 does not
exist** (Nemesis's test ROM tests 7/8 exist specifically to verify emulators do *not*
implement it).

- **The rule** (Nemesis, hardware + the Sprite Masking & Overflow test ROM): an x=0 sprite
  masks all later-in-link-order sprites on its lines **only if at least one earlier sprite on
  that same line had x≠0**. First-on-line x=0 does not mask (stacking two doesn't either) —
  **unless the previous line ended in a sprite-pixel (dot) overflow**, in which case a
  first-on-line mask is effective for that line only.
- **The implementable formulation** (Kabuto, subsumes all three Nemesis test cases): *pixel
  output is disabled when a sprite with x=0 is read after a previous sprite read (same line,
  previous line, or previous frame) had x≠0; output re-enables at the start of the next
  line.* One latch.
- Mask sprites still consume a sprite slot and their declared pixel budget; parsing of the
  rest of the line continues (only pixel output is suppressed). Phase-1 evaluation never
  reads X (it is not cached — R5), so masking is strictly a render-phase effect.
- **Per-line limits** (corroborated): H40 = 20 sprites / 320 px / 80 total; H32 = 16 / 256 /
  64 total; only the first 80/64 link entries are ever parsed.
- X compare is on the full 9-bit field: X=512 behaves as X=0 (`x & 0x1FF == 0`) — medium
  confidence (single Natsumi post, unchallenged).

**Evidence**: Nemesis, SpritesMind t=541 (hardware statements + the test-ROM cell list,
quoted verbatim in the recon notes); Kabuto notes (the latch formulation); Plutiedev sprites
page (limits); Natsumi t=2576 (X&$1FF). **Confidence**: high. **Classification**: behavioral
(including the previous-line dot-overflow carry — it is state, not timing).
**Open remainder**: VDP revision differences — none documented, *nothing to pin*; the
mid-line display-disable pixel-budget cut (~120–128 px, TascoDLX — Mickey Mania's 3D level) —
*defer, timing-adjacent, Phase 3 slot territory*.

## R11 — Shadow/highlight resolution table (§3 pipeline step 6)

**PINNED — full table** (official manual + Sik t=2692 + Plutiedev + Mask of Destiny t=2561,
all in agreement):

Three per-pixel states: **highlight / normal / shadow**.

1. **Default state**: if the priority bits of *both* A and B are 0 at the dot → **shadow**
   (the backdrop is shadowed too). If any plane's priority bit is 1 → **normal**.
   **Transparent plane pixels still contribute their tile's priority bit** (the Bloodlines/
   Ranger-X light-ray trick); **transparent sprite pixels do not.**
2. **Sprite pixels**: an opaque non-operator sprite pixel is shadowed only if the sprite is
   low-priority AND both planes are low-priority; a high-priority sprite pixel is never
   shadowed. **Quirk**: a sprite pixel with color index 14 of *any* palette is never shadowed
   (always normal); planes render color 14 normally.
3. **Operators** (sprite pixels, palette 3 only): color 14 = highlight, color 15 = shadow.
   The operator pixel is **not displayed**; it shifts the underlying pixel one step:
   normal+highlight = highlight; normal+shadow = shadow; **shadow+highlight = normal**
   (undoes); shadow+shadow = shadow (no double-shadow). The operator must itself be the
   winning sprite-layer pixel to take effect; plane resolution beneath is unchanged.
4. **Sprite-to-sprite**: operators behave as opaque pixels inside the sprite line buffer
   (overwriting lower sprites); the operator semantics apply only against the background
   layers afterward (Mask of Destiny — the sprite layer is flattened first).
5. **Intensity ramps** (official chart): normal = codes 0–7 Min→Max; shadow = Min→½Max;
   highlight = ½Max→Max.

**Evidence**: Sega Genesis Software Manual §L/§M pp.61–68 (state diagrams incl. backdrop
shading, operator non-display, the CRAM palette-3 carve-out, the RGB ramp chart; noted manual
typo: the Code-14 page's body text says "Code 15"); Sik SpritesMind t=2692 (the state
algebra, verbatim); flamewing/TmEE same thread (the color-14 never-shadowed quirk, sprites
only); Plutiedev shadow-highlight; Mask of Destiny t=2561 (line-buffer flattening).
**Confidence**: high. **Classification**: behavioral (pure per-pixel resolution).
**Open remainder**: measured DAC output levels (SpritesMind t=2188 has them — fetch if
calibrated RGB is ever needed; our introspection API reports CRAM values + our fixed ramp,
so nothing blocks) — *defer, rendering calibration*; operator under an opaque high-priority
plane pixel (the "visible layer" reading says no effect — high confidence) — *pin as
no-effect, flag for the attribution proptests*; backdrop color = palette 3 entry 14/15 and
S/H × debug register — *defer, exotic cells for the Phase-3 ledger*.

## The pending-toggle experiment (R1's open cell) — recorded result

`tools/blastem-differential/vdp_pending.asm` + `run_vdp_pending.py` (BlastEm 0.6.2 as
black-box instrument over its GDB-RSP stub; fresh session per cell; method in the file
headers — an ambiguous control word routes a $BBBB sentinel to VRAM $0200 if the toggle
survived the probe, or $0300 if the probe cleared it).

```
sel=0 control (no probe) -> $0200=BBBB $0300=2222 | pending PERSISTS (validates discriminator)
sel=1 status read        -> $0200=1111 $0300=BBBB | status read CLEARS the toggle
sel=2 HV counter read    -> $0200=BBBB $0300=2222 | HV read does NOT clear it
sel=3 data-port write    -> $0200=CCCC $0300=BBBB | data write CLEARS it (Kabuto confirmed)
```

All cells completed (`$C0DE` done marker, `$0100=AAAA` sentinel intact). Interpretation:

- **sel 0** proves the method: with no probe, the ambiguous `$4300` was consumed as a second
  word and the write landed at the armed `$0200`.
- **sel 1** is the new pin: after a status read, `$4300` was interpreted as a *first* word
  (arming `$0300`), so the status read had cleared the first-write state. This matches the
  widespread community idiom (defensive `move.w (VDP_control).l,d0` before command setup in
  Sonic-era code) that permitted documentation could not confirm. **Instrument-sourced pin**
  (BlastEm 0.6.2), per the STOP×trace precedent: recorded here + carried into the design
  brief; revisit only if a better oracle (hardware test ROM) contradicts.
- **sel 2**: the HV-counter port is not a control-port access — the toggle survives.
- **sel 3**: data-port writes clear the toggle — the doc-pinned Kabuto rule, now
  experiment-confirmed (and the probe write itself landed at the live half-updated address
  `$0200`, confirming the no-latch model).
