## CR-21 — `emulator/write_memory` — ADOPT WITH CHANGES

**R1. The proposed row names a `len` param that does not exist.** The row says `len` ≤
`limits.maxWriteLen` in the params column, but the fragment has no `len` param — correctly, since a
write's length derives from its payload. Row and fragment contradict; D14 resolves by schema, making
the row text a standing spec bug on day one. Replace the row with:

```markdown
| `emulator/write_memory` ← `write` | `addr`\|`symbol`; `bytes`\|(`value`+`width` 1\|2\|4); payload ≤ `limits.maxWriteLen` bytes | `addr`, `len` |
```

and add to the prose one sentence naming the over-cap refusal, which the CR nowhere gives a code:
*"A payload longer than `limits.maxWriteLen` bytes is `-32602` — refused, never truncated."*

**R2. "exactly the window `read`'s `bus` space serves" is false.** Per §11.12 (protocol.md:845-846 /
schema read.len), read's bus space is 24-bit and serves cartridge ROM as well (region "cartridge
ROM"). What serves exactly $E00000–$FFFFFF is the work-RAM branch of the bus read
(engine.rs:975-986), not the bus space. Replace the parenthetical with: *"(mirror-masked — the same
window `read` reports as region \"work RAM\")"*. Leaving it as written lets a second implementer
conclude read's bus space is also confined to that window, contradicting §11.12.

**R3. Param constraints must be mechanical, not $comment-borne.** The fragment as proposed accepts
`{}` and accepts bytes+value together, while four refusal combinations live only in prose. House rule
(schema watchpoint_add $comment: "enforced mechanically in both directions rather than left to
prose… D14 makes the schema the authority on which keys may appear together"; errorResponse's if/then
gives the same reason). Add to params:

```json
"oneOf": [{ "required": ["addr"] }, { "required": ["symbol"] }],
"allOf": [
  { "oneOf": [{ "required": ["bytes"] }, { "required": ["value"] }] },
  { "dependentRequired": { "value": ["width"], "width": ["value"] } }
]
```

This mechanically encodes all four prose refusals (both, neither, width-with-bytes,
value-sans-width) and the addr/symbol alternative that read_memory, run_to, lookup_symbol and
watchpoint_add already enforce. (emulator/read's fragment lacking the addr/symbol oneOf is an
existing gap in §11.12's fragment, not a license.)

**R4. Placement: not a sixth bullet under emulator/read.** The read blockquote opens "Five things
are normative" (protocol.md:831) then lists five bullets; appending a write_memory bullet would make
that sentence false in place. The write_memory entry must be its OWN blockquote block (after the
read/alias block, before or after the z80_read/z80_write rows), not a list item inside read's.

**R5. Pin the watch-surface interaction.** A poke that "travels the bus path" raises a question the
CR never answers: does it match armed watchpoints? Two conformant servers could observably differ —
precisely the split the state rule's closing sentence exists to prevent. Structural answer: a hit's
`pc` is "the instruction that drove the access" (schema watchpoint_hits), and a poke has no driving
instruction — any pc stamped on it would be the invented value D11 bans. Add to the prose: *"A poke
is a debugger access, not a guest access: it is never offered to the watch surface — no watch
matches it, and `watchpoint_hits.seen` does not move — because a hit's `pc` names the instruction
that drove the access and a poke has none to name."*

**R6. limits.maxWriteLen must match siblings and be tied to the method.** Every existing limits key
carries `"minimum": 1`; add it. Add to its description (mirror in maxHashLen): *"REQUIRED when the
server advertises `emulator/write_memory`"* — the limits object's own argument ("a client has no
other way to discover that number, and discovering it by being refused is discovering it too late")
applies with full force to a brand-new bound.

**Recommendations:** (a) tighten bytes to pattern `"^0x([0-9A-Fa-f]{2})+$"` — also refuses
empty/odd payloads for free. (b) value-fits-width as if/thens on width — worth doing, not blocking.
(c) result caveat declared with no nameable condition; name one or follow sprites' shape ("declared
absent, not omitted by accident") and drop it.

**Factual corrections:** (i) "the exact gap CR-4 closed for run_to" — wrong precedent. CR-4
(register :231) is D12's unbounded-wait gap, not "a bound with no error code and no refuse-vs-clip
rule." Correct precedents for refuse-not-clip: §2.1's limits rule ("REFUSES above it rather than
clamping (§5)") and §11.12's refused-never-clipped; drop the CR-4 cite. (ii) Anchor nit: the
run-control state rule is :793-801; :803-805 is the separate reached/deadlineReached note.

## CR-22 — `emulator/reset` — ADOPT WITH CHANGES

**R1. The definition of `deferred` must be rewritten, and the Oracle claim corrected.**

The factual error: the CR says "Oracle's threading forces `true` in its normal path (:492) because
the reset drains on the GUI thread after the reply is composed." The code says the opposite: OpReset
queues the request (:477), then busy-waits up to 5 seconds for pendingReset->done (:479-486), which
main_gui.cpp:2057-2061 sets only after doFullReset has run — and only then composes the
deferred:true reply (:492). In Oracle's main path the reset is COMPLETE before the reply. Under the
proposed definition Oracle's honest answer would be false; its shipping true is a MECHANISM report
(which thread applied it), not a WHEN report. The CR's claim that this definition is "the only
definition under which both shipping behaviours are legal" is therefore wrong — it legalizes ours
and makes Oracle's emission untruthful. That does not block adoption (Oracle is already
non-conformant per D11/§8, "a legacy peer that no longer claims conformance", protocol.md:1432-1438),
but the CR must say so instead of claiming the opposite. (The false-at-:469 gloss is also shaky: the
fallback path calls FlagInitialize(), which flags a reset the system applies on its next cycle —
"applied inline before the reply" is an interpretation, not what the code shows.)

The ambiguity: "queued for the next frame boundary" — on this bus a frame is the EMULATED frame
(D11: "never a UI frame counter"). A paused machine advances no emulated frames, so one server reads
"a reset queued while paused never lands," another reads "host loop tick," both conforming. Replace
the prose's deferred sentences (and the fragment description to match) with:

> "`deferred` reports *when* the reset landed relative to this reply — `false`: it was applied
> before this reply was composed, and every subsequent read on any connection sees the post-reset
> machine; `true`: the server accepted it and handed it to the thread that owns the machine without
> waiting for completion. A deferred reset MUST be applied within a bounded time regardless of run
> state — a server that cannot bound it answers `-32010` instead of `true` — and a client that
> needs it visible polls `status` until the stamp's `mclk` has restarted. A server that hands the
> reset off and then waits for completion before replying answers `false`: the key reports when it
> landed, never which thread applied it."

**R2. Pin the post-reset run state.** The CR is silent on whether a paused machine stays paused —
and the shipping reference disagrees with the obvious answer: OpReset takes a `run` param (default
true → resume; resetStayPaused = !run, :476), so Oracle's default reset RESUMES a paused machine.
Observable in every subsequent stamp's `running`, so two servers could conformantly differ. Add:

> "`reset` MUST NOT change the machine's run state: a paused machine is paused at the reset vector,
> a free-running machine keeps running from it — §5's ban on implicit mode changes, applied here.
> (The legacy socket's `run` param, which resumes by default, is deliberately not adopted: that
> composition is `reset` + `resume`.)"

**R3. Replace the "checkpoint methods' reason" citation with the reason itself.** The contract
contains NO statement that checkpoint methods are exempt from the state rule — that ruling lives
only in an engine.rs comment (:2018-2029), i.e. a server implementation. A contract sentence must
not lean on a reason a contract reader cannot find. Rewrite the opening of the prose:

> "Deliberately **not** subject to the state rule above, and a server MUST NOT refuse it with
> `-32005` on a free-running machine: it advances nothing and replaces state wholesale between
> frames, so it cannot fight the free-run loop for the machine, and gating it would force the
> pause-call-resume dance §5 forbids resolving implicitly."

**Recommendations:** (a) state the held-pads rationale (cold-start determinism for scene preambles;
the debugger's injected state is not the machine's) — as written it invites the hardware analogy it
breaks. (b) note a deferred:true reply's own stamp is pre-reset. (c) consider registering or
explicitly deferring a pushed event for reset.

**Factual corrections (quote → truth):** "the reset drains on the GUI thread after the reply is
composed" → the reply is composed only after the drain: ControlSocket.cpp:479-486 waits on done, set
at main_gui.cpp:2061 after doFullReset; timeout returns an ERROR, not deferred:true. "queued and
drained… with a 5-second deadline" is right as mechanism; the inference drawn is wrong. Pin 5's
"checkpoint-block precedent" is an implementation comment, not contract text (see R3).

## CR-23 — `emulator/memory_hash` — ADOPT WITH CHANGES

**R1. Write the routing rule out; drop the "exactly as read's bus space" equivalence.** Same defect
as CR-21 R2, plus "-32004 past the end" does not say past the end of WHAT — region or space. Replace
the routing sentence with:

> "The base (or resolved symbol) must land in one of two regions: work RAM (`$E00000–$FFFFFF`,
> mirror-masked) or cartridge ROM (`$000000` up to `romBytes`), and the range must not run past
> that region's last byte. A base in neither region, or a range whose end crosses out of its
> region, is `-32004` — refused, never wrapped or clamped. `region` names which of the two
> answered, with `read_memory.region`'s spellings."

If the shared-rule ambition of pin 7 is wanted, state it as a named rule beside the memory table and
cite it — but do not assert an equivalence to `read` the contract does not contain.

**R2. Actually pin the FNV algorithm — CR-20's condition is otherwise not discharged.** CR-20's
ruling: "the algorithm must be pinned as state_hash's is, since cross-server comparability is its
whole point." `$defs/hash64` says only "a 64-bit FNV-1a fingerprint" — width and family, not the
function. CRC-32 is fully pinned (naming zlib fixes polynomial, init, reflection, final xor); FNV is
not. Add to the prose (or $defs/hash64, amended together per D14):

> "`fnv1a64` is FNV-1a with 64-bit parameters — offset basis `0xCBF29CE484222325`, prime
> `0x100000001B3` — folded over the range's bytes in ascending address order."

Without this, two servers can both emit "FNV-1a 64" and never match.

**R3. Mechanical addr|symbol.** Add `"oneOf": [{ "required": ["addr"] }, { "required": ["symbol"] }]`
to params; as proposed, `{"len": 1}` alone validates.

**R4. limits.maxHashLen: add `"minimum": 1` and the REQUIRED-when-advertised sentence**, per CR-21
R6.

**Recommendations:** (a) use the house "a server MUST NOT refuse it on a free-running machine,
exactly as `read` is" spelling. (b) add one sentence that the sample is taken at a single coherent
machine point (engine-thread, between frames) — a torn hash is a plausible-looking wrong
fingerprint, the worst kind. (c) caveat: name the condition or drop it (sprites precedent).
(d) standalone blockquote block, per CR-21 R4.

**Factual corrections:** none — CR-23's evidence is clean end to end. Its one weakness is the
discharge claim ("both algorithms pinned") — a reasoning gap, not a false quote.
