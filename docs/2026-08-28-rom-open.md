# Opening a ROM from inside the player — and why the drag-and-drop half is a different parcel

**Date:** 2026-08-28 · **By:** oracle overseer, implementing directly · **Branch:** `parcel/rom-open`

## 0. Why this was written by the overseer rather than dispatched

The owner asked for it in this session (*"Is there a way to load the rom in the program or only through
cli?"* → *"Yes please, both"*). **This session's configuration forbids calling the Agent tool unless the
owner asks for it**, and a feature request is not that ask — treating it as one is the
permission-laundering line this lane has already recorded once (`docs/2026-08-27-obj-join-recon.md` §0).
So the orchestrate-don't-implement norm yields to his explicit instruction, exactly as it did there, and
the work was done here. Recorded because a later reader will otherwise see the seat implementing and read
it as drift.

## 1. What was true before

**The player took its ROM from `argv` and from nowhere else.** Verified firsthand rather than assumed:

* `main.rs:333` parses the argument; `:869` reads it; the usage line names no other route.
* **F5 re-reads the *same* path** (`commands.rs` binds `Cmd::ReloadRom`; the arm read `args.rom_path`).
  It is built for the rebuild loop and is careful — reads before touching the machine, aborts on an
  unflushable `.srm`, re-derives the save-state fingerprint, re-validates the `.lst`. It cannot point
  somewhere else.
* **A bus client could always do what the person at the keyboard could not**: `emulator/reload_rom` takes
  a `path` and swaps the cartridge (`engine.rs:4612`), and the window follows it (`main.rs`'s
  `pumped.rom_changed` branch).

So the asymmetry was the finding: **the tools could change his ROM and he could not.**

## 2. What this parcel adds

**"Open ROM..." — `O`, and in the palette's GAME group.** It opens the folder the running image came from
as a pick list: `../` first, then subdirectories, then `.bin`/`.md`/`.gen`/`.smd` images, each group sorted
case-insensitively, with the loaded image marked `[loaded]`. Enter on a directory descends; Enter on an
image swaps the cartridge. It is the same [`Picker`](../crates/oracle-frontend/src/palette.rs) the
save-slot list already uses.

⚠ **A claim in the first draft of this document was wrong, and catching it changed the parcel.** I wrote
that "the palette's existing typed filtering works on it for free". **It does not.** The picker's input
arm was `PaletteKey::Char(_) | PaletteKey::Backspace => {}` — typing was swallowed outright — and the
picker's draw loop had no scroll, so it painted rows until it ran out of panel and stopped. With two save
slots nobody noticed; over a *folder*, that is a surface that looks like a search box, is not one, and
hides rows the selection can still walk onto invisibly. So the picker gained a filter of its own (§2.2).
*Recorded because the claim was already written down as a finished fact, and the only thing that caught it
was going back to read the function rather than the sentence.*

### 2.2 The picker is now typeable, and that is a shared surface

`Picker` gains its own `query` (separate from the palette's, which belongs to the command list behind it),
a `visible()` filter over the existing `subseq_match`, a query line, and the same scroll-to-selection the
command list already had. **`sel` now indexes the VISIBLE list**, and the one place that must convert back
is Enter.

That conversion is the whole risk and is what the new tests aim at: with a filter applied, `sel = 0` means
*the first row on screen*, and an implementation that indexed `items` directly would run row 0 of the
**unfiltered** list — a different game, chosen silently, with the right row highlighted. The empty-filter
case is asserted too: Enter with nothing matching does **nothing**, rather than running the row the user
just filtered away.

The save-slot picker inherits the filter. That is a deliberate widening, not a side effect: ten slots is
already more than fits comfortably, and two pick lists that answer the same keystrokes differently is worse
than both being typeable.

**Deliberately not a native file dialog.** `rfd` would pull a GTK/portal dependency tree into a frontend
whose dependency list is kept deliberately small, needs a portal present at runtime, and — the argument
that decided it — **a native dialog is untestable by construction**, while the model below is covered
headless with four tests and four recorded mutations. The palette already owned typed filtering, a
selection model and a pick list; the cheaper option was also the better-behaved one.

### 2.1 The part that is not the feature, and matters more

**F5 and "Open ROM" are now ONE swap block with two entry points** (`main.rs`, after the dispatch loop),
because they are the same delicate sequence and two copies would drift into two half-correct ones. The
entry points set `pending_rom`; the block does the work.

Three things follow, and the third is a **pre-existing defect this feature would otherwise have made
reachable by a person**:

1. The early exits had to stop being `continue`. In the arm this grew out of, `continue` skipped to the
   next command — harmless. Out here the same word would skip presenting, input and audio for the whole
   iteration, so **a failed reload would freeze the window instead of printing why**. It is a labelled
   block and `break 'swap`.
2. The `.srm` is flushed against the **outgoing** path, before anything is re-derived: that data belongs
   to the game being put away.
3. **`rom_path` is now a variable, and every path keyed to it moves with it** — `srm_path`,
   `slots_on_disk`, the `.lst`, and the bus's `MachineInfo`. Before this parcel they were all computed
   once from `args.rom_path` and never revisited.

⚠ **The registered consequence: this was already wrong for a bus-driven swap, and still is.** A client
calling `emulator/reload_rom {path}` on a hosted window changes the cartridge; the frontend's
`pumped.rom_changed` branch re-keys the save-state fingerprint and **nothing else**. So after a
bus-driven swap the window still flushes battery data to the *previous* game's `.srm`, still probes the
previous game's save slots, and F5 still reloads the previous game. **Not fixed here** — closing it needs
a `Bus::rom_path()` accessor that does not exist (`bus.rs` has no getter for the engine's current path;
`bus_stub.rs` would need a matching no-op), and this parcel had no business growing a bus surface.
**Registered as F-BUSSWAP-PATHS**, revival condition: before any consumer is told it may swap a hosted
window's cartridge. *Found while reading for this feature, reported before it was asked about.*

## 3. What was verified, firsthand, with real exit codes

Shell note: this workspace's shell is zsh, where **`${PIPESTATUS[0]}` is empty** — the array is
`$pipestatus[1]`. A first attempt printed `EXIT=` and could have been read as a clean run. Every figure
below comes from `$?` on an unpiped command writing to a log.

| gate | result |
|---|---|
| `cargo fmt --all --check` | **exit 0** |
| `cargo clippy --workspace --all-targets` | **exit 0**, `grep -cE "^warning\|^error"` = **0** |
| full aggregate, final tree | **exit 0** — `LEGS=58 PASSED=1946 FAILED=0 IGNORED=6` |

**Accounting for the +6, stated as arithmetic rather than as a second measurement.** An intermediate
aggregate on the tree *before* the picker-filter work read `58/1944/0/6`, and that run already contained
the four `rom_browser` tests, so the pre-parcel baseline is **1940** by subtraction. 1940 + 4 (browser)
+ 2 (picker filter) = **1946**, and the leg count is unchanged at 58 because both files are test modules
inside the existing frontend binary rather than new legs. *The 1940 is derived, not run — no aggregate was
taken on `main` itself.*

**All four new tests appear by name in their own run's log** — `rom_browser::tests::{scan_lists_parent_
then_dirs_then_roms_each_sorted, scan_reports_the_directory_error_rather_than_an_empty_listing,
picker_label_marks_only_the_loaded_image_by_path, rom_extensions_are_case_insensitive_and_bounded}` — not
merely "the suite was green", per the bar that a green log and an absent run are the same artifact.

### 3.1 Mutations, all four recorded, all reverted and the revert verified by `diff -q`

| mutation | the assertion that fired |
|---|---|
| sort case-**sensitively** | `left: [.., "Beta.GEN", "alpha.bin", ..]` vs `right: [.., "alpha.bin", "Beta.GEN", ..]` |
| swallow the `read_dir` error → `Ok(vec![])` | `assertion failed: scan(&missing).is_err()` |
| mark `[loaded]` by **file name** instead of path | `left: "s4.bin   [loaded]"` / `right: "s4.bin"` |
| widen `ROM_EXTS` to include `lst` | `assertion failed: !is_rom(Path::new("s4.lst"))` (and the ordering row) |
| Enter indexes `items` directly instead of resolving through `visible()` | **both** picker rows: `left: Run(SlotSelect(0))` against `right: Run(SlotSelect(2))`, and `left: Run(SlotSelect(0))` against `right: None` |

The last one is the parcel's most important mutation, because its defect is **silent**: the highlighted
row is correct, Enter is pressed, and a *different* cartridge loads. Nothing on screen contradicts it.

The first fixture is **created out of alphabetical order on purpose**: one built in the answer's order
would have passed with the sort deleted.

The third mutation is the one worth keeping. Marking by file name looks equivalent and is not: two folders
in this workspace hold an `s4.bin`, and a picker that marks the wrong one as `[loaded]` tells the user the
game they are looking at is already running when it is not.

### 3.2 A test of mine was wrong against correct code, and the reason generalises

The first draft of `picker_filters_on_typed_text_and_enter_runs_the_row_on_screen` typed `"gam"`, then
`"mma"`, and asserted the result still matched `gamma.bin`. It does not. `commands::subseq_match`
**consumes** its title iterator as it goes (`let mut t = …; query.all(|q| t.any(|c| c == q))`), so it is a
true subsequence test: `"gammma"` runs out of `m`s before `gamma.bin` does. The filter was right and the
test was wrong.

**The prediction was made from source and then confirmed by execution, from a different direction.** The
reading said this one test would fail; the aggregate then in flight came back `FAILED=1` naming exactly
`palette::tests::picker_filters_on_typed_text_and_enter_runs_the_row_on_screen` and nothing else. Two
derivations that could not share a parameter — one read four lines of a helper, the other ran the binary —
which is the corroboration test rather than the echo one.

Worth recording because of *how* it was caught: not by running it, but by reading the helper's four lines
when the assertion looked too convenient. I had used `subseq_match` as though I knew what it did — the
same "derived, never copied" failure this repo books against expectations, arriving in a **test's own
setup**, which is the half nobody re-derives. The corrected test now says the consuming behaviour out loud
so the next person editing the query strings does not rediscover it.

## 4. ⚑ THE DRAG-AND-DROP HALF — MEASURED, AND IT IS NOT A CALLBACK

He asked for a dialog **and** drag-and-drop. The dialog half shipped. The drop half did not, and the
reason is a property of the window toolkit rather than a judgement about scope.

* **minifb 0.28 has no file-drop support of any kind.** Grepped its `lib.rs`: the only `drop`/`drag`
  matches are `target_os = "dragonfly"` and a cursor-shape doc comment. There is no drop event to handle.
* **The owner's desktop is Wayland** (`XDG_SESSION_TYPE=wayland`, `WAYLAND_DISPLAY=wayland-0`), and his
  player (pid 3614020, `target/release/oracle-frontend .../aeon/s4.debug.bin`) carries no `--x11`, so it
  is a **native Wayland surface** — minifb tries Wayland first and only falls back to X11 when the connect
  fails (`icon.rs`'s module docs, measured previously for the icon).
* So it is two implementations, not one: **X11 wants hand-rolled XDND** (reachable — we already depend on
  `x11-dl` and `icon.rs` sets the precedent of reaching minifb's raw handle), and **Wayland wants our own
  `wl_data_device`** bound on minifb's own `wl_display`, on our own event queue, plus a new dependency.
  minifb exposes both handles (`WaylandWindowHandle`/`WaylandDisplayHandle` at `wayland.rs:1260-1286`), so
  it is not impossible — it is a parcel, and the half that applies to his machine is the harder one.

**Recommendation: do not build it on this parcel's back.** Filed as decision `d-18` with a cheaper middle
option — accepting a **pasted path** in the picker's query line, which is what most people reach for
drag-and-drop to accomplish, and which costs ~20 lines on both backends.

*Stated against my own recommendation: he asked for both, and this defers half of what he asked for. It is
deferred with a measurement and a decision card rather than quietly dropped, and the picker does not depend
on it.*

## 5. ⟨RUNTIME⟩ — what has NOT been done

**Nothing in this parcel has touched a running window.** Everything above is `cargo test`; the browser's
model is covered headless and the swap block is not covered at all. Per this repo's own bar — *a merged
serve is not a served method; spawn the consumer's own path and call it* — the foreground pass owed is:
launch a lane-owned player on a scratch ROM folder, press `O`, descend and come back through `../`, open a
different image, and confirm (a) the `.srm` and save slots follow the new cartridge, (b) the `[loaded]`
marker survives the round trip through `../`, and (c) an unreadable folder leaves the previous listing up.
**Not to be aimed at the owner's window**, which is running his own build.
