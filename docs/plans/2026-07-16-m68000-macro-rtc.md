## 1. Goal and the invariants that bound it

Policy 7: the macro-inlined run-to-completion fast path is the ratified escape hatch from the
cycle-granularity addendum (the interpreter's data-driven representation is not best-in-class on the
hot loop). Its acceptance gate is fixed: **the existing both-drivers equivalence harness over the
full SST sweep — identical final state + per-cycle transaction stream + cycles — threshold
`ran >= 1_000_058`, never weakened.**

Three hard invariants shape every option below:

1. **Single definition.** Recipes stay the *one* definition of behavior. Any fast path is **derived**
   from them, never a second hand-written implementation. (Two bodies that must agree = the exact
   divergence-surface the single-definition hybrid was chosen to abolish.)
2. **Recipes are not cacheable per opcode.** They bake decode-time state — live CCR for
   Bcc/Scc/DBcc/TRAPV, the MOVEM mask, live `Dn` for shift counts / bit numbers. `decode(&regs)` runs
   at *every* instruction boundary. A design that memoises "opcode → compiled trace" is wrong.
3. **The gate is sacred.** SST threshold `ran >= 1_000_058`; `export_state` v1 layout frozen
   (`tests/export_state_v1.rs`); Oracle `state_hash` untouched; clean-room held.

## 2. Recon — a fresh baseline (measure before designing)

The addendum's "~5.4× slower than the hand-written atomic baseline" is a **June figure, pre-pivot**:
it measured **ADD.w only**, with `MAX_OPS = 20` and a smaller vocabulary, and against a
`step_instruction`/`prototype.rs` baseline that **no longer exists** (deleted in Push B). It cannot be
reproduced and must not be quoted forward. So this pass starts from a new instrument.

**Instrument:** `crates/oracle-core/examples/microop_perf.rs` (committed with this push). It runs the
**vendored SingleStepTests corpus** — the exact opcode/addressing/data distribution the fast path must
reproduce — through the real `decode` + `run_to_completion`, over a non-logging flat bus (`FlatBus`'s
per-access `Vec` logging is System-side instrumentation, not CPU cost, and would swamp the signal).
Three phases isolate where the time goes. A "COMMON" mix weights MOVE / arithmetic / compare / logic /
branch / address (what dominates real Sonic-era code); a "HEAVY" mix (MUL/DIV/MOVEM) bounds the tail.

**Baseline (release, this machine, COMMON mix, 70k–105k cases; figures stable across cap sizes):**

| Phase | ns/instr | Note |
|---|---|---:|
| decode-only (`decode(&regs)`) | **~42** | opcode dispatch + building the `[MicroOp; 40]` recipe |
| exec-only (RTC over a pre-decoded template) | ~70 | includes a 532 B template clone the real path skips |
| **full (decode + RTC)** | **~90** | **≈ 11.1 M instr/s** — the real per-instruction cost |

**Structural facts (probed):** `size_of::<MicroOp>() = 12`, `size_of::<MicroState>() = 532`
(a `[MicroOp; 40]` array = 480 B, + scratch `[u32; 10]` + cursor/flags), `MAX_OPS = 40` (MOVEM.l).

**The three findings that re-shape the pass:**

- **F1 — cost is ~half decode, ~half execute.** Decode-only is ~47 % of the full 90 ns. The addendum's
  premise ("run-to-completion inlines to near-atomic speed; the cost is per-operand symbolic
  resolution in *execution*") is now only *half* the story. **Recipe *materialization* — building a
  532-byte struct per instruction — is the other half**, and it grew when `MAX_OPS` went 20→40.
- **F2 — the recipe op-array was double-buffered.** `RecipeBuf::finish(&self)` called
  `MicroState::from_ops(self.as_ops())`, so the 480-byte `[MicroOp; 40]` array was constructed **twice**
  per decode (once in `RecipeBuf::new`, once in `from_ops`) plus a slice `copy_from_slice`. This is pure
  waste — a materialization cost with no behavioral role.
- **F3 — the interpreter floor is "build a 532 B struct + walk ~7 ops."** With no clone in the real
  path, the production hot loop is one `MicroState` construction + a symbolic walk. To go *materially*
  below this floor you must **not build the struct at all** — which is precisely the codegen escape
  hatch (straight-line effects, no array), and precisely why it is a large change.

Verified fix for F2 (this push): make `RecipeBuf::finish(self)` **move** its already-built array into
the `MicroState` (new `MicroState::from_buf(ops, len)`), constructing the array exactly once.

| | decode-only | full | throughput |
|---|---:|---:|---:|
| before (double-buffer) | 41.6 ns | 90.1 ns | 11.1 M/s |
| after (build once) | **32.5 ns** | **79.1 ns** | **12.6 M/s** |

−22 % decode, **−12 % end-to-end**, byte-identical behavior (423 lib green; SST gate below). No recipe,
vocabulary, or `MicroOp`/`MicroState` layout change — single definition trivially preserved.

## 3. The design space, against the invariants

The question is *how* a fast path can be faster than "loop `exec_one` over a built `MicroState`" while
staying **derived** from the one recipe definition and **non-cacheable**.

- **(A) Optimise recipe materialization** — build the array once (F2), and later shrink/streamline it
  (a top-nibble decode dispatch table; packing `MicroOp` 12→8 B). *Pure representation.* Preserves
  single-definition trivially (recipes unchanged; only the plumbing that materializes/walks them
  changes). Bounded, safe, SST-gated. **Ceiling: the F3 floor** — it makes building-and-walking
  cheaper, but you still build and walk. Realistic aggregate: ~1.5–1.8× over today.
- **(B) The codegen escape hatch** — the ratified path. A macro consumes the *one* recipe definition
  and emits **both** (1) the data recipe (for the quiesce/step driver + snapshots) and (2) a
  straight-line RTC executor that performs the reads/ALU/writes inline, **building no array and doing
  no symbolic operand resolution**. This is the only thing that beats the F3 floor (the addendum's
  17-line `step_instruction` is an example of the straight-line code such a macro emits). It kills
  *both* halves (F1) at once. Single-definition holds **because both artifacts come from one source**;
  non-cacheable holds because the executor still dispatches on `opcode` + reads live decode-time state
  at the boundary (it is decode-inlined, not decode-cached).
- **(C) Per-opcode cached compilation** — a JIT/trace cache keyed by opcode. **Rejected**: violates
  invariant 2 (recipes bake decode-time state), and complexity is unjustified when each instruction
  decodes+executes exactly once (nothing to amortise within an instruction).

**The catch with (B):** it requires the recipe to exist in a form a macro can consume — a *declarative*
recipe substrate. Today the ~50 families are **imperative Rust builders** (`decode.rs` 15 k lines +
`ea.rs` 2.7 k lines: `buf.push(MicroOp::…)` interleaved with decode-time `if`/loops, the table-driven
`SrcSeq`/`DstSeq` EA machinery, and one-off mechanisms — MUL/DIV self-booking cycles, the
address-error in-flight rewrite, MOVEM mask expansion, DIVU/DIVS `[idle, prefetch]` reordering). A
macro cannot mechanically transform arbitrary imperative Rust. **Standing up (B) is a per-family
migration to a declarative DSL — a multi-push grind comparable in size to the coverage grind, with
real single-definition risk *during* the transition** (each family briefly has a hand-shape until the
macro subsumes it; the both-drivers+SST gate is the safety net, but the churn is large).

## 4. ROI framing (the fact that should drive the owner decision)

The cycle-granularity addendum already recorded the load-bearing point: *"the interpreter still does
~45 M ADD.w/s (~60× real-time), fine for MVP-debuggable and for differential testing (BlastEm, the
accuracy oracle, runs ~50× real-time and **is the bottleneck**)."*

So:
- **The BlastEm differential fleet does *not* benefit from the codegen** — BlastEm bottlenecks it. The
  interpreter at ~12 M instr/s (~16× real-time for the CPU alone) is already far past BlastEm's pace.
- **The codegen's real prize is pure-oracle-next N-instance / headless throughput** (many oracle-next
  copies, no BlastEm), where wall-clock scales ~linearly with CPU throughput. There, best-in-class
  (~5–8×) is worth real money.

Policy 7 places the pass "before the differential fleet / N-instance workloads." The measurements say:
the *differential* half of that never needed it; the *N-instance* half does — but only once an
N-instance workload actually exists and demonstrates a throughput wall.

## 5. The plan: staged, with the codegen bet surfaced

### Push P1 — recipe materialization (THIS push, gated)

The safe, universal, single-definition-trivial win, measured end-to-end:

- **P1.1 (instrument):** commit `examples/microop_perf.rs` — the reusable throughput harness (SKIPs
  cleanly without the vendored corpus, so it never breaks a fetch-less build). Every future perf slice
  measures against it.
- **P1.2 (fix F2):** `RecipeBuf::finish(self)` moves its op array into `MicroState::from_buf`; the
  recipe's `[MicroOp; 40]` array is constructed exactly once per decode. Behavior byte-identical.

**Gate:** fmt-clean per commit; `clippy --all-targets -D warnings`; determinism gate + proptests +
`tests/export_state_v1.rs` golden; **full workspace incl the SST sweep `ran >= 1_000_058`** (both
drivers + per-cycle transactions + snapshot/restore — the acceptance gate proves the fast-path change
did not perturb a single case). Result recorded in `phase0-status`.

### Push P1b — bounded safe interpreter optimizations (designed; future, still option A)

If the owner's call (§6) is "interpreter optimization is enough for now," these are the next safe,
SST-gated slices, each measured on the P1 harness before/after, each preserving single definition:

- **Top-nibble decode dispatch table.** `decode_dispatch` is today a linear chain of `is_*(opcode)`
  predicates; a jump on `opcode >> 12` cuts the late-family cost. **Care:** the chain encodes
  ordering-as-correctness (e.g. `cmp_class` before the EOR arm; privilege gate first) — the table must
  preserve every intra-nibble ordering constraint. SST + the 65 536-opcode totality sweep are the net.
- **Pack `MicroOp` 12→8 B** (if achievable without semantic loss): a 40-slot array drops 480→320 B,
  making construct + walk ~⅓ cheaper. **Care:** `Operand` needs a discriminant + `u8` payload (≥ 2 B),
  so this is a layout study, not a given; do only if the size actually falls and SST stays green.

Estimated aggregate for P1+P1b: ~1.5–1.8× over today's baseline (~18–20 M instr/s), at low risk.

### Push P2… — the codegen escape hatch (designed; **owner-gated** — the decision in §6)

The ratified path (option B). Design shape, so the owner can evaluate concretely:

1. **Declarative recipe substrate.** Express each family's recipe once in a macro DSL that captures the
   op sequence *and* the decode-time parameterization (register/size/immediate/condition), rich enough
   to cover today's mechanisms (self-booking cycles, the in-flight abort rewrite, mask expansion).
2. **The macro emits two artifacts** from that one source: the `RecipeBuf` builder (drives the
   interpreter + the step/quiesce driver + snapshots — unchanged consumers) and a straight-line
   `run_fast(&mut regs, bus, params)` executor (no array, no symbolic resolve).
3. **A third driver** (`step_fast`) in the SST harness, checked in `run_case` alongside driver 1 (RTC)
   and driver 2 (step) — identical final state + transaction stream + cycles, per case. This *is* the
   policy-7 acceptance gate; it makes the derivation provable, not asserted.
4. **First gate = a single-family prototype** (e.g. the arith `<ea>,Dn` shape) migrated to the DSL with
   its `run_fast` green across the family's full SST file, measured on the P1 harness. Only after that
   proves the DSL + macro + third-driver gate does the per-family grind proceed.

**This is a multi-push grind with single-definition risk during migration; committing to it is an
architecture bet, not a grind default.** Hence §6.

## 6. The decision to surface (owner / reviewer)

Given the fresh baseline (F1: half the cost is materialization) and the ROI framing (§4: the BlastEm
fleet is BlastEm-bound; only N-instance headless benefits from the codegen), the grind worker's
recommendation is **not** to open the full codegen grind by default. Instead:

- **Ship P1 now** (this push) — safe, measured, gated.
- **Then choose** one of:
  - **(a) Proceed to the codegen escape hatch (P2)** — commit to the declarative-recipe migration for
    best-in-class N-instance throughput now (start with the single-family prototype gate).
  - **(b) Take the bounded interpreter round (P1b) and re-measure** — likely ~1.6× for low risk; defer
    the codegen until an N-instance workload demonstrates a throughput wall. **Recommended default**:
    it is reversible, keeps single definition unchallenged, and the codegen's prize is unrealised until
    the N-instance consumer exists.
  - **(c) Declare policy 7 satisfied at P1(+P1b)** and record the codegen as an explicit, triggered
    future decision (like PAL / wasm) rather than an open TODO.

A grind worker holds this open rather than silently committing a project to (or away from) a
multi-week migration.

## 7. Out of scope (standing docket — flag, do not pick up)

- `set_ipl` has no deassert path until the VDP lands (delivered VInt re-fires after RTE) — plumbing.
- The L7 `ipl == mask == 7` edge.

  the dropped write's value.

## 8. Risks

- **P1 (low):** the `finish(self)`-by-move change touches every recipe builder's terminal call; a
  post-move reuse would be a compile error (Rust move-checks it), and the SST both-drivers sweep proves
  byte-identical execution. The committed harness depends on the gitignored corpus but SKIPs cleanly.
- **P1b (medium):** the decode dispatch table must preserve ordering-as-correctness; `MicroOp` packing
  may not shrink. Both are SST + totality-sweep gated; do not ship on a size that didn't fall.
- **P2 (high, deferred):** single-definition risk during the per-family DSL migration; the third-driver
  SST gate is the mitigation, but the surface is large — hence the owner gate in §6.
