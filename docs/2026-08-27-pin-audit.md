# Q-28 pin audit — what in oracle stands between the owner and testing

**Date:** 2026-08-27 · Read-only audit, nothing changed. Prompted by an **owner directive relayed twice**
(owner → aurora → hub): *"Man I hate these pins… I can't even test or use the thing I just built…"*
⚑ **NOT WITNESSED BY THIS LANE.** Scope as given: pinned ROMs, fixtures, socket-path conventions on his
path to testing. Certification freezes and corpus pins explicitly out of scope.

## 1. No pinned ROM stands on his path — verified, not assumed

* **The player takes the ROM as an argument.** `oracle-frontend` has no built-in ROM; nothing to unpin.
* **Hardcoded ROM paths exist only in `crates/oracle-core/examples/`** (`vgm_capture.rs`'s `DEFAULT_ROM`,
  `k4_openbus_probe.rs`). Developer examples he does not run. Left alone.
* **`reload_rom` already drops a symbol table that stops binding to the new image.** So loading a fresh
  ROM cannot leave him reading a stale listing — the failure mode that would matter most here is
  designed out rather than warned about.

## 2. The one refusal on his path is a SAFETY NET and must not be removed

`load_symbols` refuses (`-32602`) when a listing does not describe the loaded ROM. **This is the
opposite of a pin, and our own source carries the number that proves it:** of the symbols `s4.lst` and
`s4.debug.lst` share, **92.6% name a different address** — *"a mismatched listing is not degraded
information, it is confidently wrong information"* (`engine.rs:4492`).

**It does not block loading a ROM at all.** It refuses only a *mismatched listing*, and it self-heals
the moment the matching one is loaded. **Keep.** The directive's own line — *keep it for the agent and
give him the live one* — does not apply to a check whose whole job is stopping him from being told
wrong addresses about his own build.

## 3. ⚑ THE REAL HIT, AND IT IS THE SOCKET CONVENTION THE DIRECTIVE PREDICTED

**The MCP shim SPAWNS ITS OWN PRIVATE EMULATOR by default** (`oracle_mcp.py`: private
`mkdtemp` socket) **and attaches to a running window ONLY when `$ORACLE_SOCKET` (or legacy
`$EXODUS_SOCKET`) is set** (`:132-138`).

**So `mcp__oracle__*` silently drives a DIFFERENT emulator, with a DIFFERENT ROM, from the window he is
looking at** — and nothing in the reply says so. That is agent bookkeeping (the private spawn exists to
keep agents off his player) sitting between him and the thing he just built. **Exactly the class the
directive names.**

**Remedy is the directive's own, and the default must NOT change** — flipping it would re-expose his
window to every agent in the suite, and it is a deliberate ruling in `oracle-old`. **Keep the private
spawn for agents; give him the live one:**

```sh
ORACLE_SOCKET=/tmp/oracle-aurora-trunk.sock   # his window, as launched
```

**⚑ WHETHER THE WINDOW HAS SINCE BEEN RELOADED ONTO THE LIVE BUILD CANNOT BE READ FROM THE COMMAND
LINE, AND I DID NOT GO AND LOOK.** `argv` is frozen at `exec`, so it is a claim about how the process
*started*, never about what it is running now — this lane's own *check the vintage of the process, not
the version of the file* bar, and bar 16's two-valued-output clause: the argv is equally consistent with
*"still on the deleted pin"* and *"reloaded onto the fresh build, argv merely historical"*. aurora
reports they loaded the live copy in, which would make the second reading right.

**I did not settle it by dialling `/tmp/oracle-aurora-trunk.sock`, deliberately: that is his live test
surface.** The read is cheap and non-invasive and it is still his window, and `BP-WINDOW-CONFIRM` was
declined on the same ground an hour earlier. **He can settle it in one glance** — the ROM-freshness
banner this lane shipped yesterday reports exactly this state, including *"the file has gone"*, which is
what that window would say if it is still on the original path.
