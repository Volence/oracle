## The params-closure stress verdict (the CR's one new rule, stressed as the centerpiece)

**The subjects-reversed argument HOLDS, and the asymmetry is real.** Item 20's hazard was concrete: a
client validating **results** against a vendored schema rejects a conformant server that added a
registered key — the validator and the publisher are different parties at different revisions. On
**params** the validating party (the server) validates against the fragment set it itself implements
and advertises; it cannot be stale relative to itself. I hunted for a client-side mirror hazard and
found none that survives: a client pre-validating its own *outgoing* requests against a stale vendored
schema can only refuse to send keys it does not know exist (self-limiting, not a peer rejection); a
client with a **newer** schema than the server passes its own validation and is refused by name — which
is the stated cost, not a hidden one.

**The cost is real, priced correctly, and better than the silence it replaces.** A future optional
param stops degrading silently on old servers: the new client is refused where it was "tolerated."
But the tolerance was never neutral — the demand's own probe is the proof that an ignored semantic
param is a *misexecution* wearing a success reply (`Player_1`+0, twice, with an address the caller
never asked for). A named refusal (`error.data.unknownParams` + the accepted set in `message`) is
branchable and even serves as the only params-level feature-detection this bus has, since `initialize`
advertises methods, not params. Residual, worth knowing and not worth a change: probing a
side-effectful method for param support on a **new** server performs the effect — "the refusal
precedes any effect" protects only the refused case — so a client should probe deliberately. **D5's
additivity story survives** because its subject was always the client-read direction; the CR quotes
the reconciliation (*"Closure binds servers; additivity protects clients"*) and reverses it validly —
additivity never entitled a client to send unregistered keys, and the `initialize` carve-out preserves
the one place D5's "old clients ignore unknown flags" sentence lives. The carve-out itself is doubly
safe: asserted in §2.5, and structurally out of the closure's reach (`handshake`, not `methods`).

**The keyword choice is right and I verified its premise both ways.** Today `unevaluatedProperties`
and `additionalProperties` are equivalent across all 34 params objects — a full applicator scan finds
exactly one property contributed inside an applicator anywhere (`watchpoint_add`'s `mode` `const` in
its `if`/`then`s), and it is declared at the parent, so **both** keywords accept the census call
(executed both ways; case 43 reproduced, and reproduced again with `additionalProperties: false`
substituted). The choice is about the next fragment, exactly as §7 decision 5 argues, and item 20's
own reproduced experiment (`protocol.md:1544-1557`) is the measured basis.

**Blast-radius-nil for the MCP: HELD, with S1's caveat.** The MCP's generated tool schemas carry
`additionalProperties: False` (`oracle_mcp.py:895`) so no unknown key leaves the client; the forwarder
injects nothing (`args = dict(arguments or {})` → `call_method(method, args)`, `:931`/`:967`); the
`write_memory` tool declares exactly the five known keys (`:307-323`). The unswept direction — a tool
prop its fragment does *not* declare, which 27c would newly refuse — is S1's mechanical sweep.
