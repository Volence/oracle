# TESTROM-H40-HALF — the half of `vdp_sprite_masking` nobody had measured, and the answer to Q1

**Date:** 2026-09-18 · **Branch:** `parcel/h40-half` · **Scope:** test harness and docs only. Nothing under
`crates/oracle-core/src/` was touched (`git diff --stat 34682ca..HEAD -- crates/oracle-core/src/` is empty).

Two deliverables, and they turn out to be the same finding seen from two sides:

- **A.** `SpriteMaskingTestRom` runs its nine tests in **two** screen modes. The conformance harness had
  measured the power-on one since the row was first pinned on 2026-07-25. It now measures both, behind a
  mode proof that cannot be skipped.
- **B.** The ROM's own screen says `PRESS START BUTTON TO SWITCH BETWEEN H40 AND H32 MODE`; in this core it
  is `C` that switches. Recorded as **Q1** on 2026-07-25 and never investigated. **Answered: the ROM's text
  is stale relative to its build.** Our core is not defective here. Q1 is closed.

---

## A — the H40 half

### Why it is not a cosmetic variant

H40 is not "H32 but wider" as far as this ROM is concerned. The VDP's sprite limits are per-mode:

| limit | H32 | H40 |
|---|---|---|
| sprites per line | 16 | 20 |
| sprite pixels (dots) per line | 256 | 320 |
| sprites per frame | 64 | 80 |

Tests 1 (`MAX SPRITES PER LINE`), 2 (`MAX SPRITE DOTS-BASIC`), 3 (`MAX SPRITE DOTS-COMPLEX`) and 9
(`MAX SPRITES PER FRAME`) are tests **of those limits**. Measuring only H32 left the H40 numbers — a
different code path in `Vdp::sprite_line`'s budget accounting — unexercised by this instrument.

### The row

```
vdp_sprite_masking
  H32: 1=TICK/TICK 2=TICK/TICK 3=TICK/TICK 4=PASS 5=PASS 6=PASS 7=PASS 8=PASS 9=TICK/TICK
       [post-hoc path differs: 6=FAIL]
| H40: 1=TICK/TICK 2=TICK/TICK 3=TICK/TICK 4=PASS 5=PASS 6=PASS 7=PASS 8=PASS 9=TICK/TICK
       [post-hoc path differs: 6=FAIL]
```

**Nine H40 verdicts read for the first time, and all nine pass.** Every one classifies against the four
already-pinned glyph hashes with **no re-derivation** — no `UNKNOWN-GLYPH`, so the L3 trap this row has now
twice avoided was not entered a third time.

**The H32 segment is byte-identical to the old row.** Measured, not asserted from the shape of the diff: the
base commit's harness and this one were each run and their printed rows compared (below).

**One row, not two BASELINE entries.** `baseline_covers_every_rom` asserts a ROM ↔ row bijection, and a
regression in *either* mode is a diff on this single line either way, so a second entry would have cost the
guard and bought nothing.

### Where every H40 coordinate came from

The brief's rule was: derive in the new mode from the picture, never copy or scale the H32 constants. The
H40 rectangle comes out **equal** to the H32 one, so it is worth showing the derivation rather than the
number.

**x 216..248, in H40.** Two independent readings, recorded in `Screen::glyph_x`:

1. *Nametable.* On the H40 screen, plane-A row 6 (and 10, and 14 — sampled) carries exactly four non-zero
   cells past the test's name text, at plane columns **27, 28, 29, 30** — `$010E $010F $010C $010D` for a
   tick pair, `$0104 $0105 $0106 $0107` for a `PASS`. Those are the same columns as in H32, because **the
   ROM does not right-align its verdicts**: in a 40-column screen they sit nine cells in from the right
   edge rather than at it. 27 × 8 = 216, 31 × 8 = 248.
2. *Framebuffer*, which is the reading that does not depend on a horizontal-scroll assumption. An H40
   luminance dump of x ≥ 200 over lines 48..119 puts every lit pixel of all nine verdict glyphs in
   **x 216..=246**, with x 248..319 blank on all nine rows. (The ink at x 201..207 on rows 88..94 is the
   final `W` of `6.MASK S1 ON DOT OVERFLOW`, not a glyph.)

**Rows 6..14, 8 lines each, in H40.** From the same dump: the glyph ink occupies exactly lines 48..=119 and
every glyph is 8-line aligned at 48 + 8k.

**The mode label.** Derived from the machine, not written down. The old row's prefix was the string literal
`"H32:"` — a label that cannot be wrong is not a measurement. It is now `ProvenScreen`'s label, taken from
`CompletedFrame::width()` — *the width the captured frame ended on*. That is deliberately **not**
`sys.vdp().render_line(0).len()`, which `scanline_capture.rs` warns about in its own docs: a post-hoc
re-query answers for whatever mode the chip is in *now*, which after an H32↔H40 switch is the next frame's.

### The gate — the mode proof is a type, not an assert

The failure this parcel exists to prevent is silent. If the toggle does not take, the "H40" half re-scrapes
the H32 screen, all nine glyphs classify cleanly, and the row reads nine plausible verdicts for a mode the
run never entered. An `assert!` beside the scrape would catch that today and stop catching it the first time
someone reordered the function.

So the proof **gates** the scrape structurally:

- `ProvenScreen::establish` is the only constructor. It takes the mode the caller set the machine up for,
  the width the captured frame ended on, and the mode the previous half proved.
- It refuses on **two** independent conditions, neither implying the other: `measured == want.width()`
  (a toggle that did not take, took the wrong way, or a capture read at the wrong width), and
  `want != previous` (a future edit that set *both* halves up for the same mode — the first check would
  pass twice and the row would carry two readings of one screen under two labels).
- `sprite_masking_classify` takes a `ProvenScreen`. There is no path to a glyph that skips it. An unproven
  mode is not a thing that file can represent.

Same shape as the `[post-hoc path …]` bracket: stated positively, so an unmeasured mode can never read as a
measured one.

### One guard retired, and its non-vacuous heir

The old `cap.pixels().len() == width * ACTIVE_LINES` assert compared the capture's length against a width
**re-queried from the chip**. In the H40 half that would have compared 224 lines of 320px against 224 × 320
and agreed — for a reason unrelated to the picture. `CompletedFrame` now carries that job and is stricter:
it refuses a log shorter than a frame, and refuses a tail whose per-line widths do not sum to the pixels
held.

What the old assert could *not* see, and what replaces it, is a frame **torn across a mode switch**: lines
before the R12 write 256px and the rest 320px. `CompletedFrame::pixels` pads a short line with black and cuts
a long one, so such a frame hands back a clean 320 × 224 rectangle with a black gutter and hashes
confidently. `refuse_a_ragged_frame` refuses it. Measured today: every line of the H32 capture is 256px and
every line of the H40 capture is 320px.

**That guard is tested directly rather than through the run, and the reason is a finding of its own: this
ROM cannot produce its subject.** The tear can only occur in the frame the R12 write lands in; that write is
itself a VDP write; and `VdpIdle` will not stop until 8 frames after the last VDP write — so the torn frame
is always at least nine frames older than the retained one. Two behavioural mutations were tried and both
fired a *different* guard first. A guard whose subject is structurally unreachable rots into decoration, so
the subject is supplied to it directly (`a_ragged_captured_frame_is_refused`).

### The press

`C`, held two frames on port 1, then released. Measured: at the H32 idle stop the ROM is parked at pc
`$316` — the "wait for bit 5 to go low" half of its wait routine — so it sees the press on the first frame
of it. The toggle is edge-shaped, not level-shaped (holding `C` for ten frames toggles once). The release
matters because the routine's *other* half waits for bit 5 to come back high before it will accept anything
again. Two frames rather than one is slack, not a tuned constant — the gate is what says whether it worked.

Run shape, measured: H32 idle stop at frame 15 (last VDP write frame 7, captured frame 14, width 256); press
in frame 15; ROM redraws over frames 15–22; H40 idle stop at frame 30 (last VDP write frame 22, captured
frame 29, width 320).

### The control arm now holds in both modes

The live-vs-post-hoc divergence `POSTHOC-CARRY` found is **not an H32 accident**. It reproduces identically
in H40: test 6 (`MASK S1 ON DOT OVERFLOW`) reads `PASS` live and `FAIL` post-hoc in both modes, because
`Vdp::render_line` re-seeds R10 masking from the end-of-frame `sprite_dot_overflow_carry` regardless of
display width. So `the_glyph_scrape_reads_the_live_render_path` now requires the divergence **in each
half** — a fix that quietly repaired one mode's carry seeding and not the other's fails it — plus a new
assertion (0) that the two halves really are two different screens.

**Two process notes worth keeping, because both were nearly a false pass.**

- **A3's first attempt was applied-and-still-green.** The second press was placed 2 frames after the first,
  which lands while the ROM is still redrawing in H40, so the pad was already released by the time the wait
  loop was reached: the mutation was a **no-op on the machine**, not a gate that failed to fire. Moving it
  to 20 frames made it real. Rule 6(c) says applied-and-still-green is a runner defect to fix, not a pass —
  in this case it was a *mutation* defect, and the only way to tell them apart was to go and find out which.
- **Mutation D's first attempt did not apply at all**, because `cargo fmt` had reshaped the line the patch
  matched on. The patch script asserted on its own pattern and said so; the run that followed was therefore
  the *baseline* printing green. Printing the applied diff before every run is what made that visible.

### Tried and declined

`Retain::LastFrame → Retain::First` (POSTHOC-CARRY's torn-capture mutation) no longer reaches the ragged

## B — Q1 answered: the ROM's text is stale, and this core is right

**The question.** Is `Start`-does-not-toggle a defect in our input / TH protocol, or is the ROM's on-screen
text stale relative to its build?

**The answer: the ROM's text is stale.** More precisely, the ROM's wait routine is **missing the direction
write** that its own intent requires, so no correct implementation can do what the text says.

### The ROM's polling code, read statically

Disassembled from `vendor/TestRoms/vdp_sprite_masking.bin`
(sha256 `1331819e…dc967d`), the wait routine at `$0002FA`:

```
0002F0  6100 0008            bsr.w   $0002FA
0002F4  4EF9 0000 0280       jmp     $00000280
0002FA  13FC 0000 00A1 0003  move.b  #$00,$00A10003    ; P1 DATA register
000302  4E71                 nop
000304  4E71                 nop
000306  4E71                 nop
000308  4E71                 nop
00030A  0839 0005 00A1 0003  btst    #5,$00A10003
000312  6700 FFF6            beq.w   $00030A           ; spin while bit 5 == 0  (wait for RELEASE)
000316  0839 0005 00A1 0003  btst    #5,$00A10003
00031E  6600 FFF6            bne.w   $000316           ; spin while bit 5 == 1  (wait for PRESS)
000322  4E75                 rts
```

Three things follow, and the third is decisive:

1. It writes `#$00` to `$A10003` — the **Data** register — then spins on bit 5 of the same register. The
   four `nop`s are the settle delay the TH protocol calls for, so the author's *intent* was plainly "drive
   TH low, then read Start on bit 5".
2. **Writing the Data register does not drive TH.** A pin drives the wire only if the **Control**
   (direction) register makes it an output — recon IO2/IO3, and the universal documented model. Every bit
   of `$A10003` written while its direction bit is 0 goes to the latch and nowhere else.
3. **The string `$A10009` — P1's Control register — does not occur anywhere in the ROM's 256 KB image.**
   Nor does `$A1000B` (P2's). Byte-scanned for the 4-byte operand `00 A1 00 09`: **zero occurrences**.
   `00 A1 00 03` occurs exactly **three** times — at `$02FE`, `$030E`, `$031A`, which are the operands of
   the three instructions above and nothing else.

So this ROM **never configures TH as an output, anywhere, ever.** TH stays an input at its power-on
default, floats high on the port pull-up (recon IO3: *"a wire configured as input with nothing driving it
floats high (pull-up → reads 1)"*), and the pad therefore drives its TH-**high** set, in which **bit 5 is
`C`** (recon IO4). The ROM reads `C` because `C` is what is on the wire.

### What our core actually returns at that instruction

Traced at the read, with the pad injected on P1 (one frame, all reads of `$A10000..$A1001F` logged with the
PC):

| pad held | accesses in the frame | what the read at pc `$000316` returned | mode after |
|---|---|---|---|
| nothing | 4266 × `Read Byte $A10003` | `$FF` — bit 5 set, the spin continues | H32 |
| `Start` | 4266 × `Read Byte $A10003` | `$FF` — bit 5 set, the spin continues | H32 |
| `C` | **1** × `Read Byte $A10003` | `$DF` = `1101_1111` — bit 5 **clear**, the spin exits | **H40** |

`$FF` and `$DF` are exactly `pad_device_byte(pad, th_high = true)`: `0b1100_0000 | C<<5 | B<<4 | R<<3 |
L<<2 | D<<1 | U`. The core is answering the TH-high phase because TH is high, because nothing made it an
output. **No write to `$A10009` appears in the trace either** — the ROM issues none.

### The corroborating arm — and why it is in-corpus, not cross-emulator

The brief offered `tools/blastem-differential` as a cross-emulator A/B. It was not used, and the reason is
that **a sharper A/B already exists inside this harness**, on the same core, in the same run shape:

`vdp_port_access` **does** write `$A10009` (twice, at `$1126` and `$116E`) and reads `$A10003` eight times —
the full TH protocol — and `run_port_access` advances it through all 16 pages **by pressing `Start`**, with
a pinned baseline of `16/0/16`. So this core's `Start` bit is demonstrably readable by a ROM that drives TH,
today, in this test file. `io_sample` is the third data point: it writes `$A10009` once and reports `JOYPAD`
on both ports, which is the TH-low detection signature (bits 3–2 forced 0).

A cross-emulator run could only have told us what another emulator's model does. It could not have made
"this ROM contains no direction write" false — that is a property of the ROM image, and it is what settles
the question.

### The one residual, stated rather than buried

Everything above turns on one pinned rule: **an input-configured TH pin reads high.** If the hardware pull
were the other way, the ROM's `move.b #$00,$A10003` would be irrelevant, bit 5 *would* be `Start`, and the
ROM's text would be right.

That rule is pinned in-tree (`docs/2026-07-17-io-recon.md`, IO3, status **PINNED**) and is the basis of
every documented pad-detection routine, so this is a citation of the reference the parcel was told to use,
not an assumption. But no ROM in the corpus discriminates it: `vdp_port_access` and `io_sample` both *drive*
TH, so they exercise the driven case only.

**What would settle it empirically**, if anyone wants it settled: a 68000 sequence that reads `$A10003`
with the Control register untouched at `$00` and reports the whole byte. Pull-up-high predicts `$FF`;
pull-low would predict `$B3` (bit 7 high, TH low, bits 3–2 forced 0, Start/A/Down/Up released). That is one
small harness ROM through `tools/blastem-differential`'s existing RAM-dispatch rig — a real experiment, and
a ROM-independent one, but it is a question about the **port model**, not about this parcel's row, so it is
recorded here rather than done inside a harness parcel.

### Disposition

Q1 is **closed** as "the ROM's text is stale relative to its build". No core change is warranted or made:

- the defect is the ROM's missing direction write, which is in the ROM image;
- our `Start` bit is proven readable in the same harness by a ROM that drives TH;
- and `crates/oracle-core/src/` is unchanged by this parcel, so nothing here can have moved pad behaviour
  or frozen currency.

The harness therefore uses `C` **on the evidence**, not as a workaround, and both the row comment and
`ProvenScreen::establish`'s failure message say why, so the next reader does not re-open it.
