# F-IO-DATA-BIT7: what a controller-port Data read returns in bit 7

**Status: SETTLED 2026-09-25, outcome (a): bit 7 is the Data latch's own bit 7.** Branch `parcel/io-data-bit7`.
Confidence: **high**. Three sources agree, and two of them show the mechanism rather than just asserting the
behaviour. One is a die-extracted gate netlist of the discrete I/O chip, one is a decap-derived model of the
integrated chip, and one is a published measurement on a real console. No source found says anything else.
Every emulator examined (seven) also returns the latch, but most of them trace back to the measurement, so
they are listed as corroboration and not counted as separate evidence.

## The question

A port's Data register (`$A10003` / `$A10005` / `$A10007`) has eight bits. The port has only seven pins
(`PA0-PA6` on pins 50-56, `PB0-PB6` on 57-63, `PC0-PC6` on 12-18, per `emu-russia/SEGAChips` `IOChip/Pinout.md`; there is no `PA7`/`PB7`/`PC7`), so no pin drives Data bit 7. Until this
parcel our core forced it to `1` on every read (`pad_device_byte` ORed in `$80` on both TH branches, and
`read_data` passed it through wherever Control's bit 7 was clear, which is every normal game). BlastEm 0.6.2
returns the latch's bit 7. So on every normal pad read (the game writes `$40`/`$00` to Data) we answered
`$FF`/`$B3`-shaped bytes where BlastEm answered `$7F`/`$33`. The 2026-09-19 booking recorded this as the one
entry in `known_differences.py` that did not claim ours was right.

There were three candidate answers: (1) constant `1` (a pull-up; ours), (2) the latch (BlastEm), or (3)
open bus, meaning the chip leaves D7 undriven and the 68000 sees whatever the bus last held. Under (3), both
emulators would be wrong. The die netlist rules out (1) and (3).

### The netlist trace, step by step (source 1)

`IO.v` is a gate-level netlist whose cells are empty modules, so no simulation is possible. I traced it by
following the connections, using a throwaway Python walker over the instance list. Every step is a literal
line of the file:

1. `assign VD7_o = w205;` VD7 is the 68000 data line.
2. `io_MUX4BIT g_289 (.S(w53), .Z0(w205), .A0(w289), .B0(w753), …)`, where `w289 = ZD7_i`. This picks the
   Z80 data bus (bus bridging) or the register-read value `w753`. `S = w53 = NOR3(n_CAS0, n_IO, …)` selects
   the register path on an I/O access.
3. `io_MUX4BIT g_253 (.S(w871), .Z0(w753), .A0(w807), .B0(w809), …)` selects registers 0-7 or 8-15 on
   address bit 4.
4. `io_MUX8TO1 g_303 (.S0(w797), .S2(w183), .S1(w128), .A(w153), .B(w796), .C(w934), .D(w368), .E(w803), .F(w51), .G(w733), .H(w732), .Z(w807))`
   is the bit-7 slice of the register read mux. Its selects in 68000 mode are VA1/VA2/VA3, which give the
   register index. The inputs line up with the register map: A = `n_JAP` (register 0, Version bit 7 =
   domestic/export), **B = register 1, Port A Data**, E/F/G = the three Control registers (flip-flops *with*
   reset `nRES(w112)`), and H = an `SLATCH` for TxData (Nuked models TxData as a latch too).
5. `io_MUX4BIT g_88 (.S(w8 = n_M3), .Z0(w796), .A0(w63 = PB1_i), .B0(w254), …)`. In Mark III (SMS) mode,
   bit 7 of register 1 is pin PB1 (Nuked: `read_data |= (port_b.port_i << 6) & 192`). **In Mega Drive mode
   it is `w254`.**
6. `io_DFFRPOS g_87 (.Q(w254), .nRES(1'b1), .D(w138), .C(w142) );` **`w254` is the output of a flip-flop.**
   `w138 = MUX4BIT(g_292)` picks VD7 (68000 mode) or ZD7 (Z80 mode): data-bus bit 7. `w142 = NAND4(g_286)`
   is the write strobe decoded from `/LWR`, `/IO` and VA4..VA1 = `0,0,0,1` (register 1). It clocks exactly
   eight flip-flops (`g_36 g_38 g_39 g_40 g_83 g_84 g_197 g_87`), which together are the 8-bit Port A Data
   register.

Port B's bit 7 follows the same pattern (`w934 → g_256 → w822 = g_192.Q`, `D = w138`, clocked by the
Port B strobe `w33`), and so does Port C's (`w368 = g_600.Q`, `D = w138`, clock `w333`).

## Verdict

**The latch.** On a Data-register read, bit 7 is the value of an ordinary register flip-flop, and it holds
whatever the CPU last wrote there. Control has no effect on it (its bit 7 is the TH-interrupt enable, and
no Control flip-flop is on bit 7's read path). The pad has no effect on it either (no pin reaches it). It
is not open bus, because the I/O chip drives VD7 from that flip-flop. MacDonald's console measurement shows
this directly (`$7F` → write `$80` → `$FF` → write `$00` → `$7F`), and two independent decap efforts show
the mechanism behind it.

## What changed

* `crates/oracle-core/src/io.rs`: the new const `DATA_LATCH_ONLY = 0x80` carries the three citations.
  `read_data` now computes `from_latch = (ctrl & 0x7F) | DATA_LATCH_ONLY` and returns
  `(latch & from_latch) | (device & !from_latch)`. `pad_device_byte` no longer invents a bit 7, because
  the pad drives seven pins. The module doc, the `Io` doctest (EXP `0xFF` → `0x7F`) and four unit tests
  whose expected bytes carried the old forced bit 7 were updated. Each new expectation is derived as
  "IO4's seven pins + the latched 0": `0xD7→0x57`, `0x93→0x13`, `0xFF→0x7F`, EXP `0xFF→0x7F`. A new
  case also covers `configured(0xC0) → 0xFF`.
* `crates/oracle-core/src/bus.rs`: `port1_pad_reads_through_the_th_protocol_over_the_bus` now expects
  `0xFF→0x7F` and `0x93→0x13`, for the same reason.
* `crates/oracle-core/tests/io_controllers.rs`: the "recorded divergence" test is replaced by two gates.
  The expected values come from the sources above, not from our output:
  * `data_bit_7_follows_the_latch_through_the_bus` runs `th_pullup.bin` through the real 68000 bus.
    Observables +0/+11/+8 are exactly MacDonald's three reads, `$7F`/`$FF`/`$7F`. All 12 observables must
    now equal BlastEm's recorded bytes **whole-byte**, where before only bits 6-0 were compared.
  * `data_bit_7_is_the_latch_on_every_port_whatever_control_says` asserts MacDonald's listing verbatim
    on P1/P2/EXP. It then checks the netlist rule across Control ∈ {`$00,$40,$80,$C0,$7F,$FF`} × latch ∈
    {same set}, with a pad pressed. Last, it checks the normal game read (`$40`→`$7F`, `$00`→`$33`).
* `tools/blastem-differential/known_differences.py`: the `io-data-bit7` entry is **removed** (closed,
  not flipped). A comment records why. There is no divergence left to put on the ledger, because ours
  and BlastEm now agree byte for byte on `th_pullup.bin`.

### Red-first

Both new gates were written and run against the **unchanged** core first, with only the test file edited
and `io.rs` still as committed at `d1cdc48`. Both failed on assertions (exit 101), not on compile errors:

```
test data_bit_7_is_the_latch_on_every_port_whatever_control_says ... FAILED
  P1: pristine read is $7F (gen-hw.txt 3.0/3.1)   left: 255  right: 127
test data_bit_7_follows_the_latch_through_the_bus ... FAILED
  left: (255, 255, 255)  right: (127, 255, 127)
test result: FAILED. 3 passed; 2 failed
```

After the fix, all 5 tests passed (exit 0). Two mutations were then run against the committed fix
(`git checkout --` restored the file after each). They test different wrong answers:

* **M1, back to "constant 1"**: put `0x80` back into both `pad_device_byte` branches and set
  `from_latch = ctrl`. Both gates went red (exit 101): pristine `255` vs `127`, and the bus arm
  `(255,255,255)` vs `(127,255,127)`.
* **M2, "constant 0 / no latch"**: set `from_latch = ctrl & 0x7F` and leave the pad clean. Both gates went
  red (exit 101): *"P1: after writing $80, $FF"* read `127` vs `255`, and the bus arm read `(127,127,127)`
  vs `(127,255,127)`.

So the gates tell all three candidate answers apart.

## What is open

* **Data latch is not cleared by reset (side finding, not acted on).** In the netlist, all eight Data
  flip-flops have `nRES` tied to `1'b1`. The Control flip-flops reset from `w112 = AND(n_M3,
  DFF(n_SRES @ VCLK))`. Nuked-MD agrees: `p_data` is updated with a reset input of `1`, while `p_control`
  gets `chip->reset`. So on hardware a reset-button press keeps the Data latch, and its power-on value is
  whatever the flip-flops wake up as. (MacDonald's read-out shows `$7F`, and MAME's reset code carries a
  TODO about it.) Our `System::reset` models a power cycle, which sets Data back to `0`. That matches
  MacDonald's `$7F` default, so nothing observable changes today. **If a separate reset-button path is ever
  added, it must keep the Data latch.**
* `run_th_pullup.py`'s `LABEL` strings still predict whole bytes as `$FF`/`$B3`, the old forced-bit-7
  shape. Its verdict functions already read only bits 6-0 plus a separate bit-7 classifier, which prints
  "the Data latch's own bit 7" for BlastEm, so nothing it reports is wrong. Only the label hints are
  stale. I left the file alone because it is instrument code.
* A real-console run of `th_pullup.bin` is still the one arm nobody here has done. For bit 7, MacDonald's
  published measurement stands in for it.
