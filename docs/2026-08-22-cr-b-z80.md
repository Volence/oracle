## 1. Summary

The contract's Z80 memory surface is two rows in §6:

```
| `emulator/z80_read` | `addr` (0–`$3FFF`), `len`? (≤`$2000`) | `addr`,`len`,`bytes` |
| `emulator/z80_write` | `addr`; `bytes`\|`value` | `addr`,`len` |
```
*(`contract/protocol.md:996-997`, at `origin/main` `f172e61`.)*

That is the whole of it. There is no normative blockquote for either row — unlike `emulator/read`,
`emulator/memory_hash` and `emulator/write_memory`, each of which sits under one, in the same table, on the
same page. The two Z80 rows are also physically *below* `write_memory`'s blockquote rather than inside the
table they belong to, which is why a reader scanning the *memory & Z80* table can miss them entirely.

This CR proposes five changes:

| # | Change | Closes |
|---|---|---|
| B1 | `z80_write`'s `value` gains an optional **`width`** ∈ {1, 2}, default **1**, landing **little-endian**; the reply's `len` is defined as `width` on that spelling | **D-10** |
| B2 | Both rows state `0–$3FFF`; an access whose **end** runs past `$3FFF` is `-32004`, **refused, never wrapped**; the `$2000–$3FFF` mirror is stated | **new** (§5), plus D-10's address-bound half |
| B3 | `z80_read`'s `len` becomes `def 1, ≥1, ≤$2000`, **refused, never clamped** at the ceiling | **D-09** |
| B4 | `z80_write` is named in §6's run-control state rule | **D-11** |
| B5 | A normative blockquote for the pair, so these two rows stop being the only memory rows with none | — |

**Three of these depart from a recommendation the audit itself made, and each departure is argued at the
point of use rather than in this table:** B1 declines the audit's reading (b) in two of its three parts
(§4.4); B2 adds a clause the audit did not ask for and that no reading of D-10 implies (§5); B4 is
recommended *with* a documented consumer cost the audit did not measure and which could reasonably reverse
it (§7.4).

**What it costs consumers.** Nothing, on every call site this CR could find — and that finding is not the
comfortable one it looks like. There are **zero programmatic consumers** of either method in any sibling
tree, and **48 written-down mentions in three trees** describing manual/agent-driven use — 46 in `aeon`
across 23 files, one in `seraph`, one in `empyrean`'s wiki. Not every mention is an invocation, so no
call-site count is asserted; what is asserted is the *form* of every invocation that appears, and it is
uniform: **a single-byte `value` or an explicit `bytes` string, never a `value` above `0xFF`, never a
`width`** (§2.5). B1 is designed so that every one of those forms keeps its current meaning verbatim. B4 is the one proposal that changes what a live workflow can do, and §7.4 quantifies it.

### 2.4 What each implementation actually does — verified firsthand, attributed separately

Both columns below were re-derived for this CR by reading the source, not inherited. Where a prior document
in this repo reached the same conclusion it is cited as agreement, not as the source.

#### The Rust successor (`oracle/`, worktree `490dd31`)

**It serves neither method.** `grep -n 'z80_read\|z80_write' crates/oracle-aether/src/engine.rs` returns
exactly one line — `:2017`, a doc comment on `emulator/read` explaining why the Z80 is not a `space` value
— and no dispatch entry. `capabilities.z80` is published `false` (`engine.rs:1276`). Both methods are
`-32601` today. **This lane therefore has no shipped behaviour that any reading of D-10 would break, and no
implementation experience to argue from.** That is stated as a limitation on this CR's authority, not as
neutrality.

Two core facts constrain any future handler and bear on §5:

- `Z80_RAM_SIZE = 0x2000` (`crates/oracle-core/src/bus.rs:704`) — the Z80 RAM is **8 KiB**.
- The 68000-side window masks `self.z80_ram[z as usize & (Z80_RAM_SIZE - 1)]` for `0x0000..=0x3FFF`, on
  read (`bus.rs:929`) and on write (`bus.rs:1020`). **`$2000–$3FFF` is a mirror of `$0000–$1FFF`.**

#### The legacy C++ server (`oracle-old/`, `d629771`) — the implementation the rows were transcribed from

`OpZ80Read` is `ControlSocket.cpp:694-716`; `OpZ80Write` is `:718-749`.

| question | legacy `z80_write` | anchor |
|---|---|---|
| `value` width | **exactly one byte, always** — `bytes.push_back((uint8_t)(req.getInt("value") & 0xFF))` | `:736` |
| `width` param | **never read.** Passing `width: 2` is silently ignored | `:718-749` (absent) |
| over-range `value` | silently truncated: `value: 300` writes `0x2C` | `:736` |
| `bytes` vs `value` | `bytes` wins if both are given; neither is an error | `:727-740` |
| missing `addr` | **silently writes to `$0000`** — `getU32("addr")` defaults to `0` | `:723`, `:149` |
| base bound | `addr > 0x3FFF` refused; message names `$0000-$1FFF` *and its `$2000-$3FFF` mirror* | `:724`, `:690-692` |
| **end bound** | **none** — see §5 | `:743-747` |
| reply `len` | `bytes.size()` — always `1` on the `value` path | `:748` |
| run-state gate | **none.** No pause check anywhere in the handler | `:718-749` |

| question | legacy `z80_read` | anchor |
|---|---|---|
| `len` default | **1** — `req.getInt("len", 1)` | `:701` |
| `len` ceiling | `0x2000`, applied by **`std::min`** — silently clamped, no error, no flag | `:701` |
| base bound | `addr > 0x3FFF` refused | `:700` |
| **end bound** | **none** — the tail folds modulo `0x2000`, and a source comment says so | `:708-710` |

The `-32004` mapping is by **message substring**: `ErrorReply` classifies a message containing `"only"`,
`"out of"`, `"range"`, `"rejected"` or `"supported"` as `-32004` and everything else as `-32602`
(`:219-221`). `Z80RamRangeError` begins *"only Z80 sound RAM…"*, so the base-bound refusal is `-32004`.

**The single most decision-relevant fact in this document is a comment.** Verbatim, `:732-737`:

```cpp
    else if (req.has("value"))
    {
        // Single byte — the Z80 bus is 8-bit. For multi-byte sequences use
        // `bytes` (written low-address-first, no endianness guesswork).
        bytes.push_back((uint8_t)(req.getInt("value") & 0xFF));
    }
```

**The legacy implementation did not fail to specify a width. It declined to have one, on purpose, and wrote
down why.** That is the audit's reading (a), authored, shipped and justified — and it means D-10 is not a
blank the contract may fill freely. It is a disagreement between a shipped decision and a proposed one.

For the contrast the audit draws: the **same** server's 68000 `write_memory` *does* take `width` and *is*
big-endian, via a descending loop `for (int i = width - 1; i >= 0; --i)` (`:612-618`). So the legacy server
already implements the exact asymmetry the audit asks the contract to bless — width-bearing big-endian on
the 68000 row, width-free single-byte on the Z80 row. The asymmetry is not novel; only its absence from the
contract is.

*(This section reaches the same conclusions as `oracle/docs/2026-08-22-peer-schema-defect-answers.md:552-608`,
committed `02f4bf6`, which reported them first. Every line above was re-read at `d629771` for this CR;
the agreement is corroboration, not citation.)*

**The one correction this sweep makes to a prior document in this repo.**
`oracle/docs/2026-08-22-acceptance-21-survey.md:912` classifies `z80_read` and `z80_write` under **"no

recorded as executed, driving a real sound-debugging workflow. **The distinction is load-bearing for this CR**, because a manual consumer

is designed to do — and against any change that silently reinterprets them.

**What the sweep cannot see, stated plainly.** Ad-hoc calls typed into a session and never written down.
The 48 mentions are a floor on usage, not a ceiling, and they skew toward *documented* usage, which is the
usage most likely to be repeated by a future reader. **No count of invocations is claimed** — a line saying
*"drive it (reload_rom / run_frames / z80_read+write / vgm_start+stop)"* is a mention, not a call, and
separating the two reliably is not something a grep can do. The uniformity of the invocation *form* is what
this CR relies on, and that is checkable line by line.

## 3. The inclusion ruling: D-09 and D-11 travel with D-10

The parcel queue names only D-10 as "CR-B". This CR takes D-09 and D-11 in as well. The case each way:

### 3.1 The case for taking all three

1. **They are the same two lines of the document.** §6's Z80 surface is `protocol.md:996-997`. D-09 amends
   line 996, D-10 amends line 997, D-11 amends the rule at `:858-878` *by naming line 997 in it*, and B2
   amends both lines. A CR that fixes one and leaves the others means the same two lines are opened twice.

2. **D-09 and D-10 are provably one missing paragraph, seen from two ends.** D-09 is "`len` **in** has no
   stated default". D-10's actual complaint is that "`len` **out** is underdetermined". The defect is `len`.
   The prior analysis in this repo reached the same conclusion independently:
   > *"D-09 and D-10 are the same missing paragraph seen from two sides, and pinning `len`'s default on the
   > read row settles the reply's `len` on the write row too if `value` is given a width."*
   > — `oracle/docs/2026-08-22-peer-schema-defect-answers.md:549-550`

3. **D-11 cannot be deferred past implementation, because an implementer must answer it to write the
   handler.** A server building `z80_write` decides, in its first ten lines, whether to call the
   equivalent of `require_paused`. If the contract is silent, that decision is invented — which is
   precisely the harm §6's run-control rule names as its own reason for existing: *"Leaving them unnamed
   would let one server refuse and another accept, both conforming"* (`protocol.md:867-868`). Serving the
   method with D-11 open does not defer the question; it answers it in code, unreviewed.

4. **The pre-release window shuts once, and this contract has already ruled that it should be spent in one
   sitting.** §11.16 took a whole recommendation in rather than registering half of it for later, on
   exactly this reasoning:
   > *"the pre-release window closes once, and a field registered for later can only come back optional or
   > in a v2. The override is recorded here as a decision rather than absorbed as a natural next step."*
   > — `contract/protocol.md:3306-3308`

### 3.2 The case against — which is real, and is strongest for D-11

- **The audit itself pairs D-11 with a different defect.** Its recommendation reads: *"name `z80_write`
  (**and see D-16 for `write_vram`**) in the rule, or state affirmatively that it is exempt"*
  (`audit.md:171`). D-16 is the identical complaint against `write_vram` (`audit.md:215-224`). So on
  the audit's own arrangement, D-11's natural companion is D-16, not D-10 — the shared subject is *"which
  write rows the state rule names"*, and settling one write row while leaving the other silent reproduces
  the very inconsistency D-11 objects to. **An adjudicator could reasonably strike B4 from this CR and
  route D-11 + D-16 to a single run-control CR, and this CR would still stand.** B4 is written to be
  severable for that reason: nothing in B1, B2, B3 or B5 depends on it.
- **D-11 has a consumer cost the other two do not.** B1 and B3 leave every observed call site meaning what
  it means today. B4 makes every observed free-running invocation illegal as written (§7.4). Bundling a change with a cost alongside
  two without one invites a package ruling where an itemised one is available.
- **A wider CR is a slower CR.** D-09 alone is a two-word edit that matches shipped behaviour and could
  land today.

### 3.3 The ruling taken, and what would reverse it

**All three are in, and B4 is marked severable.** The decisive argument is 3.1(3): D-09 and D-10 can be
deferred without a server inventing contract, and D-11 cannot. A method cannot be built while its
run-state position is undefined, and this parcel exists to build it.

**What would reverse it:** if the adjudicator prefers to rule D-11 and D-16 together, B4 should be struck
and its evidence (§7.4) forwarded to that CR rather than re-gathered. This CR asks that the *answer* be
given somewhere before `z80_write` is served, not that it be given here. **Q4 in §11 puts that choice to
the adjudicator explicitly.**

## 4. B1 — `value` gains a width (D-10)

### 4.1 The proposal

On `emulator/z80_write`:

- `value` MAY be accompanied by **`width`**, an integer in **{1, 2}**.
- **`width` defaults to `1`** when `value` is given without it.
- A `value` that does not fit its `width` is `-32602` — **refused, never truncated**.
- A multi-byte `value` lands **little-endian**: the low byte at `addr`, the next at `addr+1`.
- **`width` with `bytes` is `-32602`** (it qualifies the numeric spelling only), matching `write_memory`.
- The reply's **`len` is `width`** on the `value` spelling, and the decoded byte count on the `bytes`
  spelling. This is the key that D-10 says is underdetermined; it is now determinate on both paths.

### 4.2 What is wrong today, and who it hurts

`z80_write {addr: "0x1F02", value: 195}` is a valid request under the published fragment
(`bus-protocol.schema.json:1676`, and upstream's own `vectors.json:53` asserts it **passes**), and the
contract does not say how many bytes it writes. The reply must carry `len` — the fragment marks it
REQUIRED — and there is nothing to compute it from. The fragment says so in its own words:

> `len` […] Determinate for a `bytes` payload; underdetermined for a `value` one until §6 pins a width
> (audit D-10).

**Who it hurts, concretely.** It hurts the *next implementer*, not today's caller. Today's callers all pass
single bytes (§2.5) and the legacy server writes single bytes, so the ambiguity is currently latent. It
becomes live the moment a second server ships: this lane's survey already recorded the block —

> **`z80_write` is the one hard contract block in the whole set.** The result's `len` is **required**, and
> for a `value` payload there is no width to compute it from. Serving the `value` spelling means inventing
> a width — which is exactly what the fragment refused to do.
> — `oracle/docs/2026-08-22-acceptance-21-survey.md:454-456`

The failure mode if it is left open is the bad kind: a client sends `value: 0x1F02` to two conformant
servers and gets a one-byte write of `$02` from one and a two-byte little-endian write from the other, both
reporting success, with different `len` values that the client has no rule to check against.

### 4.3 Why *these* choices — each departure argued where it is made

**Why little-endian, and why symmetry with `write_memory` would be a bug.** `write_memory` says
*"Multi-byte values land **big-endian**, as the 68000 stores"* (`protocol.md:975-976`). The clause after the
comma is the rule; "big-endian" is its consequence on that machine. The Z80 stores a 16-bit value low byte
first — `ld (nn), hl` writes `l` at `nn` and `h` at `nn+1` — so applying the *rule* to the Z80 row yields
**little-endian**, and copying the *consequence* would produce a poke that lands a pointer backwards while
looking symmetric. The audit reaches this independently and calls it *"the one place a symmetric rule with
`write_memory` would be actively wrong"* (`audit.md:163-165`). This CR agrees and adopts it.

**Why `{1, 2}` and not `write_memory`'s `{1, 2, 4}`.** `write_memory`'s domain is not arbitrary — it is the
68000's byte/word/long, the three widths that machine stores. The Z80 has byte and 16-bit-pair stores and
no 32-bit store at all; a `width: 4` on this row would name an operation the target machine cannot
perform, and its byte order would be an invention rather than a transcription of how the machine stores.
A client wanting four bytes has `bytes`, which is exact and already in the row.
*The counter, stated fairly:* two poke rows with two different width vocabularies is one more thing to
learn, and CR-20's ruling warned specifically against *"two vocabularies wearing one name"*. The answer is
that these are two *names* (`write_memory`, `z80_write`) with two vocabularies, which is the shape that
ruling endorsed — it kept `z80_read` as its own row precisely because its bounds differ. But an adjudicator
who wants one width vocabulary across the bus should take `{1, 2, 4}`; it costs correctness nothing, only
honesty about the target machine. **Q2 in §11.**

**Why optional-with-default-1 rather than `write_memory`'s REQUIRED `width`.** This is the largest
departure in the CR and it deserves the strongest counter-case, which is given in §4.5.
The argument for it has three parts:

1. **A width-free `value` on a Z80 has an obvious right answer, and a width-free `value` on a 68000 does
   not.** `write_memory` can refuse `{addr, value}` honestly because 1, 2 and 4 are all plausible and the
   server would be guessing. On an 8-bit bus, 1 is not a guess — it is what the machine's data bus is, and
   it is what the only shipped implementation deliberately chose, in a comment, for that reason (§2.4).
   The contract's job here is to write down an answer that already exists, not to refuse a question that
   already has one.
2. **It preserves every observed invocation verbatim.** Every one passes a bare `value` or a `bytes`
   string (§2.5); none passes `width`. A REQUIRED `width` makes every bare-`value` invocation `-32602`.
   Since these are *manual* callers (§2.5), there is no script to migrate — the migration is people and
   agents across 23 aeon documents remembering a new required parameter, and the failure mode of
   forgetting is a refusal on a workflow that worked yesterday.
3. **It is strictly additive on the params side, under a rule the contract already owns.** §2.5 makes
   request params closed: *"A server MUST refuse a request carrying a top-level `params` key that the
   method's schema fragment does not declare"* (`protocol.md:582-583`), reinforced as §8 item 22. Since
   `z80_write` now *has* a fragment, and that fragment does not declare `width`, **a conformant server must
   refuse `width` today**. Adding it can therefore only widen the accepted set: no client can be relying on
   `width` being accepted, because the contract requires it to be rejected. (This also means the legacy
   server's silent ignoring of `width` is already non-conformant with §2.5, independently of D-10 —
   recorded in §9, not proposed as a fix here.)

### 4.4 Where this departs from the audit's recommendation

The audit recommends: *"adopt (b) explicitly, with `width` and **little-endian** stated (the Z80 stores low
byte first…), and state the `0–$3FFF` bound on the write row too"*, where (b) is *"`value` takes
`write_memory`'s width machinery, with the Z80's little-endian order"* (`audit.md:160-165`).

This CR adopts (b)'s **byte order** and (b)'s **address bound** unchanged, and departs on the two
remaining parts of "`write_memory`'s width machinery": the **domain** ({1,2} not {1,2,4}, §4.3) and the
**requiredness** (optional-default-1 not REQUIRED, §4.3). Both departures are in the direction of the
audit's own reading (a) — the shipped legacy behaviour — which this CR treats as the *floor* the design
must not fall below rather than as the answer. The result is neither (a) nor (b): it is (a)'s default with
(b)'s ceiling, so that every existing call keeps its meaning while a 16-bit poke stops being a
hand-marshalling exercise.

### 4.5 Alternatives rejected, and the case for the strongest of them

**(a) `value` is always one byte; `width` is never accepted.** *This is the strongest alternative and this
CR does not consider it unreasonable.* It closes D-10 completely and with less machinery than B1: `len` is
always `1` on the `value` path, there is no byte order to specify because no multi-byte numeric write
exists, the fragment gains a `maximum: 255` and nothing else, and the shipped implementation is already
conformant on the day it lands. It also has an authored justification from the implementer who chose it
(§2.4). **The case against it, which is why B1 is recommended instead:** a client poking a 16-bit Z80
pointer — a sound driver's stream read pointer is the canonical case, and the observed aeon workflows poke
around exactly such structures — must hand-assemble `bytes: "0x021F"` from the value `$1F02`. That
byte-swap is silent when done backwards, it is the server's job on the sibling row, and "we declined to do
it so the client must" is a worse contract than "we do it and say which order". *An adjudicator who weighs
minimalism above that ergonomic argument should take (a); it is a defensible ruling and B2, B3, B4 and B5
are unaffected by it.* **Q1 in §11.**

**(b) verbatim — `width` REQUIRED with `value`, domain `{1,2,4}`, little-endian.** The audit's
recommendation as written. Rejected on §4.3's three grounds; the requiredness is the operative objection
(it refuses every bare-`value` invocation on record, for a question that has an obvious answer on an
8-bit bus).

**(c) Strike `value` from the row entirely; `bytes` is the only spelling.** Superficially the cleanest — one
payload spelling, no width, no order, `len` trivially determinate. Rejected on two independent grounds:
D5 bars removing a catalogued spelling, and §2.5's evidence shows `value` is the spelling every observed
caller actually uses.

**(d) Keep `value` width-free but make the reply carry `bytesWritten` instead of `len`.** Renames the
symptom. `len` is REQUIRED by the row and by the fragment; the defect is that it has no defined value, not
that it has the wrong name.

## 5. B2 — the tail bound and the mirror ★ the item the audit did not register

**This section reports a defect that is live in the only running implementation today, that no numbered
audit defect covers, and that this CR considers more severe than D-10.**

### 5.1 The finding

Both legacy handlers bound only the **start** address. `OpZ80Write` checks `addr > 0x3FFF` (`:724`) and
then writes the payload with `WriteRamByte(d.z80ram, addr + i, bytes[i])` in a loop (`:743-747`).
`WriteRamByte` folds its address — `off = pow2 ? (addr & (bytes - 1)) : (addr % bytes)` (`:306`), with
`bytes = 0x2000` for the Z80 RAM — and **returns `true` unconditionally** once the device is present
(`:298-320`). Nothing checks `addr + len`.

Therefore: **`z80_write {addr: "0x3FFF", bytes: "<16 bytes>"}` writes one byte at `$3FFF`, then folds
`$4000 → $0000` and overwrites the first fifteen bytes of Z80 sound RAM, and replies
`{addr: "0x3FFF", len: 16}` — success.** The same is true of `z80_read`, whose source comment states the
behaviour without treating it as a problem: *"ReadBusByte folds the address modulo the device size
(0x2000), so the `$2000-$3FFF` mirror and **len-wraparound** are handled here"* (`:708-709`).

Precision matters here, and the precise statement is narrower than "the mirror is a bug":

- A fold of `$2000–$3FFF` down to `$0000–$1FFF` is **correct**. It is the hardware mirror, and both
  implementations agree on it (`oracle-core/src/bus.rs:929,1020`; legacy `Z80RamRangeError` at `:690-692`
  names the mirror explicitly). An access spanning `$1FFF → $2000` touching the same storage twice is
  right, even though a client cannot tell from the reply that it did.
- A fold of **`$4000 → $0000`** is **wrong**. `$4000` on a Z80 is the YM2612, not RAM. The access has left
  the region the row bounds, and instead of being refused it silently lands somewhere else.

So the defect is exactly: *an access whose end runs past `$3FFF` wraps instead of being refused.*

**The brief that commissioned this CR carried this as an unverified observation. It is confirmed, and the
confirmation is this section: `ControlSocket.cpp:743-747` + `:298-320` + `:306` for the write,
`:701-712` + `:275-294` + `:287` for the read, at `oracle-old` `d629771`.** The wording in the brief said
the write "wraps mod 8 KiB and clobbers `$0000`", which is right; the refinement above is that the clobber
is a defect only past `$3FFF`, since below it the fold is the hardware.

### 5.2 Why this outranks D-10 in severity

D-10 is an *underspecification*: two conformant servers could disagree, but no server is currently wrong,
and today's callers are unaffected because they all pass single bytes. B2's defect is a **silent wrong
answer in a running implementation**: the caller is told `len: 16` and success, the bytes are not where the
reply says they are, and the memory that *was* overwritten belongs to whatever else the sound driver keeps
at `$0000`. It is the exact failure class this bus repeatedly writes rules to prevent —

> **refused, never clipped**, because a clipped read reports bytes it never looked at
> — `protocol.md:939-940`

> refused, never wrapped or clamped
> — `protocol.md:960`

and it is unreachable by any client-side workaround, because a client cannot distinguish a wrapped success
from a real one.

**⟨RUNTIME⟩** This is a source-derived finding. A one-call confirmation against the live legacy server —
`z80_write {addr:"0x3FFC", bytes:"0x0102030405060708"}` then `z80_read {addr:"0x0000", len:4}` — would
settle it observationally. It was **not attempted**: this CR is barred from touching `mcp__oracle__*`.
Tagged for foreground follow-up.

### 5.3 The proposal

On **both** Z80 rows:

- `addr` is `0–$3FFF` (this half is D-10's recommendation, applied to the write row as the audit asks).
- An access whose **end** — `addr + len`, or `addr + payload length` — runs past `$3FFF` is **`-32004`,
  refused, never wrapped and never clipped**.
- `$2000–$3FFF` **mirrors** `$0000–$1FFF`: it is 16 KiB of address space over 8 KiB of storage, and an
  access spanning `$1FFF → $2000` touches the same storage twice. Stated so a client reading `len` bytes
  from `$1FF0` knows why the tail repeats.
- `z80_write`'s payload takes the same `$2000` ceiling `z80_read`'s `len` has — refused, never truncated.
  The row states **no payload cap at all** today, which is the third unstated bound on it.

**The bound stays `0–$3FFF`, and narrowing it to `0–$1FFF` is specifically not proposed.** That narrowing
has already been raised in this repo and **ruled against**:

> **The CR narrowed a catalogued bound. Twice.** `emulator/z80_read` is `addr` (0–`$3FFF`), `len` ≤ `$2000`
> in §6, and the working legacy implementation agrees (`$0000-$1FFF` mirrored at `$2000-$3FFF`, max 8192).
> The CR proposed `$1FFF` […] — which is not true of `z80_read` today at all.
> — `oracle/docs/2026-08-16-ruling-cr20.md:14-16`

Stating the mirror is the fix that ruling leaves available. Removing half the address space is not.

### 5.4 B2b — the generalisation, offered separately so B2 does not depend on it

While drafting B2 the contract was searched for a rule that already answers it, per the
precedent-before-invention discipline. **The rule exists — three times, never once generally.**

| where | text |
|---|---|
| `emulator/read`, `protocol.md:938-939` | *"A base outside its space, or a range whose **end** runs past it, is `-32004` — **refused, never clipped**"* |
| `emulator/memory_hash`, `:958-960` | *"the range must not run past that region's last byte […] `-32004` — refused, never wrapped or clamped"* |
| `emulator/write_memory`, `:970-972` | *"a base outside it, a range whose **end** runs past it […] is `-32004`, **refused, never clipped**"* |

Three rows, three hand-written copies, and the audit's D-16 recommendation asks for a **fourth** (*"state
`0–$FFFF`, refused, never clipped, with the `end`-past-the-space clause `read` already carries"*,
`audit.md:223-224`). B2 as written would make it a fifth and sixth.

**B2b, offered as an optional extra the adjudicator may take or leave:** state it **once**, in §6, as a
general rule —

> **The range rule.** Any method taking an address and a length is bounded at **both** ends. A base outside
> the method's stated region, or a range whose **end** runs past it, is `-32004` — **refused, never
> clipped, never wrapped, never clamped**. A row states its region; it does not restate this rule.

— and let `read`, `memory_hash`, `write_memory`, `write_vram` and both Z80 rows inherit it. The rule is
already universally true of every address-ranged row in the catalog; writing it once is a transcription of
existing practice, not new legislation, and it is why D-16's fourth copy and B2's fifth become unnecessary.

**The case against B2b, which an adjudicator may find sufficient:** (i) it legislates for rows this CR did
not audit, and a general rule can over-reach onto a future row where clipping is genuinely right —
a streaming or paginated read, say; (ii) it removes a per-row statement that an implementer currently reads
*at the row they are implementing*, which is where it is most likely to be obeyed; (iii) a CR scoped to two
Z80 rows is a strange vehicle for a document-wide rule. **B2 is written to stand alone: if B2b is
declined, B2 states the clause locally on both Z80 rows and nothing else changes.** **Q3 in §11.**

## 6. B3 — `len`'s default, its floor, and its ceiling (D-09)

### 6.1 The proposal

`z80_read`'s row becomes `len? (def 1, ≥1, ≤$2000)`, with the ceiling **refused, never clamped**.

### 6.2 The argument

**The default.** The audit's recommendation is *"`len? (def 1, ≤$2000)`, matching `read`"* (`audit.md:152-153`).
This CR adopts it unchanged, and adds the fact the audit did not have: **the legacy server already defaults
to 1** — `req.getInt("len", 1)` (`ControlSocket.cpp:701`). So B3's default half is a pure documentation fix.
It changes no behaviour on the only running implementation, and it agrees with `emulator/read`'s `def 1`
(`protocol.md:917`) and `read_memory`'s fragment `"default": 1`. There is no live disagreement to resolve —
only silence to fill.

**The floor, which the audit did not name.** The fragment gives `len` `"minimum": 0`
(`bus-protocol.schema.json:1655`). `len: 0` is therefore a valid request — **and no conformant reply to it
exists.** The result requires `bytes`, typed `$defs/hex`, whose pattern is `^0x[0-9A-Fa-f]+$` — one or more
hex digits, so the empty payload `"0x"` fails it. A server that honours `len: 0` cannot produce a reply that
validates. This is mechanically provable from the fragment alone and is a straight internal contradiction:
**`len` should be `minimum: 1`**, as `read_memory`'s and `read`'s are. (The same applies, harmlessly, to
`z80_write`'s result `len: minimum 0`: neither payload spelling can produce zero bytes, since the `bytes`
pattern requires at least one pair and `value` writes at least one byte. That one is unreachable rather than
contradictory, and B1's `width ≥ 1` keeps it so.)

**The ceiling, which is where the two implementations disagree.** §6 states `≤$2000`. The legacy server
applies it with `std::min<uint32_t>((uint32_t)req.getInt("len", 1), 0x2000)` (`:701`) — **silently clamped,
no error, no flag**. Two consequences: a caller asking for 10000 bytes gets 8192 and is told `len: 8192`
with nothing marking the shortfall, and — because `getInt` returns a signed value that is then cast —
`len: -1` yields 8192 bytes rather than a refusal. Silent clamping is against every stated instance of the
house rule (§5.4's table) and against the bus's own reasoning that *"a clipped read reports bytes it never
looked at"*. B3 states the ceiling as **refused, never clamped**, which makes the legacy behaviour
non-conformant — recorded in §9 as an accepted consequence, on the precedent quoted there.

### 6.3 Alternatives rejected

**Leave `len` with no default and make it REQUIRED.** Honest, and it would close D-09 by removing the
question. Rejected: it breaks the `read`/`read_memory`/`z80_read` family symmetry for no gain, `read` has
`def 1` and this row is its Z80 twin, and a required `len` makes the one-byte peek — the commonest use in
the observed workflows (`STAT_ALIVE` reads `$5A`, `STAT_TICK` keeps advancing) — more typing for no safety.

**Default to something larger, e.g. 16.** Guessing the caller's intent. `read`'s `def 1` is the precedent
and the least surprising value; a larger default silently moves more bytes than asked for.

## 7. B4 — `z80_write` in the run-control state rule (D-11) ★ severable

### 7.1 The proposal

Add `z80_write` to §6's named list:

> `run_to`, `run_to_scanline`, `run_frames`, `step*`, `press`, `play_input`, `reload_rom`, `write_memory`
> and `write_cram` require a **paused** machine.
> — `protocol.md:860-861`

### 7.2 The argument for

The rule's own stated reason is quoted by the audit and it transfers word for word:

> `write_memory` is named for `press`'s reason — a poke mid-free-run mutates the timeline just as surely,
> and leaving it unnamed would let one server refuse and another accept, both conforming.
> — `protocol.md:868-870`

A Z80 RAM poke is a poke. The silence is the specific harm the rule names.

And the direction is the reversible one — the contract says so explicitly, about this exact kind of gate:

> Requires a **paused** machine (see the run-control state rule) — **strict by design: relaxing a refusal
> later is additive (D5); introducing one is not.**
> — `protocol.md:979-981`

Gating now and relaxing later is a widening a future CR can make on evidence. Leaving it ungated and
gating later is a breaking change to whatever has come to depend on the free-running call. Under
uncertainty, that asymmetry favours the gate.

### 7.3 What the two implementations do

Neither gates it. Legacy `OpZ80Write` has no pause check (`ControlSocket.cpp:718-749`) — and neither does
legacy `OpWrite`, the 68000 poke that the contract **already** names in the rule (`:591-630`). So B4 does
not create a new divergence class: it moves `z80_write` into the same already-non-conformant bucket
`write_memory` occupies on that server today. The Rust server serves neither method, so it is unconstrained.

### 7.4 The argument against — measured, and strong enough that it could reverse this

**Every observed `z80_write` call site is a free-running poke, and the workflow depends on it.** From §2.5:

- *"With the song playing, use `emulator_z80_write` to set `SCF_SFX_OVERRIDE` (bit 6) …"*
  (`aeon/docs/superpowers/plans/2026-06-20-sound-phase5a-sfx-engine.md:408`)
- *"play MT; post CTRL=1 (`z80_write 0x1F07 0x01`): music freezes …, `SND_STAT_TICK` keeps counting; jump
  SFX still audible"* (`plans/2026-07-03-sound-game-feel-moments.md:191`)
- **13 posts to `$1F03` *"at ~0.8 s spacing via the aether bus (`emulator/z80_write`); every post verified
  consumed within 1 frame"*** (`notes/2026-08-10-r5-rekey-flam-trace.md:15-18`) — a machine that was
  demonstrably running, because a paused Z80 consumes nothing.

This is not incidental. **The Z80 sound driver's mailbox is a producer/consumer channel designed to be
written while the consumer runs**, and the observation being made in every one of these workflows is an
*audible* one — what the FM chip does after the post. Under B4 each becomes pause → poke → resume, and the
pause/resume brackets perturb the timing of the very thing being measured.

**And it inverts `write_cram`'s precedent rather than following it.** `write_cram` was named in the rule on
a second argument beyond symmetry:

> on a running machine a game that composes its palette every frame overwrites a direct CRAM write inside
> the frame it lands in, so the free-running call is not a weaker answer but a vanishing one. **The paused
> machine is where the method does its work**, which is a better argument for the gate than symmetry.
> — `protocol.md:870-874`

For the Z80 mailbox the second limb is false in the strongest way: the running machine is where the method
does its work, because the byte only means anything once the Z80 reads it. A CRAM poke on a running machine
vanishes; a mailbox poke on a running machine is *consumed*, which is the point. **An adjudicator could
reasonably rule the exemption on exactly this reasoning**, and it would be following `write_cram`'s own
argument rather than contradicting it — `emulator/reset` is the precedent for an affirmative exemption
written into the document with its reason (`protocol.md:880-884`).

### 7.5 The ruling recommended, and its escape hatch

**Name it**, on §7.2's reversibility argument — but the recommendation is held with less confidence than
B1's, B2's or B3's, and the recommendation carries an explicit relaxation path so §7.4's evidence is not
lost: if a consumer measures that the pause/resume bracket perturbs a sound-timing observation, that is a
CR to relax this gate, it is additive under D5, and §7.4 is its pre-loaded evidence.

**What must not happen either way is the silence.** The audit's formulation is right and this CR endorses
it without qualification: *"name `z80_write` […] in the rule, **or state affirmatively that it is exempt**.
The one thing that cannot stand is the silence, which is the rule's own argument for existing"*
(`audit.md:171-173`).

### 7.6 Alternatives rejected

**Exempt it affirmatively, with the mailbox reason written into §6.** Not rejected on the merits — it is
the live alternative, is argued in §7.4, and is **Q4/Q5 in §11**. It is not the recommendation only because
of §7.2's D5 asymmetry.

**Gate the `bytes` spelling and exempt `value`.** A gate that depends on payload spelling is a rule nobody
will remember, and the two spellings are the same operation.

**Gate it but let the server auto-pause and resume.** Barred outright: *"Servers MUST NOT resolve the
wrong-state case implicitly on the client's behalf"* (`protocol.md:817-820`).

rule's explanatory paragraph:

> `z80_write` *(named 2026-08-22)* is named for `write_memory`'s reason: a Z80 RAM poke mid-free-run mutates
> the timeline just as surely. It is named rather than exempted on the D5 asymmetry this section already
> states for `write_memory` — relaxing a refusal later is additive; introducing one is not — and a measured
> free-running mailbox workflow exists that a future CR may cite to relax it.

### 8.3 New normative blockquote in §6, under the two Z80 rows *(B1, B2, B3, B5)*

> **`emulator/z80_read` and `emulator/z80_write`** address the Z80's own 16-bit space, which is deliberately
> **not** a value in `emulator/read`'s `space` enum (see that row's note). Scope: `$0000–$3FFF`. A base
> outside it, a range whose **end** runs past it, or a payload that would run past it is `-32004` —
> **refused, never wrapped, never clipped**. `$2000–$3FFF` **mirrors** `$0000–$1FFF`: the region is 16 KiB
> of address space over 8 KiB of storage, so an access spanning `$1FFF → $2000` touches the same storage
> twice, which is the hardware and not an error.
>
> **`z80_read`**: `len` defaults to **1**, is at least 1, and is capped at `$2000` — a larger `len` is
> `-32602`, **refused, never clamped**, because a clamped read reports a byte count the caller did not ask
> for.
>
> **`z80_write`**: exactly one payload spelling — `bytes` (hex string, even digit count) or `value`, which
> MAY carry **`width`** ∈ 1|2 and **defaults to width 1**. Both spellings at once, or `width` with `bytes`,
> is `-32602`. A `value` that does not fit its `width` is `-32602` — refused, never truncated. A multi-byte
> `value` lands **little-endian** — the low byte at `addr` — because the Z80 stores low byte first; this is
> the one place where symmetry with `write_memory`'s big-endian rule would be **actively wrong**, and the
> rule both rows share is *"as the target machine stores"*. The reply's `len` is the byte count actually
> written: `width` on the `value` spelling, the decoded payload length on the `bytes` spelling. A payload
> over `$2000` bytes is `-32602`, refused, never truncated. Requires a **paused** machine (see the
> run-control state rule).
>
> A **`z80_write` is a debugger access, not a guest access**, on `write_memory`'s reasoning: it is never
> offered to the watch surface, because a hit's `pc` names the instruction that drove the access and a poke
> has none to name.

*(The final paragraph and the `require paused` sentence carry B4; drop both if B4 is struck.)*

### 8.4 Optional, if B2b is taken

Add **the range rule** (§5.4's text) to §6 as a general rule, and delete the fourth-copy clause from
§8.3's blockquote, leaving only *"Scope: `$0000–$3FFF`"* plus the mirror sentence. `read`, `memory_hash` and
`write_memory` keep their existing local statements — this CR does not propose editing rows it did not
audit — but D-16 and every future row inherit rather than restate.

### 8.5 Schema — `contract/schema/bus-protocol.schema.json`

No fragments are added; two are amended. **Fragment count does not move.**

`methods["emulator/z80_read"]`:
- `params.len.minimum` `0` → `1`; add `"default": 1`.
- Descriptions restate the bound as prose (D-32: bounds on hex-string fields are not schema-expressible),
  and the `end`-past-`$3FFF` clause is prose-only for the same reason.

`methods["emulator/z80_write"]`:
- Add `width`: `{"enum": [1, 2]}`.
- `dependentRequired`: `{"width": ["value"]}` — `width` with `bytes` is refused mechanically. **Note the
  asymmetry with `write_memory`, which has the pair in both directions** (`{"value": ["width"], "width":
  ["value"]}`); here only one direction is declared, because `value` without `width` is legal and means
  width 1.
- `value.maximum`: `65535`. The tighter must-fit-`width` check is prose, on `write_memory`'s precedent
  (`value` bounded `0..2^32-1` mechanically, must-fit-`width` left to the server).
- `result.len.minimum` `0` → `1`.

### 8.6 ⚠ Obligations this CR creates that no fragment can express

Listed explicitly so they land in a server's tests rather than in nobody's:

1. **The end-past-`$3FFF` refusal** — a relationship between `addr` and a payload length, on a
   hex-string address. Not expressible; server-side, and the one that §5 shows is live today.
2. **`value` must fit `width`** — `write_memory` has the identical unexpressible obligation.
3. **The little-endian placement** — a fact about bytes in memory, invisible to a schema entirely. The only
   way to check it is a write-then-read round trip.
4. **`len` refused-never-clamped at `$2000`** — the schema can reject `len: 8193`, but it cannot distinguish
   a server that refuses from one that clamps and reports `8192`.
5. **The mirror** — a client cannot detect from a reply that its range folded. Nothing to assert.

## 9. What this CR does and does not bind

**It binds the contract.** It does not bind any server's schedule, and it does not assert that either
implementer will conform by any date.

**What is asked of the Rust successor (this lane):** to implement the rows as ruled. It serves neither
method today, so there is nothing to migrate. This lane has no shipped behaviour that any of B1's readings
would break — which is precisely why it is a poor witness on D-10 and says so (§2.4).

**What is asked of the legacy C++ server: nothing by this CR.** It remains what `mcp__oracle__*` reaches.
If B1–B4 land, that server becomes non-conformant on this pair in five specific ways, enumerated so the
consequence is visible rather than implied:

1. `len` silently clamped at `$2000` rather than refused (`:701`) — B3.
2. The end-past-`$3FFF` wrap on both methods (`:743-747`, `:708-710`) — B2.
3. `value` over `0xFF` silently truncated (`:736`) rather than refused against `width` — B1.
4. No run-state gate on `z80_write` (`:718-749`) — B4. *(It is already in this position on `write_memory`,
   which the rule names today.)*
5. Missing `addr` silently writing to `$0000` (`:723`) — not proposed by this CR, but already
   non-conformant: the fragment marks `addr` REQUIRED. Recorded, not fixed here.

**Two further pre-existing non-conformances, recorded and not proposed:** the legacy server ignores an
unrecognised `width` rather than refusing it, which §2.5/§8 item 22 already requires it to refuse; and
`bytes` silently winning over `value` when both are given contradicts the fragment's `oneOf`. Neither is
created by this CR; both are noted so a future reader does not attribute them to it.

**That outcome is the accepted one under precedent this contract has set repeatedly** — quoted rather than
paraphrased:

> *Consequence, accepted with eyes open:* the moment this is normative the legacy C++ Oracle is
> **non-conformant** […] **a server on its way out does not get to hold the contract at the weaker shape**.
> — `protocol.md`, D11, as quoted in `oracle/docs/2026-08-22-cr-a-breakpoints.md:810-815`

**No compatibility flag is proposed.** There is deliberately no way to advertise the old shape:
`capabilities.z80: false` remains available to a server that does not serve the pair at all, which is this
lane's current state.

**One thing this CR explicitly does not do:** it does not touch `write_vram` (D-16), whose run-control
silence is the same defect as D-11 and whose address bound is the same defect as B2's. §11's Q6 asks whether
the ruling here should be stated to govern it.

## 10. Where this CR is weakest

Written so an adjudicator can rule against it on the merits without having to find the soft joints first.

### 10.1 The lane raising it has no implementation experience of either method

This is the most serious objection. D-10 is one of the three defects the audit says belongs to the legacy
server; the legacy server made a *deliberate, documented* choice (§2.4); and this CR asks to overrule half
of that choice, from a lane that serves neither method and has never had a client complain. §4.5's
ergonomic argument for `width` is a *prediction* about a client that does not exist yet. If the adjudicator
weights shipped experience above predicted ergonomics, **alternative (a) should win and B1 should fall.**

*(The related procedural worry — whether that audit clause reserves ruling *authority* over D-10 — is
treated as settled, not open: the oracle overseer resolved the identical question for CR-A at
`docs/2026-08-22-cr-a-breakpoints.md:963-986`, on the ground that the clause is *"a binding on scope, not a
reservation of authority"*, and D-10's own Recommendation likewise commissions an amendment by name
(*"adopt (b) explicitly… and state the `0–$3FFF` bound on the write row too"*). §11.2 lists it under
settled, and the adjudicator may of course disagree.)*

### 10.2 `width` optional here and REQUIRED on `write_memory` is a genuine inconsistency

§4.3 argues it is the *right* inconsistency. It is still one, and a reader of §6 will meet two poke rows
whose numeric spellings behave differently, with the difference explained only in a blockquote. If the
adjudicator's priority is a bus a newcomer can predict rather than one that matches each target machine,
take (b) verbatim and accept refusing every bare-`value` invocation on record.

### 10.3 B2's severity claim rests on source reading, not observation

§5 says the wrap is live today. That is derived from three functions read at `d629771`, not from a call.
The reasoning is short and the code is quoted, but it is inference. **⟨RUNTIME⟩** — see §10.5.

### 10.4 The `{1, 2}` width domain may be over-thinking it

The argument is that the Z80 has no 32-bit store. A debugger poke is not an instruction, and nobody is
harmed by `width: 4` being accepted. The domain choice is the least load-bearing decision in this CR and the
one this drafter would concede first.

### 10.5 Nothing here was confirmed at runtime

No emulator call and no `cargo` invocation was made — both are barred on this dispatch. Two items would
benefit from foreground confirmation and are tagged:

- **⟨RUNTIME⟩ §5.1** — the tail wrap. `z80_write {addr:"0x3FFC", bytes:"0x0102030405060708"}`, then
  `z80_read {addr:"0x0000", len:4}` against the live legacy server. If `$0000` holds `05 06 07 08`, §5 is
  confirmed observationally.
- **⟨RUNTIME⟩ §6.2** — the silent `len` clamp. `z80_read {addr:"0x0000", len:10000}` should, on the source
  reading, return `len: 8192` with no error.

### 10.6 The consumer evidence is documentary, not instrumented

48 mentions in checked-in markdown are strong evidence of *intended and recorded* use and weak evidence of
*frequency*. §7.4's case against B4 would be stronger with a session log and weaker if those documents are
stale. Two are checked-off completed steps and one is a written-up trace of 13 executed posts; most of the
rest are plan steps whose execution state this CR did not verify.

## 11. Questions for the adjudicator

### 11.1 Handed over undecided

**Q1 — D-10's shape.** Take B1 (optional `width` ∈ {1,2}, default 1, little-endian), or the audit's (b)
verbatim (REQUIRED `width` ∈ {1,2,4}), or the legacy's (a) (`value` is always one byte, `width` never
accepted)? §4.5 argues (a) is the strongest alternative and this CR does not think it unreasonable.

**Q2 — the width domain**, if Q1 lands on a `width` at all: `{1, 2}` (the Z80's store widths) or
`{1, 2, 4}` (one vocabulary across the bus)? §10.4 says this drafter would concede `{1,2,4}` first.

**Q3 — B2b, the general range rule.** State the both-ends bound once in §6 for every address-ranged method,
or write a fifth and sixth local copy? A CR scoped to two rows may be the wrong vehicle for a document-wide
rule even if the rule is right.

**Q4 — is B4 in this CR at all?** The audit pairs D-11 with D-16 (`write_vram`), not with D-10. B4 is
severable and nothing else depends on it. Rule it here, or route D-11 + D-16 to one run-control CR?

**Q5 — if B4 is ruled here: gate or exempt?** §7.2 argues gate (D5 reversibility); §7.4 argues exempt on
`write_cram`'s own reasoning, with measured free-running consumer workflows behind it. This is the closest
call in the document.

**Q6 — does the D-11 ruling govern `write_vram` (D-16)?** Whichever way Q5 goes, saying so here would stop
the next CR re-litigating it.

**Q7 — should the two Z80 rows move into the *memory & Z80* table?** Presentation, not semantics, but they
are currently below `write_memory`'s blockquote and a reader scanning the table misses them (§8.1).

### 11.2 Considered settled, and not asked

Listed so the adjudicator can see what this CR decided on its own authority and object if it overreached.

- **D-09's default is `1`.** Both the audit's recommendation and the shipped legacy behaviour
  (`ControlSocket.cpp:701`) say so, and `read` agrees. No live disagreement exists.
- **`len` must be `minimum: 1`, not `0`.** Mechanically provable from the fragment: `len: 0` admits no
  conformant reply, because `$defs/hex` cannot express an empty payload (§6.2).
- **Byte order is little-endian** *if* a multi-byte `value` exists at all. The audit and this CR agree
  independently; it is a fact about the Z80, not a design choice.
- **The address bound stays `0–$3FFF`.** Narrowing to `$1FFF` was ruled against in this repo at
  `docs/2026-08-16-ruling-cr20.md:14-16`; this CR does not reopen it.
- **The end-past-`$3FFF` wrap is a defect.** §5. What is *asked* is only whether it is stated locally or
  generally (Q3), never whether wrapping is acceptable.
- **This CR is procedurally in order.** §10.1's parenthesis, on CR-A's overseer ruling at
  `docs/2026-08-22-cr-a-breakpoints.md:963-986`.
